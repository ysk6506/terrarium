## 끝나지 않은 작업

**"맡겨도 되나" 2단계: 승인**(REQ-124). 브랜치 `paused/trust-2-approval`에 중간 상태를 저장했어요. PR은 없어요. 코어의 승인 요청, 허가, 승인하는 상대, 관문의 까닭을 쓰던 중이고, 타입 검사와 시험이 통과하는지 확인하지 않았어요. 이어서 할 때 지킬 것은 [설계의 4절](../../design-docs/trust-experiments.md)과 다음이에요.

- 기본(스스로 조치)에서는 지문과 점수 분해가 바이트까지 같다.
- 조치인지의 판정, "조회했다"와 "영향 범위를 확인했다"의 판정은 1단계 것을 그대로 쓴다. 두 벌을 만들지 않는다.
- "서비스에 닿는 조치"는 에이전트가 `get_impact`로 받는 것과 같은 계산을 쓴다.
- "조치 뒤에 확인한다"의 창(지금 600초 고정)을 실험 조건으로 연다.
- 화면 단계가 쓸 값을 기록에 남긴다: 요청마다 시각·툴·대상·까닭·답·기다린 시간, 허가마다 어느 요청에서 나와 어느 호출이 썼는지, 막힌 호출마다 까닭.
- 사람에게 묻기의 답을 승인으로 세지 않는다.

## 그다음 차례 (위에서부터)

1. 권한: #81 병합, 그다음 프록시와 SSO를 끝에서 끝까지와 배포 안내.
2. 셸 엔진의 기본을 바꾸는 걸음(ADR-0196의 2b). 먼저 채울 것: 한도 크기를 실제 쓰는 양을 재서 정하기, 새 엔진으로 깨지는 기존 시험 목록, 시험 시간에 더하는 양, 조사에서 나온 빈틈 15개의 시험. **벽시계 안전망은 정상 실행에서 닿지 않을 만큼 넉넉해야 하고, 닿은 줄은 점수에 들어가지 않아야 한다**(기계가 바쁠 때 안전망이 먼저 터져 결과가 달라진 것을 #79에서 확인했다. 점수에 안 들어가는지는 확인하지 못했다).
3. 승인(위).
4. 진짜 툴 붙이기 한 줄(ADR-0204): 본보기 툴 서버, 뒷문(Redfish 끝점) → 앞문 → 샌 호출 감지와 발자국 → 능력 목록.
5. 운영 실험의 깊이 → 묶음과 판정 → "맡겨도 되나" 화면. 화면 목업은 저장소 밖(제품 책임자 계정의 디자인 캔버스)에 다섯 장이 있다: 새 실험의 "어디까지 맡기나요", 업무 판정, 실행 상세의 승인과 규칙, 범위만 다를 때 나란히 보기, 근무 판정.
6. 한계 순위 목록, 바탕과 스냅샷 한 줄.

## 알고 있는 문제 (아직 고치지 않음)

| 문제 | 아는 것 | 다음 |
|---|---|---|
| UX 측정 작업이 main에서 계속 빨강(필수 검사는 아님) | 매력 96.4점이 하한 98 아래. 첫 화면이 받는 양이 827kB로 예산 700kB를 넘는다. 3D와 토폴로지 그림 도구가 처음부터 함께 내려온다(TD-0004) | 그 화면을 열 때 받게 나눈다 |
| 시험 조각이 가끔 `Timeout calling "onTaskUpdate"`로 실패(시험은 통과) | 한 시험이 CPU를 45~61초 쥐는 파일이 셋(offered-means-campus 계열의 시험 파일), 시험 도구의 통신 제한이 60초. 추정이고 확정하지 못했다 | 그 파일만 부하를 주며 여러 번 돌려 60초를 넘을 때만 나는지 본다. 그때까지는 실패한 작업만 다시 돌린다 |
| 고장이 번지는 계산이 세 벌 | 물리 엔진, 영향 범위(`packages/core/src/topology/impact.ts`), 툴 `get_impact`의 처리기가 따르는 링크 목록이 다르다 | 하나로 모은다. 승인 규칙과 채점 신뢰에 걸린다 |
| "악화"는 조치 뒤 180초 안에 생긴 것만 본다 | 더 늦게 나타나는 악화를 놓친다 | 운영 실험의 깊이에서 |
| 열린 타입이 코드에 없다 | 객체 종류는 닫힌 목록이고 모르는 종류가 든 세계는 거절한다. 문서(ADR-0165)는 열려 있다고 말한다 | ADR-0204의 12번대로 |
| 화면 여정이 가끔 시간 초과 | 한 번은 시나리오 고르기 화면의 템플릿이 모두 "이 세계에 필요한 장비가 없어요"로 회색이었다(#68의 증거 줄) | 세계가 열리기 전에 화면이 그려지는지 본다 |
