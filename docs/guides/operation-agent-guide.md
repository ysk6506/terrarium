# 운영 에이전트 설계 가이드

운영 모드는 사건 하나를 푸는 시험이 아니라 **정해진 시간 동안 데이터센터를 맡는 시험**이에요. 이 글은 그 시험에 내보낼 에이전트를 만드는 사람을 위한 규정집이에요. 읽고 나면 알게 되는 것은 다섯 가지예요.

1. 운영 모드가 어떻게 돌아가는지
2. 에이전트가 쓸 수 있는 툴과 지켜야 할 규약
3. 무엇이 점수가 되는지
4. 상주하는 에이전트의 모양 (하네스별 예)
5. 처음 만들 때 자주 하는 실수

## 1. 운영 모드는 이렇게 돌아가요

- 실험을 만들 때 종류에서 **운영**을 고르면 시나리오 대신 **운영 시간**(예: 8시간, 48시간)과 **고장이 나는 방식**을 정해요.
- 세계는 장비 종류마다 정해진 고장률(MTBF)로 고장을 내요. 낮에 더 자주 나고 밤에는 드물어요. 같은 시드면 같은 고장이 같은 시각에 나요. 한 고장이 이웃 장비의 고장을 부르거나(연쇄) 같은 순간에 둘이 나기도 해요.
- 고장은 사건 기록에 `fault.add`(원인 `generator`)로 남아요. 에이전트에게는 고장 자체가 아니라 **알람**만 보여요.
- `submit_diagnosis`는 **사건 하나를 닫는 용도**예요. 운영은 시간이 다 되거나 사람이 멈출 때 끝나요.
- 세계는 **아무것도 밀어 주지 않아요.** 알람이 올라와도 에이전트를 깨우지 않아요. 에이전트가 스스로 가서 봐야 해요. (실험 변수 "알람마다 깨우기"를 켠 실험만 예외예요. 이 변수는 연결이 지원할 때만 켜져요.)

### 시간: 실시간과 빨리 감기

| | 세계의 시간 | 점수 |
|---|---|---|
| 실시간 | 실제 시간과 같아요. 8시간 운영은 정말 8시간 걸려요 | 공식 점수 |
| 빨리 감기 | 조용할 때만 10~60배로 흘러요 | 결과와 벤치마크 키에 "빨리 감기 N배"가 붙어요. 공식 점수가 아니에요 |

빨리 감기에서도 아래 동안은 **실제 속도**로 돌아와요.

- 알람이 새로 올라온 뒤 5분(실제 시간)
- 담당자 팀의 소식이 있은 뒤 5분(실제 시간)
- 에이전트가 툴을 부르는 동안과 부른 뒤 2초(실제 시간)

그래서 느긋하게 기다리는 에이전트는 빨리 끝나고, 바쁘게 움직이는 에이전트는 실제 시간만큼 걸려요. 기록에는 세계 시간과 실제 시간이 모두 남아요.

**테라리움 서버가 멈췄다 다시 켜져도 운영은 이어져요.** 서버가 다시 켜지면 멈춘 자리에서 세계를 다시 세우고(멈춰 있던 동안 세계 시간은 흐르지 않아요) 에이전트를 다시 시작해요. 이때 프롬프트 끝에 "서버가 멈췄다가 다시 시작됐고 운영은 멈춘 자리에서 이어졌어요. `events_since(0)`으로 확인하고 이어서 맡아 주세요"가 붙어요. 툴 주소는 그대로이고, 서버가 없던 동안 간 호출은 실패해요. 그래서 호출이 실패하면 잠시 뒤 다시 하고, 다시 시작했을 때는 `cursor`를 0부터 새로 시작하세요. 결과에는 "서버가 다시 시작돼 n분 뒤 이어 갔어요"가 남아요.

## 2. 툴과 규약

모니터링은 **당기기**예요. 아래 다섯 툴이 전부예요.

| 툴 | 하는 일 | 규약 |
|---|---|---|
| `events_since(cursor)` | 새 알람, 알람이 풀린 것, 넘긴 일의 진행과 완료 | `{ cursor, events }`를 돌려줘요. **돌려준 `cursor`를 다음 호출에 그대로 넘기세요.** 처음에는 0이에요. 이벤트 종류: `alarm_raised`, `alarm_cleared`, `handed`, `started`, `done`, `shutdown` |
| `list_alarms` | 지금 올라와 있는 알람 | 풀린 알람은 안 보여요. 놓친 사이에 풀렸다면 `events_since`로만 알 수 있어요 |
| `query_metrics` | 장비 하나의 지표를 시간순으로 | 알람이 없는 장비도 볼 수 있어요. 조용할 때 쓰면 비용만 들어요 |
| `service_status` | 서비스 하나의 상태와 이유 | 서비스를 살리는 일이 점수의 중심이에요 |
| `wait(seconds)` | 기다리기 | **실제로 그만큼의 세계 시간이 흐른 뒤에 돌아와요.** 빨리 감기에서는 조용하면 빨리 돌아와요. 하네스가 이 호출에 시간 제한을 걸지 않게 하세요 |

조치와 넘기기에는 `failover_service`, `migrate_vm`, `restart_service`, `run_command`(가짜 셸), `escalate(domain)`, `ask_human`이 있어요. 규약은 같아요.

- 툴 호출 한도(기본 5,000회)에 닿거나 시간이 다 되면 실행이 끝나요. 끝난 뒤의 호출은 "실행이 끝났다"는 오류를 받아요.
- `escalate`는 그 시점의 고장만 넘겨요. 나중에 생긴 고장은 다시 넘겨야 해요. 맡은 팀이 끝내는 시각은 몇 시간 뒤이고 `events_since`에 `done`으로 와요.
- `ask_human`은 사람이 답할 때까지 열려 있고, 기다린 시간은 에이전트의 시간으로 세지 않아요.
- 조치로 옮겨 둔 것(VM 이동, 서비스 대기 전환)은 팀이 끝낸 뒤 **되돌리는 것까지**가 일이에요.

## 3. 점수가 되는 것

결과 화면의 첫 줄은 **서비스 가용률 · 놓친 알람 · 탐지 지연** 셋이에요. 아래는 모두 사건 기록에서 계산해요.

| 지표 | 뜻 | 계산 |
|---|---|---|
| 서비스 가용률 | 서비스가 돌아간 시간의 비율 | 1 − (멈춘 시간 + 느린 시간의 30%) ÷ (서비스 수 × 운영 시간) |
| 놓친 알람 | 올라온 뒤 어떤 조회로도 보지 않은 알람 | 알람이 올라온 뒤 `events_since`·`list_alarms`·`service_status`·`list_services`·`get_impact` 중 하나를 부르지 않았고, 알람이 떠 있는 동안 그 장비를 조회한 적도 없는 알람의 수. `events_since`는 풀린 뒤에 불러도 그 알람을 보여 주므로 본 것으로 쳐요 |
| 탐지 지연 | 고장이 난 뒤 처음 알아챌 때까지 | 고장마다 (발생 → 그 뒤 처음 알람을 보여 주는 조회)의 중앙값. 끝까지 조회하지 않은 고장은 끝까지로 세요 |
| 사건별 복구 시간 | 고장이 난 뒤 끝날 때까지 | 최소·중앙·최대. 고장이 사라지거나, 그 장비가 올린 알람이 모두 풀리면 끝난 것으로 봐요 |
| 악화 | 조치 때문에 멀쩡하던 서비스가 멈춘 횟수 | 조치 뒤 3분 안에 멈춘 서비스 |
| 에스컬레이션 | `escalate`와 `ask_human`의 횟수 | |
| 사건당 비용 | 툴 호출과 토큰을 사건 수로 나눈 값 | 토큰은 하네스가 알려 줘야 나와요 |
| 조용할 때 쓴 비용 | 알람이 없는 동안의 호출 수와 토큰 | 토큰은 호출 수 비율로 어림해요 |
| 감시 주기 | 알람을 확인한 간격의 중앙값 | 10초 안에 이어진 조회는 한 번으로 세요 |

**줄다리기**가 설계의 핵심이에요. 자주 볼수록 놓친 알람과 탐지 지연이 줄고 비용이 늘어요. 얼마나 자주 볼지는 에이전트가 정해요. 5분 주기가 출발점으로 좋아요.

## 4. 상주 루프의 모양

어느 하네스든 에이전트의 일은 같은 루프예요.

```
cursor = 0
반복:
  news = events_since(cursor);  cursor = news.cursor
  멈춘 서비스가 있으면: 서비스부터 살리기 (VM 옮기기, 대기로 전환)
  내 도메인 밖이 원인이면: escalate(도메인)
  news에 done이 있으면: 옮겨 둔 것 되돌리기
  wait(300)
```

### 하네스 프로토콜 (`terrarium.harness/1`)

`POST /runs`로 받은 과제는 몇 시간 이어질 수 있어요. `GET /runs/{id}`가 계속 `running`을 돌려주는 동안 실행이 살아 있어요. 에이전트는 `tools.mcpUrl`로 위 루프를 돌고, 시간이 다 되면 테라리움이 먼저 끝내요. 이때 마지막 `wait` 호출이 "실행이 끝났다"를 돌려주니 그걸 종료 신호로 읽으세요. 요청 하나가 몇 시간 이어져도 되는지(프록시·게이트웨이의 시간 제한) 먼저 확인하세요.

### OpenCode

`opencode serve`의 세션 하나에 과제를 보내고 `prompt_async`로 기다려요. 모델에게 주는 지시문에 위 루프를 그대로 적고, "툴 호출 결과의 `cursor`를 반드시 기억하라"고 쓰세요. 대화가 길어지면 컨텍스트가 차므로, 지시문에 "조용하면 `wait`만 부르고 설명을 쓰지 말라"를 넣어 토큰을 아끼세요.

### GoClaw

고정 도구 주소(slot)로 붙고 한 에이전트의 실행은 한 번에 하나예요. 몇 시간짜리 실행이 슬롯을 점유하니, 운영 실험은 그 연결에서 차례로 돌아요. 에이전트의 "한 번 답하고 끝나는" 성질이 문제라면 지시문에 루프를 적고, 하네스의 최대 반복 횟수 설정을 8시간 분량(5분 주기면 96번 이상)으로 늘려 주세요.

(세 예 모두 가짜 모델과 배관으로만 확인했고, 몇 시간짜리 진짜 모델 실행은 아직 재 보지 못했어요.)

## 5. 기준 에이전트 `operator`

테라리움에 들어 있는 `operator`가 이 루프의 최소 구현이에요. 운영 모드에서는 5분마다 `events_since`를 보고, 서비스를 먼저 살리고, 원인이 다른 팀의 것이면 한 번 `escalate`하고, 팀이 끝내면 옮긴 것을 되돌려요. 소스는 `apps/server/src/adapters/harness/scripted-operator.ts`예요. 내 에이전트의 점수를 이것과 나란히 놓고 보세요.

## 6. 자주 하는 실수

- **`cursor`를 버려요.** 매번 0으로 부르면 같은 알람을 계속 받아 비용만 늘어요.
- **원인부터 파요.** 점수는 서비스가 멈춘 시간이에요. 먼저 살리고 나서 파세요.
- **조용할 때도 조회해요.** `wait`로 기다리는 게 맞아요. 조용할 때 쓴 호출은 따로 세요.
- **되돌리기를 잊어요.** 팀이 끝낸 뒤에도 임시로 옮긴 서비스가 그대로면 다음 사건에서 불리해요.
- **`submit_diagnosis`로 끝내려 해요.** 운영은 그걸로 끝나지 않아요. 사건 하나를 정리하는 용도로만 쓰세요.
