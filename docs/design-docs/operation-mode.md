# 운영 모드 (REQ-090, [ADR-0094](adr/0094-operation-mode.md))

## 한 문장으로

**운영 모드는 "사건 하나를 푸는 시험"이 아니라 "정해진 세계 시간 동안 데이터센터를 맡는 시험"이다.** 고장은 무작위로 나고, 세계는 아무것도 밀어 주지 않으며, 에이전트가 스스로 보러 가는 만큼 점수가 갈린다.

## 실험의 두 종류

| | 사건 하나 | 운영 |
|---|---|---|
| 과제 | 시나리오 하나 | 운영 시간(1~96시간)과 고장이 나는 방식 |
| 끝 | `submit_diagnosis`, 호출 한도, 시간 | 운영 시간이 다 되거나 사람이 멈출 때, 호출 한도 |
| 점수 | 채점표 | 없다. 운영 지표(아래)가 결과다 |
| 레시피 | `scenarioId`가 저장된 시나리오 | `operation`이 있고 `scenarioId`는 `operation` |

운영 실험은 저장된 시나리오가 없다. 과제는 설정 그 자체이고, 세션이 "에이전트 투입 하나뿐인 시나리오"를 코드로 만든다(`operation/scenario.ts`). 고장은 시나리오 흐름이 아니라 발생기가 내므로 같은 설정에 시드만 바꾸면 다른 하루가 된다. 스냅샷의 `scenarioDigest`는 설정의 해시이고, **벤치마크 키에는 길이·시간 방식·고장 출처·고장률·연쇄·동시가 들어가고 지시문은 안 들어간다**(지시문은 에이전트의 조건이다).

## 고장 발생기 (결정 1)

시드에서 한 번에 계획을 세운다(`planFaults`). 같은 시드·같은 세계·같은 설정이면 같은 계획이다. 계획의 항목은 세계의 시각이 되면 `fault.add`(원인 `generator`)로 들어가고 사건 기록에 남는다.

- **장비 종류별 MTBF 표.** 장비 한 대가 평균 몇 세계 시간에 한 번 고장 나는가(아래). 한 세계의 고장률은 `Σ 장비 수 ÷ MTBF`이고, 표의 값은 모의 세계에서 8시간 동안 몇 건이 보이도록 데이터시트보다 짧게 잡았다.
- **프리셋.** 조용함 ×0.3, 보통 ×1, 바쁨 ×3. 그 위에 `rateScale`(0.1~100)로 더 조절한다. 장비가 몇 대 안 되는 세계는 `rateScale`을 올려야 사건이 보인다.
- **시간대 패턴.** 세계에 하루 워크로드 패턴이 아직 없어서 기본값(낮 바쁨)을 쓴다: 새벽 1~3시 0.3배, 9~10시와 14~15시 1.8배가 가장 바쁘고 저녁으로 갈수록 줄어든다(하루 평균 1). 도착 시각은 가장 바쁜 시간의 비율로 뽑고 시간대 비율로 걸러 낸다.
- **연쇄·동시 고장.** 고장마다 `cascadeChance`로 가까운 장비(같은 랙·방)의 고장이 2~20분 뒤에, `simultaneousChance`로 다른 장비의 고장이 0~30초 안에 따라온다.
- **시나리오 세트.** "이 시나리오 세트를 n시간 안에 무작위 순서로": 시나리오의 `inject_fault` 블록만 가져와 처음 5%와 마지막 15%를 비우고 한 번씩, 바쁜 시간대에 더 자주 걸리게 놓는다. 시나리오의 조건·설정 변경 블록은 쓰지 않는다.
- 세계가 거부하는 고장(없어진 장비, 범위를 벗어난 값)과 준 툴로 닿을 수 없는 고장(고장 범위 "준 툴 안에서만")은 일어나지 않고 `left`로 센다. 결과에 "계획 N개 중 M개는 일어나지 않게 했어요"가 나온다.

## 시간 (결정 2): 시계 드라이버

`clockStep(pace, 기억, 지금, 흐른 실제 시간, 신호) → {세계 시간, 속도, 이유}`는 순수 함수다. 세션은 호스트가 알려 주는 "과제를 받은 뒤 실제 경과 시간"으로 `sync`를 부르고, 세션은 시계를 읽지 않는다.

| 방식 | 규칙 |
|---|---|
| 실시간 | 실제 1초 = 세계 1초, 언제나. 공식 점수는 이것만이다 |
| 빨리 감기 | 조용할 때만 선택한 배속(10~60배). 아래 중 하나면 1배 |

빨리 감기가 1배로 돌아오는 때: 알람이 새로 올라온 뒤 실제 5분(`alarm`), 담당자 팀의 사건이 있은 뒤 실제 5분(`event`), 에이전트가 툴을 부른 뒤 실제 2초(`call`). 몇 시간째 떠 있는 알람(맡은 팀이 오는 중)은 시계를 1배에 묶지 않는다. 그러면 빨리 감기가 그 뒤 내내 의미가 없어지고, 안 보는 에이전트가 쌓는 놓친 알람은 빨리 감기에서도 그대로 센다. `wait`는 호스트가 실제 시간을 흘려 세계 시간이 그만큼 흐를 때까지 붙들고 있다가 답한다(그래서 조용하면 빨리, 시끄러우면 실제 속도로 돌아온다). 사람의 답을 기다리는 동안 시계는 서고, 기다린 시간은 에이전트의 시간으로 세지 않는다. 결과·벤치마크 키에는 "빨리 감기 30배" 같은 표시가 붙고 "공식 점수 아님"이라고 쓴다. 화면 글에는 "벽시계" 대신 "실제 시간"을 쓴다.

## 모니터링은 당기기 (결정 4)

세계는 아무것도 밀어 주지 않는다. 에이전트가 보는 길은 `events_since(cursor)`, `list_alarms`, `query_metrics`, `service_status`(와 `list_services`·`get_impact`), `wait(seconds)`뿐이다. 안 보면 알람이 쌓이고 "놓친 알람"이 된다.

**알람마다 깨우기**는 실험 변수이고 기본은 꺼짐이다. 켜면 새 알람마다 한 줄 요약(`[경고] 서버 흡기 온도가 높아요 (srv-a1)`)을 하네스에 밀어 보낸다. 어댑터가 `wakeable`일 때만 켤 수 있고, 아니면 화면에서 회색이 되고 이유("이 연결은 알람 요약을 밀어 받을 수 없어요")를 보이며, 서버도 만들 때 거절한다. 지금 `wakeable`인 것은 내장 하네스(`operator`는 알람 요약이 오면 5분을 안 채우고 바로 본다)뿐이다.

## 측정 (결정 7)

사건 기록 하나에서 계산한다. 끝난 실행, 리플레이, 실행 중 카드가 같은 함수를 읽는다(`operationMetrics`, `incidents`).

| 지표 | 계산 |
|---|---|
| 서비스 가용률 | `1 − Σ(멈춘 시간 + 느린 시간의 30%) ÷ (서비스 수 × 운영 시간)` |
| 사건 | 발생기가 낸 고장. 끝은 고장이 사라진 때, 또는 그 장비가 올린 알람이 모두 풀린 때 중 이른 쪽 |
| 사건별 복구 시간 | 끝난 사건의 (끝 − 발생): 최소·중앙·최대. 못 끝낸 사건은 `열린 사건`으로 센다 |
| 놓친 알람 | 올라온 뒤 `events_since`·`list_alarms`·`service_status`·`list_services`·`get_impact` 중 하나를 부르지 않았고, 떠 있는 동안 그 장비를 조회한 적도 없는 알람 수. `events_since`는 풀린 뒤에도 그 알람을 보여 주므로 본 것으로 센다 |
| 탐지 지연 | 사건마다 (발생 → 그 뒤 처음 알람을 보여 주는 조회)의 중앙값. 끝까지 조회가 없으면 끝까지로 세고 `미탐지`로 따로 센다 |
| 악화 | 조치 직후 3분 안에 멈춘 서비스(복구 우선 채점의 악화와 같다) |
| 넘긴 일 | `escalate` 성공 호출 + `ask_human`으로 물은 일의 수 |
| 사건당 비용 | 툴 호출 수 ÷ 사건 수, 토큰 ÷ 사건 수(하네스가 알려 줄 때) |
| 조용할 때 쓴 비용 | 알람이 하나도 없는 동안의 호출 수, 그리고 토큰의 어림(총 토큰 × 조용할 때 호출 ÷ 전체 호출) |
| 감시 주기 | 알람을 보여 주는 조회 사이 간격의 중앙값(10초 안에 이어진 조회는 한 번) |

결과 화면의 첫 숫자 셋은 **가용률 · 놓친 알람 · 탐지 지연**이다. 타임라인은 기존 리플레이 시간 막대에 "봤다" 점(알람을 보여 주는 조회, 조회는 이것만 점이 된다), "사람 개입" 점(`ask_human`과 사람의 조치), 사건마다 발생에서 끝까지의 복구 막대(끝나지 않은 것은 빨간색)를 더한 것이다.

### 변별력 (가짜 에이전트, 8시간 빨리 감기 30배)

세계는 서비스 홀(서버 3대), 고장은 시나리오 세트의 5개, 시드 11. 시험은 `operation/discrimination.test.ts`.

| 에이전트 | 가용률 | 놓친 알람 | 탐지 지연 | 열린 사건 | 호출 | 조용할 때 호출 | 감시 주기 |
|---|---|---|---|---|---|---|---|
| 아무것도 안 함 | 79.7% | 14/14 | 2시간 8분(미탐지 5) | 3 | 0 | 0 | — |
| 5분마다 조회만 | 79.7% | 0/14 | 2분 38초 | 3 | 96 | 64 | 301초 |
| 5분마다 조회+복구 | 99.2% | 0/8 | 2분 38초 | 0 | 96 | 92 | 301초 |
| 1분마다 폭주 | 99.6% | 0/8 | 41초 | 0 | 944 | 928 | 61초 |

조회만 하는 에이전트는 놓친 알람은 없애지만 가용률은 못 올린다. 복구하면 가용률과 열린 사건이 갈린다. 폭주는 탐지를 빠르게 하지만 호출이 10배로 늘고 거의 전부 조용할 때 쓴다. 복구는 에이전트의 복구 툴 대신 "떠 있는 고장을 지우는" 대용품이다(툴 하나의 물리에 시험이 기대지 않도록).

## 운영상 필요 (결정 8)

- **중간 점검 카드.** 홈과 실험 화면에 실행 중인 운영마다 "14시간째 · 열린 사건 1 · 놓친 알람 0 · 다음 담당자 완료 2시간 뒤". 실행 중 기록은 에이전트가 한 시간 동안 호출하지 않아도 갱신되도록, 서버가 1초마다 새 사건을 읽고(워커가 호출 사이에 쓴 사건을 `events` 메시지로 보낸다) 화면이 5초마다 다시 읽는다.
- **예산 상한.** 툴 호출 상한(기본 5,000번)을 넘으면 세션이 `tool_budget`으로 끝내고 결과에 "툴 호출 N번 상한에 닿아 멈췄어요"가 나온다. 시간 상한은 운영 시간이다. 서버의 실제 시간 한도는 운영 시간 + 10분이다.
- **하네스 끊김과 재연결.** 운영 도중 하네스가 오류로 멈추면(툴을 한 번이라도 부른 뒤, 세션이 끝나기 전) 실제 5초 뒤 같은 요청을 다시 보내는 것을 세 번까지 한다. 다시 보낼 때 프롬프트에 "연결이 끊겼다가 다시 이어졌어요. `events_since(0)`으로 확인하고 이어서 맡아 주세요"가 붙는다. 끊김과 돌아옴은 사건 기록에 `link` 사건(`lost`/`back`, 이유)으로 남고 시간 막대에 "연결 끊김" 표식이 찍힌다. 호스트가 아는 가장 새 세계 시간에 끼워 넣고 순서 번호를 다시 매긴다. 세 번을 넘기면 기존 규칙대로 `agent_error`로 끝난다.
- **하네스가 오류 없이 끝나면**(`finished`) 기존 규칙대로 실행이 `agent_finished`로 끝난다.

## 서버 재시작 뒤 재개 (결정 8, [ADR-0112](adr/0112-operation-resume-and-presets-amend-tests.md))

세션은 시계를 읽지 않고 시드에서 시작하므로, **세션이 받은 입력을 순서대로 다시 넣으면 같은 상태가 된다.** 운영 실행은 그 입력을 실행 옆에 적어 둔다(`ExperimentStore.appendJournal`, 실행이 끝나면 지운다).

| 항목 | 규칙 |
|---|---|
| 기록하는 것 | 머리(세계 버전 해시·시뮬레이터 버전) · 호스트가 세션을 시계에 맞춘 시각(`s`, 실제 경과 초) · 에이전트의 툴 호출(`c`) · 사람의 조치와 답(`a`/`r`) · 호출을 본 실제 시각(`k`) · 연결 끊김 메모(`l`). 조각은 `core/session/operation/journal.ts`와 `core/experiments/journal.ts` |
| 쓰는 때 | 실행 중 1초마다(워커가 호출 사이에 쓴 입력도 `events` 메시지에 실려 온다), 호출마다, 멈추기 직전 |
| 서버가 멈출 때 | 운영 실행은 `failed`로 끝내지 않고 `running` 그대로 두고 기록만 마저 쓴다. 갑자기 죽어도 같다(최대 1초 전까지 남는다) |
| 서버가 다시 켜질 때 | `Dispatcher.recover()`가 `running`인 운영 실행에 기록이 있으면 대기열에 다시 넣고, `executeRun`이 입력을 `LocalSession`에 다시 넣어(`replayInputs`) 세션을 세운 뒤 거기서부터 이어 간다. 시계는 마지막 시각에서 이어지고 멈춰 있던 동안의 세계 시간은 흐르지 않는다 |
| 성능 | 호출 1만 개(사건 1만 개 이상)를 다시 넣는 데 약 0.3초(시험은 1초 한도: `journal.test.ts`). 호출 한도 계산을 호출마다 전체를 훑지 않게 센 값으로 바꿨다 |
| 결과 | 사건 기록에 `link` 사건 `lost`("서버가 멈췄어요") → `resumed`(멈춰 있던 실제 초)가 남고, 결과에 "서버가 다시 시작돼 n분 뒤 이어 갔어요"가 뜬다. 시간 막대에는 "연결 끊김" 표식이 찍힌다 |
| 하네스 | 같은 실행 주소(`/mcp/runs/<실행 id>/...`)가 다시 열리고, 하네스는 프롬프트에 "서버가 멈췄다가 다시 시작됐고 …`events_since(0)`으로 확인하고 이어서 맡아 주세요"를 붙여 다시 시작한다. 서버가 없던 동안 하네스가 보낸 호출은 서버가 받지 못하므로 사건 기록에는 `lost`~`resumed` 사이의 빈 구간으로만 남는다 |
| 이어 갈 수 없을 때 | 기록이 없거나, 실험이 가리키는 세계 버전이 바뀌었거나, 시뮬레이터 버전(`ORACLE_VERSION`)이 달라졌으면 "서버가 멈춰 중단됐어요. 세계 버전이 바뀌어 이어 갈 수 없어요"처럼 이유와 함께 `failed`로 끝낸다 |

다른 클러스터 노드에서 도는 세션은 입력을 넘기지 않아(`HostedSession.journalSince`가 없다) 재개할 수 없고, 서버가 멈추면 전과 같이 `failed`로 끝난다.

## 결과 상태 문구

운영 실행은 "제한 시간을 넘겨" 끝나는 일이 없다. `endReasonLabel(reason, operation)`(`oracle.ts`)이 운영의 말로 바꾼다: 시간이 다 되면 **운영 시간 끝(8시간)**, 사람이 멈추면 **멈춤(사람)**, 호출 상한이면 **호출 상한(5,000번)**. 결과 첫 줄(`score.summary`), 실행 목록의 한 줄(`endLabel`), 실험의 "끝난 이유"와 소견, 보고서 표에 같은 말이 쓰이고, 실행 상태 "멈춤"도 운영에서는 "멈춤(사람)"이다(`statusLabel(status, operation)`).

## 이번에 하지 못한 것

[build-plan](../exec-plans/active/build-plan.md)의 12g 항목에 적었다(재시작 뒤 재개와 지시문의 서버 저장은 2c 보완에서 했다): 토큰·비용 상한(하네스가 사용량을 실행이 끝나야 알려 줘서 중간에 끊을 수 없다), 알람마다 깨우기를 받는 연결(지금은 내장 하네스뿐), 운영 실험을 합친 순위표(벤치마크 화면은 점수가 없어 운영 세트의 순위를 못 낸다). 다른 클러스터 노드에서 도는 운영은 재개하지 못한다(위). 서버가 멈춘 동안 하네스 프로세스가 따로 살아 있었다면(밖에서 돌리는 에이전트) 다시 시작한 요청과 겹칠 수 있다. 시계 드라이버의 5분·2초 창은 가짜 에이전트와 코드로 정했고, 진짜 모델의 반응 시간으로 맞춰 본 것이 아니다.
