# ADR-0038 묶음 랙

## 맥락
사용자는 서버룸마다 컨테인먼트가 **수십에서 수백 개**씩 들어간다고 했다. 컨테인먼트 하나는 랙 8~24개이므로 홀 하나가 랙 수천 개이고, 서버까지 하나하나 개체로 만들면
캠퍼스가 수십만 개체가 된다. 지금 시뮬레이터는 개체 1만 개당 한 걸음(10초)에 0.15~0.2초가 든다(이 작업 환경). 개체 수에 비례하므로 서버를 모두 개체로 둔 큰 캠퍼스는
세션을 여는 데만 수 분이 걸리고 한 걸음마다 수 초가 든다. 반면 큰 홀에서 사용자가 보고 싶은 것은 랙이 어디 서 있고 얼마나 뜨겁고 어느 줄에서 전원이 끊겼는지다.
서버 하나하나의 팬 속도가 아니다.

## 결정
1. **묶음 랙**을 둔다. 랙 개체의 `props`에 `bulk: true`, `bulkServers`(대수), `bulkModel`(서버 모델), `bulkUtil`(평균 CPU 사용률), `bulkOverheadW`(스위치 등 나머지 전력)를
   적는다. 장치 자식은 없다. 새 개체 종류는 만들지 않는다(랙은 랙이다). 해석은 `world/bulk.ts`가 한곳에서 한다.
2. **전원**: 묶음 랙은 스스로 전력 소비자다. 분전반(블록의 스위치기어) A·B에 직접 전원 링크를 건다. 둘 중 하나라도 살아 있으면 켜져 있고, 둘 다 끊기면 서버가 모두 꺼진다.
   전력 = 오버헤드 + 대수 × (유휴 + (최대 − 유휴) × 사용률). 사용률은 `load.set`으로 바꿀 수 있다(랙 상태 `util`).
3. **열과 냉각**: 랙이 이미 하던 계산(흡기·배기 온도, 방 열, 후면도어·직접수랭의 액체 몫, 액침 탱크 유체)을 그대로 쓴다. 장치 합 대신 위에서 구한 전력을 쓰고,
   직접수랭의 액체 몫은 서버 모델의 `liquidShare`에서 얻는다. 냉방기·CDU 연결(`cooling` 링크)은 보통 랙과 같다.
4. **알람**: 흡기 과열은 랙 알람(기존). 전원이 끊기면 서버 알람이 없으므로 랙이 `rack_power_lost`(critical)를 올린다.
5. **검증**: W050(값이 맞지 않음), W051(서버 아닌 모델), W052(랙 U에 안 들어감), W053(장치도 직접 들고 있음), W054(전원 공급처 없음), 그리고 냉각 방식이 서버와
   안 맞으면 W030. 서버 사이 연결(네트워크)은 묶음 랙에 없다.
6. **생성기**: 캠퍼스 명세에 `detail`(0~1)을 둔다. 홀마다 컨테인먼트 중 이 비율만 서버까지 만들고 나머지는 묶음 랙이다. 상세한 컨테인먼트는 홀을 따라 고르게 퍼지고,
   홀마다 **첫 번째는 언제나 상세**하다(행동할 장비가 늘 있게). 기본값은 1(전부 상세)이라 지금까지의 세계는 그대로다. 캠퍼스 랙은 2만 개까지, 서버까지 만드는 랙은 3000개까지다.
   홀당 컨테인먼트 상한은 80에서 240으로 올린다.
7. **도구**: `get_entity`는 묶음 랙에 `inventory`(대수·모델·평균 사용률·"서버별 조회는 안 된다")를 보인다. 영향 분석(`get_impact`)은 묶음 랙을 서버처럼 전원·냉각 소비자로 따른다.
   Redfish 같은 서버 단위 API는 상세한 서버에만 있다.
8. **시뮬레이터 속도**: 같은 작업에서 공통 경로를 줄였다. 인덱스의 `ofKind`·`childrenOf`·`outgoing`·`incoming`·`enclosing`을 한 번 계산해 두고 읽기 전용으로 내준다.
   장애는 대상별로 묶어 둔다. 전원 공급 판정(`activeFeeds`)과 ATS 판정은 기억한다. 부하 집계는 한 번만 돈다(두 번째 패스는 첫 번째와 같은 값만 냈다).
   건강한 서버는 알람 규칙을 모두 돌지 않고 먼저 빠져나온다. 냉방기 목록도 한 번만 구한다.

## 이유
- 사용자가 홀을 보며 확인하려는 것(배치, 열, 전원, 냉각, 어떤 행동이 어디서 일어나는가)은 랙 단위로 충분하다. 서버 단위 정보는 행동할 장비 근처에만 있으면 된다.
- 랙은 이미 물리 개체이고 위치·냉각·열 계산이 랙에 붙어 있다. 새 종류나 새 계산을 만들지 않고 "장치를 합하는 방식"만 바꾸면 되어서 정확도와 유지비 모두 유리하다.
- 상세 비율을 명세로 두면 사용자가 정밀도와 속도를 직접 고른다. 첫 컨테인먼트를 늘 상세하게 두면 시나리오와 에이전트가 행동할 서버가 없는 홀이 생기지 않는다.
- 서버 개체는 만들지 않지만 전력과 열은 같은 모델로 합쳐지므로, 평상시 알람 없음과 장애 전파(정전·냉각 상실)가 상세한 세계와 같은 방식으로 일어난다.

## 버린 대안
- **컨테인먼트 단위로 묶기**: 개체가 훨씬 더 줄지만(랙 1개 대신 컨테인먼트 1개) 랙별 온도·전원 지도가 사라진다. 3D에서 뜨거운 랙 하나를 짚는 그림이 불가능해진다.
- **실행 중 필요한 랙만 펼치기**: 개체를 실행 중에 만들고 지우면 이벤트 기록과 재생 규칙(상태는 청사진·시드·이벤트의 함수)이 깨진다. 세션을 열 때 정하는 `detail`이 더 단순하고 재현된다.
- **엔진을 숫자 배열로 다시 짜기**: 개체당 비용을 몇 배 줄일 수 있지만 물리 전체를 다시 쓰는 일이라 지금 필요한 규모(랙 2만 개)에는 과하다. 필요해지면 따로 결정한다.
- **서버를 무작위로 일부만 만들기**: 같은 홀 안에서 어떤 랙은 서버가 있고 어떤 랙은 없어 보인다. 묶음 랙은 서버가 있다는 사실은 그대로 두고 표현만 요약한다.

## 결과
- 요구사항 REQ-049를 더한다.
- 웹은 묶음 랙을 `bulkSlots`로 서버 칸을 그려서(개체 없이) 보여 준다(3D 단계).
- 한 걸음의 비용은 여전히 개체 수에 비례한다. 큰 캠퍼스는 `detail`을 낮추고, 용량은 `docs/design-docs/capacity.md`에 잰 값을 적는다.
