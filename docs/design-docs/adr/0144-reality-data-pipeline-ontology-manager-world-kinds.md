# ADR-0144 현실 데이터는 네 단으로 들어오고, 세계는 현실과 실험 두 종류이며, 모델은 핵심을 잠그고 넓힌다

## 맥락
제품 책임자(연수 님)의 걱정과 요구(2026-11-11): FalkorDB 연동을 없애고 개체별로 여러 소스(HTTP API, 엑셀 등)를 잇되 소스의 속성을 개체의 속성으로 정할 수 있어야 한다. 모델은 표준과 이어져야 한다. 프로세스의 개체는 자유 글이 아니라 정해진 개체와 관계에서 고른다. 모델을 관리하는 자리가 필요하다. 실험 세계와 운영(현실) 세계는 나뉘어야 하고 현실 쪽 데이터는 따로 관리되며 파이프라인과 저장소의 고가용성이 필요해진다. 데이터 소스 연동과 모델 동기화는 나눠 설계한다. 다른 제품은 소스 200여 종의 전용 커넥터로 관리하기 쉬움을 준다. 사내의 다른 온톨로지·로더 프로젝트는 설계에 넣지 않는다. 설계 결정은 설계 담당이 내린다(ADR-0138).

확인한 사실: 현실 가져오기 코드(`packages/core/src/sources/realimport`, 약 1,900줄: 읽기 전용 포트, 대응, 빈 곳 채우기, 보고서)와 서버의 FalkorDB 어댑터가 남아 있고 서버에 이어져 있다. 요구사항 REQ-010은 "없앤다"고 적혀 있어 문서와 코드가 어긋나 있다. 세계 모델은 개체 종류 62, 관계 종류 15와 이을 수 있는 규칙을 데이터로 가진다.

## 결정
1. **세계는 두 종류이고 만들 때 정해진다.** 실험 세계(물리·시나리오가 상태를 만든다, 결정적, 많다)와 현실 세계(현실 소스의 동기화가 상태를 만든다, 환경마다 하나). 서로 바뀌지 않는다. 현실 세계의 한 시각을 떠내 실험 세계를 만드는 한 방향만 있다. 테라리움은 현실에 쓰지 않는다. 이미 있는 "운영 모드"(REQ-090)와 섞이지 않게 새 종류의 이름은 "현실 세계"다.
2. **평면도 둘이다.** 현실 평면(연결·받은 그대로·대응·현실 세계와 이력)과 실험 평면은 저장소·일꾼·자격 증명이 따로다. 실험받는 에이전트는 현실 평면에 닿을 길이 없다. 현실 평면은 설정으로 켜고 기본은 꺼짐이다.
3. **데이터는 네 단으로 들어온다: 연결 → 수집 → 대응 → 적용.** 수집은 모델을 모르고 받은 그대로를 고치지 않고 남긴다. 대응은 소스 접속을 모르고 선언(키·속성·관계·합치기·출처)으로 변경 묶음을 낸다. 소스의 스키마가 흔들리면 대응에서 멈추고 세계는 그대로다.
4. **커넥터는 많이 만들지 않는다.** 범용 넷(파일, HTTP, SQL, 밀어 넣기) 위에 프리셋(요청 방법 + 대응, 데이터)을 쌓는다. 테라리움이 이미 말을 아는 것(Redfish, vCenter, vROps, NetBox, 쿠버네티스 API, SNMP)부터. 공개 커넥터 규약을 따르는 바깥 커넥터를 돌리는 길은 필요가 확인되면 연다. 관리하기 쉬움은 연결 상태·건수·흔들림·만료·쓰임을 보여 주는 것으로 낸다.
5. **모델은 핵심을 잠그고 셋으로 넓힌다.** 내장 종류의 뜻·규칙·액션은 읽기 전용이다(동작이 붙어 있다). 넓히는 길: 내장 종류에 속성 더하기, 기록만 되는 새 종류·관계, 프로세스 어휘. 넓힌 모델은 실험의 지문과 점수에 닿지 않는다. 모델에는 판과 이력이 있고 JSON 스키마 + JSON-LD 맥락으로 내보내며 종류마다 표준의 짝을 적는다(통째로 따르는 표준은 없다).
6. **프로세스의 "누가"와 "무엇을"은 어휘에서 고른다.** 없으면 어휘에 더한다. 사람 개인은 넣지 않는다.
7. **고가용성은 기대는 만큼만.** 수준 0(한 번 가져오기, 지금 저장소) → 수준 1(잃지 않기: 현실 평면 전용 관계형 DB, 덧붙이기만 하는 이력, 받은 그대로의 보관, 백업·복구) → 수준 2(멈추지 않기: 복제·자동 승격·일꾼 둘 이상). 저장소를 직접 만들지 않는다. 파이프라인은 처음부터 다시 돌려도 결과가 같게 만든다.
8. **순서와 문.** A(스키마 내보내기·표준 짝·프로세스 어휘·읽기 전용 모델 화면) → B(파일·HTTP로 한 번 가져와 실험 세계 만들기, FalkorDB 제거) → C(현실 세계와 계속 동기화, 수준 1) → D(수준 2, 생태계 커넥터, 새 종류, 미리 돌려 보기). A·B는 지금 제품 목표 안이다. **C부터는 제품 목표를 넓히는 결정을 따로 한다**: 권한·SSO가 끝나고, B로 만든 세계에서 현실 사고를 재현한 증거가 있어야 한다.
9. **현실에서 만드는 세계는 순서가 거꾸로다.** 지어내는 세계는 서비스 → 아키텍처 → 크기 → 생성이고, 현실에서 만드는 세계는 있는 것(소스) → 구성(소스에 있으면 읽음, 모델에서는 속성과 관계의 역할) → 모양 알아보기(사다리를 거꾸로, 칩 + 근거 + 모름) → 빈 곳 채우기(서비스·의존·DR·전원 길·담당: 사람이 목록에서) → 확인이다. 두 길은 같은 모델과 같은 사다리 칩에서 만난다. 확인되지 않은 이중화는 있다고도 없다고도 치지 않고 "모름"으로 둔다. 세계는 "구조만 있는" 상태와 "실험할 수 있는" 상태를 가진다.
10. REQ-010을 이 결정에 맞게 고친다(폐기가 아니라 단계 B에서 새 길로 다시 연다).
11. **관계는 표 하나에서 나온다.** 관계 종류마다 잇는 규칙·뜻의 갈래·판과 방향·영향 전파·역할을 한 줄로 적고, 토폴로지 판·영향 범위·검증·모델 화면이 그 표를 읽는다. 판은 갈래와 역할을 선으로, 이중화를 타일의 숫자로 보이고, 그리지 못한 것은 숫자로 낸다. 3D는 물리만 그린다. 채점과 물리는 바뀌지 않는다. 단계 A에 넣는다(현실 데이터를 넣기 전에 판이 보여 줄 수 있어야 사람이 확인한다).
12. **현실에서 만드는 길은 입구를 나누고 뒤를 같이 쓴다.** 연결 → 수집 → 대응(개체 + 관계 규칙) → 알아보기·빈 곳 채우기 → 확인·적용을 되풀이한다. 모델·판·시나리오·채점은 같이 쓴다.
13. **현실 세계의 선은 사람이 긋지 않고 규칙이 잇는다.** 관계 모델이 잇는 틀(키 맞추기, 담김, 끝점 짝, 묶음, 관례)과 관계 종류마다의 개수·필수 속성을 내주고, 사용자는 틀을 골라 규칙을 정한다. 선마다 규칙과 근거 등급(사실·가정·모름)이 남는다. 어느 시스템에도 없는 지식(서비스 구성, 의존, DR 계획)과 바로잡기도 표(소스)로 들어온다. 한 쌍·이중화 같은 것은 선에서 계산한다. 손으로 잇는 편집은 지어내는 세계와 떠낸 실험 세계에만 둔다. 내장 관계 종류는 읽기 전용이고, 사용자가 만든 관계 종류는 기록만 된다.

## 버린 길
- 전용 커넥터 수백 종: 만들 수도 지킬 수도 없다. 커넥터는 소스가 바뀔 때마다 낡는다.
- 소스에서 세계로 바로 넣기(받은 그대로 없이): 대응을 고칠 때마다 소스를 다시 긁고, 소스가 죽으면 세계가 비고, 무엇이 언제 들어왔는지 따질 수 없다.
- 실험 세계를 현실 세계로 "전환": 결정적이어야 하는 저장소와 잃으면 안 되는 저장소의 성질이 반대다.
- 처음부터 수준 2: 읽기만 하는 거울이 멈춰도 현실은 그대로다. 기대는 사람이 생기기 전의 무중단은 값만 든다.
- 내장 종류의 뜻을 고칠 수 있는 모델 관리: 시뮬레이션과 채점이 깨진다.
- 직접 만든 고가용 저장소: 검증된 DB의 복제를 쓴다.

## 결과
설계는 [현실 데이터와 모델](../reality-data-and-ontology.md). 단계마다 따로 ADR과 시험을 둔다. 화면(모델, 연결, 대응)은 목업을 먼저 그린다.
