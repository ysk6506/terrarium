# ADR-0139 CCTV는 카메라 개체·보는 자리·배경 자리의 세 자리로 두고, 실험의 그림은 서버가 결정적으로 그린다

## 맥락
서버룸에는 CCTV가 많다. 제품 책임자(연수 님)의 요구: 당장 만들지는 않지만, 서버룸에 CCTV를 놓는 것과 CCTV를 센서로 써서 사실적인 배경을 만드는 것을 고려한 자리를 설계한다. 3D를 사실적으로 바꾸려면 에셋 제작비가 크지만(코드로 그린 도형뿐이고 모델 파일이 없다), 현실의 화면을 가져다 쓰면 그 비용이 거의 없다. 제품 목표(ADR-0138)의 3번, 채점이 늘 맞고 같다는 것이 이 설계에서도 이긴다.

## 결정
1. **세 자리.** 카메라 개체 `camera`(방 안의 장비, 위치·방향·화각, PoE로 스위치에 연결, 시야와 사각지대는 코드로 계산), 보는 자리 `sense.camera`(카메라 하나가 보는 그림과 읽어 낸 사실), 배경 자리 `scene.backdrop`(3D에서 방 하나의 겉모습). 셋은 독립이다. 자세한 계약은 [CCTV 자리](../camera-and-backdrop.md).
2. **카메라는 물리를 따른다.** 스위치나 전원이 죽으면 꺼진다. 고장 다섯(꺼짐·가림·방향 틀어짐·조명 꺼짐·시각 어긋남). 카메라는 시야 안의 것만 알려 준다.
3. **보는 자리의 세 깊이.** ① 서버가 세계 상태를 그린 그림 ② 올린 사진 위에 상태를 덧그림 ③ 커넥터로 읽은 진짜 스냅샷과 비전 판독. 실험에는 ①②만 쓴다.
4. **실험의 그림은 서버가 결정적으로 그린다.** 브라우저의 3D는 그래픽 카드마다 픽셀이 달라 쓰지 않는다. 같은 세계 상태는 같은 바이트이고, 준 그림은 실험 기록에 남는다. 진짜 스냅샷으로 실험하려면 녹화한 묶음을 시나리오에 붙인다.
5. **비전 판독은 세계를 바꾸지 않는다.** 계측값과 다르면 불일치 사건으로 남긴다.
6. **배경은 아는 구조 위에 입힌다.** 세계에 랙·벽·바닥의 위치가 있으므로 입체를 복원하지 않고 CCTV 사진을 표면에 비춘다(카메라는 점 네 개 이상의 짝으로 맞춘다, 사람은 여러 장의 가운데 값으로 지운다, 안 보이는 면은 기본 도형으로 남긴다). 스캔 파일(점 구름·메시)도 같은 자리에 끼운다. 상태 표시와 클릭은 배경 위의 논리 개체가 맡는다.
7. **에이전트 툴 둘.** `list_cameras`, `camera_snapshot`. 툴 결과에 그림 한 종류를 더하고, 그림을 못 받는 에이전트에게는 사실 목록을 글로 준다.
8. **지금 지킬 것 넷.** 미터 좌표와 안 바뀌는 ID(ADR-0088), 툴 결과를 JSON만으로 굳히지 않기, 3D에서 방의 껍질과 논리 개체를 나누기, 이름 `camera`·`sense.camera`·`scene.backdrop` 비워 두기.
9. **순서.** A 카메라·시야·서버 그림·툴(시뮬레이션만으로 닫힘) → B 사진 위 덧그림 → C 배경 → D 진짜 CCTV 커넥터와 판독. 요구가 확정되면 시작한다.

## 버린 길
- 3D 전체를 사실적 에셋으로 다시 만들기: 에셋 제작이 대부분의 비용이고 장비 종류가 늘 때마다 든다.
- 브라우저 3D의 화면을 에이전트에게 주기: 같은 상태가 같은 그림이 아니다.
- 고정 CCTV로 입체 복원: 각도가 모자라다. 구조는 세계가 이미 안다.
- 판독으로 세계 상태를 덮어쓰기: 틀린 판독이 세계를 조용히 망친다.
- 동영상 스트림: 스냅샷으로 충분하고 보관·보안 비용이 크다.

## 결과
쌍둥이 로드맵(ADR-0095)의 ③ 거울 단계에 "눈"이 생긴다. 단계 A는 현실 연결 없이도 그림을 보는 에이전트의 평가에 쓸 수 있다. 요구사항 ID는 만들 때 붙인다.
