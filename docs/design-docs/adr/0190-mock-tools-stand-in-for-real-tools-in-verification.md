# ADR-0190 검증에서는 실제 툴 자리에 이름과 입력이 같은 모의 툴이 선다 — 에이전트는 건마다 받은 주소에 붙고, 툴마다 검증 수준을 밝힌다

## 맥락
ADR-0189는 워크플로를 실험용 복사본에서 검증한 뒤에만 운영에 내보낸다고 정했고, 검증에서는 액션이 실험의 툴에 매핑된다고 적었다. 제품 책임자의 물음: 에이전트는 현실의 툴을 가진 채 연동되는데, 그 툴이 실험 세계에는 없다. 어떻게 실험하나.

빈틈은 둘이다. 첫째, 실제 툴은 현실을 보므로 실험 세계에 넣은 고장이 보이지 않는다. 둘째, 에이전트의 프롬프트와 스킬은 실제 툴의 이름과 입력에 맞춰져 있어서, 이름이 다른 실험의 툴을 주면 다른 에이전트를 검증하는 셈이 된다. 이대로면 검증과 운영이 따로 논다.

## 결정
1. **검증하는 건에서 에이전트는 테라리움이 그 건에 내준 MCP 주소에만 붙는다.** 지금 실험이 쓰는 방식이다. 그 주소에는 실제 툴이 없으므로 검증 중에 현실을 건드릴 길이 없다. 툴 주소를 건마다 바꿀 수 없는 에이전트는 검증할 수 없고 그림자까지만 간다.
2. **그 주소에는 모의 툴이 선다.** 게이트웨이에서 읽어 온 실제 툴과 서버 이름, 툴 이름, 입력 모양이 같다. 동작은 툴 매핑을 거꾸로 읽은 것이다: 툴과 인자에서 객체와 액션과 입력을 알아내 실험 세계에서 조회하거나 조치한다. 테라리움의 MCP 툴(`prepare_action` 등)은 검증에서도 운영 때와 같은 서버·툴·인자를 돌려준다.
3. **툴마다 검증 수준을 밝힌다.** 실물(실제 툴 서버를 시험용으로 띄워 실험 세계의 파사드에 붙임), 모의(테라리움이 세움), 없음(세울 수 없음). 없음인 툴에 기대는 단계는 검증할 수 없어서 승인 적용까지만 간다.
4. **모의 툴의 응답 모양**은 선언된 출력 모양, 툴을 가진 쪽이 올린 응답 예, 일반 모양의 차례로 정하고, 일반 모양일 때는 응답에 그렇다고 적는다.
5. **그림자 단계가 모의와 현실의 어긋남을 잰다.** 실제 조회 툴의 응답과 모의 툴이 냈을 응답을 견줘 어긋난 곳을 보이고, 어긋남이 큰 툴은 검증 수준을 낮추며 그 툴에 기댄 갈래의 "검증됨"을 거둔다.

## 이유
- 이름과 입력이 같아야 같은 에이전트를 검증한다. 에이전트를 실험용으로 고쳐 쓰게 하면 검증한 것과 내보낸 것이 다르다.
- 검증이 말해 주는 것은 에이전트의 판단과 호출이지 실제 툴의 동작이 아니다. 이 한계를 툴마다 밝혀야 "검증됨"이 과장되지 않는다(원칙: 모르는 것은 말하고 고칠 길을 준다).
- 주소를 건마다 내주는 방식은 이미 있다. 새 길을 만들지 않는다.

## 버린 길
- **검증에서 실제 조회 툴은 그대로 쓰게 하기**: 실험 세계의 고장이 보이지 않아 진단을 검증할 수 없다.
- **에이전트가 테라리움의 실험 툴 이름을 따로 배우게 하기**: 검증과 운영의 에이전트가 달라진다.
- **모든 툴에 실물 수준을 요구하기**: 툴마다 시험용 서버와 파사드가 있어야 해서 시작할 수 없다. 실물은 올릴 수 있는 수준으로 둔다.

## 남은 일
- 응답이 글인 툴의 모의 응답을 어디까지 닮게 할지.
- 실물 수준에 필요한 파사드의 목록(지금 있는 것과 없는 것).

## 결과
설계 문서 11절에 "검증에서는 실제 툴 자리에 모의 툴이 서요" 절, 용어집에 모의 툴과 검증 수준.
