# ADR-0027 실행 호스팅과 끝내는 규칙

## 맥락
실행 하나는 시뮬레이션(물리·시나리오·채점)이라는 CPU 일과, 에이전트를 기다리는 네트워크 일로 되어 있다. 서버 한 대(8 vCPU)에서
수십 개가 동시에 돈다(REQ-032). 그리고 "실행이 어떻게 끝났나"가 점수와 순위를 정하므로, 규칙이 공정하고 설명 가능해야 한다.

## 결정
**어디서 도나**
- 세션은 워커 스레드 풀(`WorkerHost`, 기본 vCPU − 1개)에서 돈다. 새 세션은 가장 한가한 워커로 가고, 끝날 때까지 그 워커에 있다.
  메인 스레드는 HTTP·MCP·스케줄러만 맡는다.
- 워커와는 평범한 데이터 메시지만 주고받는다. 워커가 죽으면 그 워커의 세션은 "세션을 돌리던 워커가 멈췄다"로 실패하고 새 워커가 뜬다.
- 같은 인터페이스의 `InProcessHost`가 있다(테스트, 아주 작은 설치). 두 호스트는 같은 입력에 **같은 결과**를 낸다(테스트로 확인).
- 워커는 tsx로 TypeScript 소스를 그대로 읽는다. 빌드 단계가 없어 서버와 테스트가 같은 코드를 돈다.
- 실시간 시간 정책은 호스트가 벽시계를 읽어 세션을 맞춘다. 세션은 시계를 읽지 않는다(REQ-001).

**어떻게 끝나나** (실행기 `executeRun`)
1. 세션이 끝남(진단 제출·툴 한도·제한 시간) → 하네스에 짧은 유예(기본 15초)를 주고 멈춘다. **채점한다.**
2. 하네스가 "끝"이라고 함 → 세션이 아직이면 "진단 없이 종료"로 끝낸다. **채점한다.**
3. 사람이 취소함 → 취소. **채점하지 않는다.**
4. 하네스 오류 — 에이전트가 **툴을 한 번도 부르기 전**이면 인프라 문제로 보고 실패(**채점 안 함**), 그 뒤면 에이전트의 오류(`agent_error`, **채점함**).
5. 실제 시간 한도(기본 30분)를 넘김 → 하네스를 멈추고 "제한 시간 초과"로 **채점한다.**
- 서버가 멈추거나 다시 시작되면 돌던 실행은 이유와 함께 실패로 남고, 대기하던 실행은 다시 줄을 선다.

## 이유
- 시뮬레이션 한 스텝은 큰 세계에서 수 ms다. 메인 스레드에서 돌면 수십 개 실행이 HTTP 응답을 늦춘다.
- 4번 규칙: 모델 게이트웨이가 꺼져서 시작도 못 한 실행을 0점으로 세면 에이전트에게 불공평하다. 반대로 일하다가 무너진 것은 에이전트의 몫이다.
  "툴을 한 번이라도 불렀나"는 누구나 확인할 수 있는 기준이다.
- 5번 규칙: 느린 에이전트도 언젠가는 끝나야 다른 실행이 자리를 얻는다. 그 시간은 점수에 반영된다(lockstep에선 세계 시간은 멈춰 있지만, 사람의 시간은 아니다).

## 버린 대안
- **실행마다 자식 프로세스**: 격리는 좋지만 메모리가 몇 배 든다(64 GB에서 수십 개).
- **모든 하네스 오류를 실패로**: 에이전트가 망가져도 점수가 안 깎여 순위가 왜곡된다.
- **모든 하네스 오류를 0점으로**: 인프라 장애가 순위를 흔든다.
