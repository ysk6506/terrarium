# ADR-0098 도메인 범위, 가상 담당자, 작업 티켓

## 맥락
IT 운영은 도메인(서비스/OS·가상화·서버·네트워크·스토리지·데이터센터 인프라)별로 나뉘고, 사용자는 특정 도메인만 실험하고 싶어 한다. 서비스 알람의 근본 원인이 메모리 교체면 서버 도메인으로, 서버 도메인은 벤더로 넘기고 — 그건 빨라야 4시간, 길면 며칠이다. 현실의 운영자는 동시에 여러 일을 하며 어떤 일은 지연되고 어떤 일은 남이 처리하길 기다린다. 그래서 Jira 같은 것을 쓴다(제품 책임자). 이것이 없으면 테라리움은 운영이 아니라 퍼즐이 된다.

## 결정
1. **도메인은 실험의 범위 단위.** 실험 만들기에 "내 도메인"(복수 가능). 그 도메인의 툴이 기본으로 켜지고(현실 수준 꼬리표는 그 위에, ADR-0087), 다른 도메인으로 넘기는 툴이 같이 생긴다. 고장 범위(ADR-0087)는 도메인과 맞물린다.
2. **넘기는 상대 둘.** `ask_human`(진짜 사람, ADR-0087)과 `escalate(to, request)`(**가상 담당자**: 다른 도메인 팀 또는 벤더). 가상 담당자는 세계가 흉내 낸다: 응답 시간 분포(도메인 팀 30분~2시간, 하드웨어 벤더 4시간~3일; 시드 재현), 되묻기(필요 정보를 요구), 거절 확률, 완료 시 세계 반영(부품 교체·설정 변경). 실험 설정 "다른 도메인 처리: 가상 담당자 / 진짜 사람 / 없음(그 도메인 고장은 내지 않음)". 운영 모드(ADR-0094)에서 리드타임이 세계 시간으로 그대로 흐른다.
3. **작업 티켓 툴.** `create_ticket`·`update_ticket`·`list_tickets`. 상태: 내가 할 것 / 기다리는 중(누구를, 언제까지) / 끝남. 넘긴 요청은 자동으로 "기다리는 중" 티켓이 되고, 상대의 진행·되묻기·완료는 사건으로 들어온다(`events_since`에 섞임 — 보는 것은 에이전트 몫).
4. **측정.** 임시 조치 먼저(며칠 걸리는 일 앞에서 서비스를 살렸나 — 복구 우선 채점과 연결), 잊지 않았나(상대가 끝냈을 때 마무리를 했나·얼마나 늦게), 동시 작업(기다리는 동안 다른 알람을 처리했나), 되묻기 대응 시간, 넘긴 횟수와 근거(내 도메인에서 할 수 있는 것을 넘기면 감점).
5. **화면.** 실행 화면에 티켓 보드(내가 할 것 / 기다리는 중 / 끝남), 타임라인에 상대의 사건 표식("벤더: 교체 완료 14:20"), 리플레이에서 "기다리는 동안 뭘 했나".
6. **시나리오 템플릿**에 "내 도메인 밖이 원인"인 것을 둔다(메모리 불량 → 서비스 알람 → 서버팀 → 벤더 교체 → VM 되돌리기).

## 결과
REQ-093. 3차(툴 범위·에스컬레이션·운영 모드)에 함께 구현한다.
