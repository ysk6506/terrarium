# ADR-0166 파이프라인은 버전으로 남기고, 브랜치에서 고쳐 미리보기 세계로 확인한 뒤 운영에 병합한다

## 맥락
제품 책임자의 요구: 데이터 파이프라인으로 운영 데이터가 쌓인다. 파이프라인은 계속 수정되므로 버전과 브랜치 개념이 설계돼야 한다.

지금까지 정한 것은 조각이었다: 세계에는 버전이 있고 실험은 버전을 고정한다(ADR-0151), 매핑은 데이터이고 버전이 있다(ADR-0144). 파이프라인 전체를 한 단위로 버전 매기는 것, 운영에 영향 없이 고쳐 보는 것, 고친 결과를 견줘 보고 넣는 것, 되돌리는 것은 정하지 않았다. 그대로 만들면 링크 조건 하나를 고치는 일이 곧바로 운영 세계를 바꾼다.

## 결정
1. **버전을 매기는 것은 셋이다.**

| 무엇 | 한 버전이 담는 것 | 언제 새 버전이 생기나 |
|---|---|---|
| 파이프라인 | 소스 설정(비밀 값 제외), 정제, 매핑, 중복 병합 규칙, 링크 정의를 통째로 | 정의를 저장할 때. 누가, 언제, 왜를 함께 남긴다 |
| 스냅샷 | 한 번의 수집으로 받은 원본 데이터셋 | 수집할 때. 고치지 않는다 |
| 세계 | 객체와 링크 | 스냅샷이나 파이프라인이 바뀌어 결과가 달라질 때 |

2. **세계의 버전은 "어느 파이프라인 버전으로 어느 스냅샷들을 돌렸나"를 적는다.** 같은 파이프라인 버전과 같은 스냅샷이면 같은 세계가 나온다. 어느 객체나 링크든 그것을 만든 정의와 원본 행까지 거슬러 간다.
3. **파이프라인은 층별이 아니라 통째로 버전을 매긴다.** 층들이 서로를 가리키기 때문이다(매핑은 정제한 데이터셋의 컬럼을, 링크 정의는 객체 타입의 속성을 가리킨다). 화면은 층마다 무엇이 바뀌었는지 나눠 보여 준다.
4. **운영 브랜치는 하나다.** 주기에 따라 수집하고 운영 세계를 만드는 것은 운영 브랜치뿐이다. 운영 브랜치의 정의는 직접 고치지 않고 병합으로만 바뀐다.
5. **브랜치는 운영에 영향 없이 고쳐 보는 작업 공간이다.** 운영 브랜치의 한 버전에서 갈라진다. 브랜치는 소스에서 다시 가져오지 않고 운영이 받아 둔 스냅샷을 쓴다. 그래서 소스에 부하를 더하지 않고 자격 증명을 따로 갖지 않는다. 새 소스를 더하는 브랜치만 그 소스를 수동으로 한 번 수집한다.
6. **브랜치의 결과는 미리보기 세계다.** 운영 세계와 따로 저장되고 관리자에게만 보인다. 실험과 영향 범위 조회의 대상이 아니다.
7. **병합 전에 차이를 둘로 보여 준다.** 정의의 차이(어느 층의 무엇이 바뀌었나)와 세계의 차이(생기는 객체·사라지는 객체·바뀌는 속성, 생기는 링크·사라지는 링크, 문제 목록의 변화, 미사용 행의 변화).
8. **병합은 수집 결과를 적용할 때와 같은 안전장치를 거친다**(ADR-0151: 객체가 10% 넘게 사라지면 멈춤, 사람의 확인). 브랜치가 갈라진 뒤 운영 브랜치가 바뀌었으면 먼저 최신 운영을 브랜치에 받아 미리보기를 다시 만든다. 같은 항목(같은 데이터셋의 정제, 같은 객체 타입의 매핑, 같은 링크 타입의 정의)을 양쪽이 고쳤으면 사람이 어느 쪽을 쓸지 고른다. 글자 단위로 섞지 않는다.
9. **되돌리기는 이전 파이프라인 버전을 새 버전으로 다시 올리는 것이다.** 이력을 지우지 않는다. 남아 있는 스냅샷으로 세계를 다시 만든다.
10. **세계의 이력은 덧붙이기만 한다.** 객체와 링크의 행마다 "언제부터 언제까지 이 값이었나"를 남겨, 지난 시점의 세계를 조회한다(ADR-0154의 행 저장을 따른다). 실험과 실험용 복사본은 세계의 버전을 고정한다(ADR-0151 그대로).
11. **보관.** 스냅샷은 소스마다 최근 것을 정해 둔 수만큼 두고, 남아 있는 세계 버전이나 실험이 가리키는 것은 지우지 않는다. 지워진 스냅샷이 필요한 세계 버전은 "다시 만들 수 없음"으로 표시한다. 브랜치는 정해 둔 기간 동안 쓰지 않으면 닫는다.
12. **순서.** 클로즈 베타는 버전, 되돌리기, 그리고 브랜치 하나("초안")까지다: 고치기 → 미리보기 → 비교 → 적용. 이름 붙인 브랜치 여럿과 충돌 고르기는 오픈 베타다. 초안도 저장하는 모양은 브랜치와 같게 만들어, 여럿으로 넓힐 때 다시 만들지 않는다.
13. 버전·브랜치·병합·되돌리기는 관리자만 한다(ADR-0152). 누가 무엇을 병합하고 되돌렸는지는 감사 기록에 남는다.

## 이유
- 운영 데이터가 쌓이기 시작하면 정의를 고치는 일이 가장 위험한 변경이 된다. 링크 조건 하나가 링크 수천 개를 지운다. 고친 결과를 넣기 전에 봐야 한다.
- 스냅샷을 고치지 않고 두기 때문에 브랜치가 소스 없이 돌고, 되돌리기가 다시 만들기가 된다.
- 세계 버전에 입력 둘을 적어야 "이 링크가 왜 사라졌나"에 답한다: 소스가 바뀌었나, 정의가 바뀌었나.

## 버린 길
- **층마다 따로 버전**: 서로 안 맞는 조합이 생긴다(없어진 컬럼을 가리키는 매핑).
- **브랜치마다 소스에서 따로 수집**: 소스의 부하와 자격 증명이 브랜치 수만큼 늘고, 운영과 받은 시각이 달라 차이의 원인을 가릴 수 없다.
- **데이터도 깃처럼 브랜치·병합**: 병합하는 것은 정의다. 데이터는 정의와 스냅샷에서 다시 만든다.
- **클로즈 베타에 이름 붙인 브랜치 여럿**: 충돌 고르기까지 만들어야 해서 첫 범위를 넘는다. 초안 하나로 같은 안전을 먼저 얻는다.
