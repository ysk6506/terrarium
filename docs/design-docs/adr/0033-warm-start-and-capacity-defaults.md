# ADR-0033 워밍업 캐시와 용량 기본값 (REQ-032, REQ-042)

## 맥락
수백~수천 건을 동시에 돌리려면 실행 하나의 비용을 알아야 한다. 부하 측정(`tests/spec/capacity.ts`, [용량](../capacity.md))은 두 가지를 보였다.

1. 작은 세계(랙 8개)에서는 스레드 하나가 초당 12개쯤을 마치고 거기서 포화한다. 동시 실행을 64에서 1024로 늘려도 처리량은 같고 지연만 늘며, 세션당 메모리는 약 2 MB다.
2. 세계가 커지면 **세션을 여는 시간**이 처리량을 정한다. 열 때 정상 운영 600초(60걸음)를 미리 굴리는데, 개체 4천 개에서 3.5초, 6.7천 개에서 9초다.
   같은 세계로 실험을 수천 번 돌려도 매번 같은 600초를 다시 굴리고 있었다.

## 결정
1. **워밍업 결과를 스레드마다 기억한다.** 세션이 시작할 때, 세계 다이제스트·워밍업 길이·샘플 간격·보관 시간이 같은 상태가 캐시에 있으면
   세계 상태와 지표 기록(레코더)을 거기서 복사해 시작한다. 없으면 직접 굴린 뒤 캐시에 넣는다.
2. **결과가 달라지지 않는다는 것을 시험으로 보인다.** 워밍업은 시나리오가 시작되기 전이라 시나리오, 시드, 도구, 에이전트에 상관없다.
   캐시로 시작한 실행과 직접 굴린 실행의 결과(과제, 호출 결과, 점수, 시계열, 타임라인)가 서로 같다는 시험을 둔다.
   캐시에 든 상태는 세션이 바꾸지 못한다(세계 상태는 복사해서 넘기고 이벤트는 쓰고 나면 바뀌지 않는다).
3. **키에 넣을 수 없는 것이 있으면 캐시하지 않는다.** 사용자 정의 카탈로그를 쓰는 세션, 그리고 지표 기록이 워밍업 동안 한 바퀴 돌아 버리는 설정은 건너뛴다.
4. **크기는 작게, 최근 것 우선.** 스레드마다 4개까지, 가장 오래 안 쓴 것부터 버린다. 스레드가 많아도 메모리가 비례해서 늘지만(스레드 7개 × 4개),
   세계 하나의 상태는 세션 하나가 쓰는 만큼이라 세션 수십 개에 비하면 작다.
5. **핵심 경로를 가볍게 한다**(동작은 같다). 하위 개체 목록 캐시, 정렬된 경보 목록 캐시, 고장 조회 필터 순서, 경보 동기화의 중복 읽기 제거.
   큰 세계의 열기 시간이 약 절반이 되었고, 기존 시험이 모두 통과한다.
6. **자리 기본값(`sessionsPerThread` 32)은 그대로 둔다.** 8 vCPU / 64 GB에서 가장 큰 측정 세계(6.7천 개체, 세션당 약 100 MB)를 가득 채워도 약 22 GB다.
   더 큰 세계는 설정으로 낮춘다. 메모리를 보는 입장 제어는 만들지 않았다(개수로 세는 쪽이 설명하기 쉽고, 필요해질 때 따로 정한다).

## 이유
- 같은 세계로 반복해서 도는 실험(벤치마크, "조건만 바꿔 다시 돌리기")이 이 제품의 주된 사용 방식이라 캐시가 잘 맞는다.
- 캐시를 세션 안이 아니라 호스트(스레드)에 둔다. 코어는 순수하게 남고, 캐시를 안 넘기면 예전과 똑같이 동작한다.
- 관측값: 개체 4천 개에서 열기 3.5초 → 약 1.6초, 6.7천 개에서 9.2초 → 약 3.2초. 랙 50 세계의 처리량은 초당 1.0개 → 1.6개.
  남은 시간은 시나리오가 과제를 넘기기 전까지 굴리는 구간이다. 시나리오와 시드마다 달라서 캐시하지 않는다.

## 버린 대안
- **스레드 사이에 캐시를 나눠 갖기**: 스레드는 메모리를 공유하지 않아서 복사가 필요하다. 이득보다 복잡하다. 스레드마다 한 번 굴리는 비용은 작다.
- **시나리오 시작 직전까지 캐시하기**: 시나리오와 시드마다 다른 상태라 적중률이 낮다.
- **워밍업을 짧게 줄이기**: 결과(경보, 온도)가 달라진다. 동작을 바꾸는 것은 용량 문제의 답이 아니다.
- **물리 걸음을 키우기**(10초 → 30초): 안정성이 깨진다(30초 걸음으로 600초를 굴리면 정상인 세계에서 경보가 수천 개 생기는 것을 확인했다).

## 결과
- 새 파일 `session/warm.ts`, `World.checkpoint()/adopt()`, `MetricRecorder.capture()/adopt()`.
- 새 문서 [용량](../capacity.md), 측정 도구 `tests/spec/capacity.ts`.
- 알려진 한계: 측정은 2 vCPU 컨테이너 한 대에서만 했다. 컨트롤(SQLite)의 한계와 여러 노드의 합산 처리량은 실측하지 못했다.
