# ADR-0191 검증하는 건의 툴 호출은 게이트웨이가 테라리움으로 보낸다 — 에이전트는 두 세계에서 같은 게이트웨이를 같은 이름으로 부른다

## 맥락
ADR-0190은 검증에서 에이전트가 테라리움이 내준 MCP 주소에 붙고, 거기에 실제 툴과 이름·입력이 같은 모의 툴이 선다고 정했다. 제품 책임자의 지적 셋: 툴은 제각각이라 다 흉내 낼 수 없다. 툴은 계속 바뀐다. 흉내 낸 서버를 사용자가 에이전트와 하네스에 따로 등록하고 권한을 줘야 한다면 제품이 아니다. 그리고 못 박은 전제 하나: 툴은 에이전트가 MCP 게이트웨이를 통해서만 부른다.

설계 담당은 한때 테라리움이 실제 툴을 대신 부르는 구조를 내놓았으나 이 전제에 어긋나 버렸다.

## 결정
1. **에이전트는 검증에서도 게이트웨이만 부른다.** 같은 게이트웨이, 같은 서버 이름, 같은 툴 이름이다. 에이전트와 하네스에 더 등록할 것이 없고 권한도 그대로다.
2. **보낼 곳은 게이트웨이가 바꾼다.** 테라리움은 에이전트를 부를 때 건 표를 주고, 에이전트는 게이트웨이를 부를 때 그것을 붙인다(운영하는 건에서도 같다). 게이트웨이는 검증하는 건의 표가 붙은 호출을 실제 툴 대신 테라리움으로 보낸다. 이것이 게이트웨이에 기대는 넷째 것이다.
3. **테라리움은 툴을 하나씩 흉내 내지 않는다.** 모의 툴은 게이트웨이에서 읽어 온 툴 목록과 툴 매핑에서 나온다. 매핑 한 줄을 운영에서는 안내로, 검증에서는 거꾸로 읽어 풀이로 쓴다. 매핑이 없는 툴은 검증하는 세계에 없다고 답하고 적으며, 그 툴에 기대는 단계는 검증 안 됨이다. 툴이 바뀌면 동기화가 알아채 그 매핑만 점검 필요가 된다.
4. **검증하는 건의 호출이 현실에 닿지 않음을 시작할 때마다 확인한다.** 시험 호출 하나가 게이트웨이를 거쳐 테라리움에 도착해야 검증을 시작한다.
5. **게이트웨이가 보내 주지 못하는 곳의 물러남.** ADR-0190의 방식(에이전트가 테라리움이 내준 주소에 붙음)을 쓸 수 있는 에이전트는 그것으로 검증하고, 아니면 그림자까지만 간다.
6. **조회는 주로 테라리움의 토폴로지 조회 툴로 한다.** 응답 칸까지 매핑한 조회 툴만 검증하는 세계의 값으로 답할 수 있다는 한계를 화면에 밝힌다.

## 이유
- 등록과 권한을 한 번 더 요구하면 쓰는 사람마다 드는 일이 되고, 관리자가 게이트웨이에 규칙을 한 번 넣는 것은 조직에 한 번 드는 일이다.
- 흉내를 툴마다 만들면 툴 수와 바뀌는 속도를 따라갈 수 없다. 어차피 있어야 하는 매핑을 두 방향으로 쓰면 더 만드는 것이 없다.
- 검증의 값은 "검증한 에이전트가 운영하는 에이전트와 같다"에 있다. 주소도 이름도 같아야 그 말을 할 수 있다.

## 버린 길
- **테라리움(실행기)이 실제 툴을 대신 부르기**: 등록·권한·툴 변경 문제는 풀리지만 "툴은 에이전트가 게이트웨이를 통해서만 부른다"는 전제를 깬다.
- **툴 서버마다 시험용을 띄워 실험 세계의 파사드에 붙이기를 기본으로 하기**: 가장 닮지만 툴을 가진 쪽 모두에게 일을 요구한다. 올릴 수 있는 검증 수준(실물)으로 남긴다.

## 남은 일
- 건 표를 게이트웨이까지 나르는 방법(헤더, 건마다의 경로)은 게이트웨이가 받는 방식에 맞춘다.
- 응답 칸 매핑의 모양.

## 결과
설계 문서 2절의 "게이트웨이에 기대는 것"이 넷이 되고, 11절의 모의 툴 절이 이 결정대로 바뀐다.
