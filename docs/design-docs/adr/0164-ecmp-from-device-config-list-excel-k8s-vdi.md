# ADR-0164 ECMP는 장비 설정에서 읽고, 위치 엑셀은 목록으로 받고, VMware의 쿠버네티스와 VDI 둘을 대응 표에 넣는다

## 맥락
ADR-0161은 세 가지를 제품 책임자에게 묻기로 하고 열어 뒀다. 제품 책임자의 요구(2026-11-12):

1. 위치 엑셀은 한 줄에 장비 하나인 목록 형식도 받는다.
2. ECMP는 경로표에서 받는 것이 아니라 장비 설정 값에서 읽는다.
3. 클라우드 대응 표는 VMware와 OpenStack으로 하고, 쿠버네티스는 VMware의 쿠버네티스도 받으며, VDI 서비스(Citrix, VMware Horizon)를 포함한다.

## 결정
1. **실장도 격자를 읽는 기능은 만들지 않는다.** 위치 엑셀은 목록으로 받는다. 격자 모양의 시트가 오면 화면이 알아보고 목록 양식을 안내하는 것(ADR-0161 2번)까지만 한다.
2. **ECMP는 장비 설정에서 읽는다.** ADR-0161 11번의 ECMP 문장("경로표가 오면 사실, 역할에서 끌어내면 가정")을 이것으로 바꾼다.
   - 묶음의 구성원은 그 장비의 BGP 세션 가운데 설정에서 같은 무리(이웃 무리, 주소 계열)에 든 것들이다.
   - 설정의 "여러 경로를 몇 개까지 같이 쓰는가"가 2 이상이면 ECMP 묶음이다: 하나를 잃으면 약해지고, 다 잃으면 끊긴다.
   - 그 값이 1이거나 없으면 주·대기 묶음이다: 하나를 잃으면 길이 바뀌고, 다 잃으면 끊긴다. 닿는지는 두 경우가 같고, 약해지는지가 다르다.
   - 등급은 사실이다(설정이 말한다). 설정에 이웃 무리가 없어 장비의 역할(잎·가지)로 구성원을 묶었을 때만 가정이다.
   - 경로표는 받지 않는다. 경로표는 구성이 아니라 상태이고, 상태는 미뤄 뒀다.
3. **가상화 플랫폼 대응 표의 클라우드 열은 VMware와 OpenStack 둘로 닫는다.** 다른 플랫폼이 정해지면 그때 열을 더한다(ADR-0157 4번 그대로).
4. **VMware의 쿠버네티스는 쿠버네티스 API의 모양으로 받는다.** 종류는 이미 있는 `k8s_cluster`·`k8s_node`·`k8s_workload`다. 더하는 것은 선 하나다: 노드가 VM이면 노드는 그 VM 위에서 돈다(키 맞추기). 이 선이 있어야 설비에서 시작한 영향 범위가 호스트 → VM → 노드 → 워크로드로 이어진다. 워크로드 클러스터를 다스리는 관리 클러스터는 "다스린다" 관계로 적는다.
5. **VDI는 새 종류 없이 서비스 층으로 받는다.** Citrix와 VMware Horizon을 같은 중립 뜻에 맞춘다.
   - VDI 서비스와 데스크톱 풀은 `service`다. 풀의 구성원인 데스크톱은 `vm`이다.
   - 접속을 맺어 주는 브로커와 바깥 문(게이트웨이)은 `app_instance`이고, 풀은 이들이 필요하다. 브로커가 여럿이면 하나만 살아도 되는 묶음이다.
6. **풀은 "몇 개가 살아야 하나"가 없는 묶음이다.** 데스크톱 하나가 사용자 한 명이라서, 영향은 문턱이 아니라 수로 말한다("데스크톱 240대 중 60대"). 관계 표의 묶음 뜻에 "수로 말한다"를 더한다. ADR-0156 3번을 넓힌다.

## 이유
- 경로표를 기다리면 ECMP가 늘 가정이 된다. 설정은 구성 소스(장비 설정을 가진 것)가 이미 주므로 사실로 적을 수 있다.
- 노드와 VM을 잇지 않으면 쿠버네티스가 설비와 끊긴 섬이 된다. REQ-117의 "설비에서 앱·서비스까지"가 거기서 멈춘다.
- VDI를 종류로 만들면 제품 이름이 모델에 들어온다. 풀·데스크톱·브로커는 서비스·VM·앱 인스턴스의 뜻으로 충분하다.
- 풀에 문턱을 두면("절반이 죽으면 영향") 데스크톱 60대를 잃은 일이 "영향 없음"으로 읽힌다.

## 확인한 것과 못 한 것
- VMware의 쿠버네티스, Citrix, Horizon의 개체 이름과 API 모양은 설계 담당이 아는 대로 적었다. 프리셋을 만들 때 제품 문서와 대조한다.
- "여러 경로를 몇 개까지 같이 쓰는가"의 설정 이름은 제조사마다 다르다. 견본에 넣을 때 소스(장비 설정을 주는 것)의 모양에서 확인한다.
