# ADR-0157 모델은 층마다 표준에서 뼈대를 빌리고, 종류는 세 층이며, 가상화 플랫폼은 대응 표로 받는다

## 맥락
제품 책임자의 요구(2026-11-11): 가상 네트워크와 가상 스토리지 자원까지 다루는 플랫폼 중립 모델을 둔다. 첫 대응 대상은 VMware와 OpenStack이고, 다른 플랫폼도 나중에 더할 수 있어야 한다. 개체와 관계의 표준 모델을 참고한다.

대조한 것:
- 핵심 종류 62개에 `vcenter`처럼 한 제품의 이름이 들어 있다. 가상 스위치·가상 라우터·서브넷·포트에 해당하는 종류는 없다.
- ADR-0144 5절의 표준 짝 표는 가상화를 "vSphere 개체 모델, 쿠버네티스 API"로 적었다. 한 제품의 모델이 뼈대였다.
- ADR-0150은 "모델 넓히기(사용자가 만드는 종류와 관계)"를 제안에 뒀고, ADR-0152는 사용자가 만든 관계 종류는 영향이 넘어가지 않는다고 했다.
- ADR-0156은 포트·포트 묶음·BGP 세션을 장비에 딸린 것으로 두고 영향 범위에 넣었다.

## 결정
1. **층마다 공개된 표준에서 뼈대를 빌린다.** 건물·공조는 Brick, 하드웨어는 Redfish, 랙과 케이블은 NetBox의 모델, 네트워크는 IETF RFC 8345(종단점이 포트다)와 RFC 8944(포트 묶음)·RFC 8346, 프로토콜 구성은 OpenConfig, 가상화는 DMTF CIM의 가상 시스템 모델, 스토리지는 SNIA Swordfish, 컨테이너는 쿠버네티스 API, 서비스는 TOSCA(ServiceNow CSDM은 참고). 통째로 따르는 표준은 없다. ADR-0144 5절의 가상화 줄을 이것이 대신한다.
2. **종류는 세 층이다.** 시뮬레이션 핵심 종류(62), 현실 표준 종류(테라리움이 내놓고 뜻을 정한다. 시뮬레이션은 모르고 영향 범위에는 들어간다), 사용자가 만드는 종류(제안 그대로, 영향이 넘어가지 않는다). ADR-0150 표의 "모델 넓히기"에서 테라리움이 내놓는 현실 표준 종류는 결정으로 옮긴다.
3. **종류의 뜻은 플랫폼 중립이다.** 한 제품의 이름이 든 핵심 종류는 이름을 두고 뜻을 중립으로 정한다(`vcenter` = 가상화 관리자).
4. **가상화 플랫폼은 대응 표로 받는다.** 표는 데이터이고 프리셋이 든다. 플랫폼이 늘면 열이 는다. 열을 더할 때 맞지 않으면 종류를 중립 뜻 쪽으로 고친다.
5. **관계의 갈래는 TOSCA의 관계 종류와 짝짓는다**(위에서 돈다 = HostedOn, 필요하다 = DependsOn, 이어진다 = ConnectsTo, 붙는다 = AttachesTo). 짝이 없는 "묶인다"와 "공급받는다"는 RFC 8944·CIM과 Brick을 따른다.
6. 짝은 방향이다. 만들 때 각 표준 문서와 하나씩 대조해 확정하고, 대조한 판을 적는다.

## 확인한 것과 못 한 것
- RFC 8944가 종단점에 포트 묶음(`lag`)과 구성 종단점(`member-link-tp`)을 둔다는 것, CIM의 가상 시스템 모델이 호스트와 가상 시스템을 HostedDependency로 잇고 자원 풀을 둔다는 것은 문서에서 확인했다.
- TOSCA의 AttachesTo, RFC 8345의 층 겹치기, OpenConfig·Swordfish·CSDM의 자세한 모양은 이번에 문서로 확인하지 못했다. 가상화 플랫폼 대응 표의 칸도 설계 담당이 아는 대로 적었다.

## 버린 길
- **한 제품의 개체 모델을 뼈대로**: 플랫폼이 바뀌거나 늘면 모델을 다시 짠다.
- **표준 하나를 통째로**: CIM은 넓지만 무겁고 오래됐고, TOSCA는 배포를 적는 말이라 설비가 없다. 층마다 맞는 것이 다르다.
- **가상 네트워크·스토리지를 사용자가 만드는 종류로**: 영향이 넘어가지 않아 영향 범위가 가상 층에서 끊긴다.
