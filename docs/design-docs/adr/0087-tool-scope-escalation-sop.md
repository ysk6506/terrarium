# ADR-0087 툴 범위는 실험 설계자가 정하고, 현실 수준 꼬리표를 달고, 에스컬레이션과 절차서는 실험 변수다

## 맥락
테라리움은 "우리가 주는 툴 안에서 에이전트가 데이터센터 운영을 얼마나 잘·오래·믿을 수 있게 하나"를 잰다(제품 책임자의 요구). 툴 수를 우리가 제한하면 실험에 우리 취향이 섞인다. 영향 범위 분석 같은 툴은 아직 흔하지 않아서, 그런 툴을 기본으로 주면 에이전트 실력이 아니라 우리 툴을 재는 것이 된다. 범위 밖 문제로 사람이 자꾸 개입하면 실험이 진행되지 않는다.

## 결정
1. **툴 범위는 실험 설계자가 정한다.** 툴 고르기 화면은 영역 카드(서버·전원·냉방·네트워크·가상화·관측·조치) → 세부 툴 접기/펼치기, 검색 한 칸. 맨 위에 "이 시나리오에 필요한 툴"을 계산해 보여 주고 "필요한 것만 켜기". 툴 묶음은 저장해 두기 패턴(ADR-0092)으로 프리셋이 된다.
2. **현실 수준 꼬리표.** 툴마다 흔함(장비 API·알람·메트릭·서비스 상태) / 드묾(토폴로지·절차서 검색) / 없음(영향 범위·자동 근본원인)을 단다. 운영 모드와 벤치 세트의 기본 묶음은 "흔함"만. 영향 범위는 툴이 아니라 **채점 기준**(세계가 아는 정답)으로 쓴다. "드묾·없음"은 설계자가 일부러 켤 때만 — 그 툴의 가치를 재는 실험이 된다.
3. **툴 설명 표준.** 한 줄 요약 → 언제 쓰나 / 언제 쓰지 않나(대신 무엇을) → 입력 예 하나 → 읽기/쓰기 → 비용. 변별력 점검에 "툴 고르기 점검"(기준 에이전트로 상황별 혼동 행렬)을 더해 모호한 쌍을 화면에 보인다.
4. **에스컬레이션 툴 `ask_human`.** 부르면 실행이 "사람 기다리는 중"으로 멈추고 홈·실험 화면에 카드: 최근 툴 호출 5개, 에이전트의 요청, 사람이 할 수 있는 것 셋(답만 하기 / 대신 조치하기 — 세계 화면에서 한 것이 툴 결과로 돌아감 / 툴 더 주고 계속) 또는 끝내기. 점수표에 에스컬레이션 횟수·기다린 시간·사람이 한 조치를 따로 적는다. 실험 설정에 "에스컬레이션 처리: 사람 기다림 / 정해 둔 답으로 자동 응답 / 실패로 끝냄".
5. **고장 범위.** 고장마다 "풀려면 필요한 툴"을 코어에 적고, 실험 설정에 "고장 범위: 준 툴 안에서만 / 전부". 안에서만이면 범위 밖 시나리오는 회색(이유 붙음)이고 배경 고장도 범위 밖은 일어나지 않는다. 일부러 범위 밖을 켜면 에스컬레이션 자체를 재는 실험이 된다.
6. **절차서(SOP)는 실험 변수.** "안 줌 / 줌 / 찾게 함(`search_runbooks`)". 절차서는 시나리오 편집기의 탭(단계: 할 일·확인할 것·쓰는 툴), 최고 궤적에서 초안 만들기, 팀 SOP 붙여 넣기. 채점에 "SOP 준수"(했나·순서·건너뜀)를 복구 우선 채점과 별도로 둔다. 절차서도 저장해 두기 패턴.

## 결과
REQ-080(툴 범위·꼬리표), REQ-081(에스컬레이션), REQ-082(절차서). 지금 21개 툴의 설명을 표준으로 다시 쓴다.
