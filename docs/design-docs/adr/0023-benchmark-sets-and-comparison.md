# ADR-0023 같은 시험지끼리만 줄 세운다

## 맥락
여러 사람이 각자 실험을 돌리고(REQ-033), 그 결과를 벤치마크 사이트처럼 비교하고 싶다(REQ-039). 포크한 실험이 원본보다
나아졌는지도 보여야 한다(REQ-040). 그런데 "누가 더 잘했나"는 같은 시험지를 풀었을 때만 의미가 있고, 실행 한두 번의 점수 차는
운일 수 있다. 무엇을 같은 시험지로 볼지, 몇 번 돌려야 순위에 오를지, 언제 "나아졌다"고 말할지를 정해야 한다.

## 결정
1. **벤치마크 세트 = 시험지.** 키는 `hash(세계 digest, 시나리오 digest, 오라클 버전, 시간 정책, 제품 버전 프로파일)`이다.
   하네스·에이전트·툴은 키에 넣지 않는다 — 그게 바로 비교하려는 대상이기 때문이다. 시드도 넣지 않는다(실행마다 다르다).
   이름이 아니라 digest를 쓰므로, 누가 세계를 고치면 새 세트가 된다.
2. **한 줄 = 구성(하네스 × 에이전트 × 툴 집합).** 같은 세트 안에서 같은 구성은 실험·사람과 상관없이 실행을 합친다.
   툴은 순서 없는 집합으로 본다.
3. **순위 조건: 완료된 실행 3번 이상**(`MIN_RUNS_TO_RANK`). 그보다 적으면 표에는 나오지만 순위가 없다(아래에 따로).
4. **정렬:** 평균 점수 → 합격률 → 진단까지 걸린 시간(짧을수록) → 툴 호출 수(적을수록). 모두 같으면 같은 순위.
5. **"분명한 차이" = 두 평균의 95% 신뢰구간(Student t)이 겹치지 않을 때.** 둘 중 하나라도 실행이 1번뿐이면 분명하다고 하지 않는다.
   포크 비교와 결과 화면의 문장이 이 기준을 쓴다.

## 이유
- 시험지가 다르면 점수는 비교 대상이 아니다. 세계가 조금만 달라도(랙 하나, 냉방기 하나) 난이도가 바뀐다.
- 구성을 합치면 여러 사람이 같은 에이전트를 돌린 결과가 모여 표본이 커진다. 순위가 "누가 운 좋게 한 번 돌렸나"가 되지 않는다.
- 3번은 신뢰구간을 계산할 수 있는 최소(자유도 2)에 가깝고, 사용자가 기다릴 만한 수다. 기본 시드 수(`DEFAULT_SEEDS`)와 맞춘다.
- 겹치지 않는 신뢰구간은 엄밀한 t-검정보다 보수적이지만, 화면의 오차 막대만 보고 누구나 같은 판단을 할 수 있다. 설명할 수 있는 기준이 낫다.

## 버린 대안
- **세트 없이 전체 순위**: 쉬운 시나리오를 돌린 사람이 1등이 된다.
- **하네스까지 키에 포함**: 하네스끼리 비교할 수 없게 된다(REQ-030의 핵심 비교).
- **Elo 같은 대전 점수**: 실행끼리 직접 겨루지 않으므로 맞지 않고 설명하기 어렵다.
- **p-value 표기**: 숫자의 뜻을 오해하기 쉽고, 실행 수가 적을 때 잘못된 확신을 준다.

## 결과
- 서버의 대시보드 API는 `buildLeaderboards`를 그대로 쓴다. 세트 제목은 세계 이름 · 시나리오 이름이다.
- 시간 정책이나 제품 버전을 바꾼 포크는 원본과 다른 세트에 들어간다. 원본과의 비교(REQ-040)는 세트와 무관하게 보이지만,
  순위표에서는 따로 선다.
