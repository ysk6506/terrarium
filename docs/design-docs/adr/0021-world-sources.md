# ADR-0021 세계 소스

## 맥락
세계는 두 길로 만들어진다. 사업장 프리셋과 크기 파라미터로 생성하는 길(REQ-009, REQ-035)과, FalkorDB 그래프 같은
현실 기록을 읽어 오는 길(REQ-010, REQ-011)이다. 현실 기록은 소스마다 모양이 다르다: 사업장 지도나 전력 계통이 없는 소스도 있고, 관계 이름의 철자가 여럿일 수 있다
(PART_OF/PORT_OF, NicPort/NICPort). 어느 길로 만들든 시나리오가 의미 있으려면 세계가 평상시에 조용해야 한다.

## 결정
1. **조립은 한 곳**(`core.sources`의 `BlueprintAssembler`): 서버룸 안 배치는 `core.spatial`이, 서버룸 → 층 → 건물 → 부지 배치는 조립기가 한다.
   생성기와 가져오기는 "무엇이 어디 있는지"만 말한다 (ADR-0008).
2. **생성 세계는 평상시 건강해야 한다**: PDU 용량의 80% 안에서만 서버를 채우고, 냉방기·분전반·UPS 수를 예상 부하로 정하고,
   VM 수요를 호스트 CPU가 쉬는 동안 60%를 넘지 않게 맞춘다. 이중화(N+1 냉방, A/B 전원)는 실제로 고장 하나를 견뎌야 한다.
3. **사업장 프리셋은 이름과 대략의 부지 크기만** 가진다. 실제 지도처럼 보이게 하지 않는다.
4. **KG 지식은 매핑 하나에만** 있다(`CLOUD_TOPOLOGY_MAPPING`). 순수 데이터라 배포마다 JSON으로 덮어쓸 수 있다.
   이름 변형은 목록으로, 저장 방향이 불확실한 관계는 `either`로 받는다.
5. **접어서 가져온다**: ESXi 호스트는 HOSTED_ON으로 물리 서버에 합치고, NIC 포트 → 스위치 포트 사슬은 포트 이름을 단 서버→스위치
   네트워크 링크로, 스토리지 볼륨 사슬은 데이터스토어→스토리지 `backed_by`로 접는다.
6. **배치는 관계 먼저, 위치 속성 다음**, 둘 다 없으면 "미배치" 랙에 모은다. 추정한 개수는 모두 보고서에 센다.
7. **시뮬레이션에 필요하지만 기록에 없는 것은 가정하고 드러낸다**: 전력 계통(A/B PDU·분전반·UPS)과 냉방 관계가 없는 랙, 냉방기가 없는 서버룸.
   더한 것에는 `synthesized` 표시를 하고 보고서에 문장으로 남긴다. **실제 장비는 고치지 않는다**: 실제 냉방 용량이 부족하면 경고만 한다.
8. **현실은 읽기만 한다**: 포트에는 읽기 메서드 셋뿐이다. 그래프 어댑터는 `READ_QUERIES`로만 질의를 만들고(라벨은 식별자 검사,
   값은 매개변수), 읽기 전용 API(GRAPH.RO_QUERY)로 실행한다. `assertReadOnly`가 두 번째 잠금이다.
9. **범위**: 큰 그래프는 서버룸 이름으로 범위를 좁혀 가져온다. 범위 밖으로 가는 링크는 버리고 개수를 보고한다. 기본 상한은 2만 개다.

## 이유
- 조립이 한 곳이면 두 소스의 세계가 같은 규칙으로 놓이고, 공간 규칙을 한 번만 테스트하면 된다.
- 시작부터 알람이 울리는 세계에서는 에이전트가 장애를 찾을 수 없다. 측정이 무의미해진다.
- 가정을 숨기면 결과를 믿을 수 없고, 현실 장비를 "고치면" 그것은 더 이상 그 현실의 쌍둥이가 아니다.
- 쓰기 경로가 구조적으로 없으면 실수로 현실을 바꾸는 일이 일어날 수 없다.

## 버린 대안
- **KG 스키마를 코드 곳곳에서 해석**: 스키마가 바뀔 때마다 여러 파일을 고쳐야 한다.
- **전력이 없는 세계를 그대로 둔다**: 모든 서버가 전원 없음으로 시작해 시뮬레이션이 되지 않는다.
- **부족한 실제 냉방을 자동으로 키운다**: 현실과 다른 세계가 되고, 그 사실이 보이지 않는다.

## 결과
설명은 [세계 소스](../world-sources.md). FalkorDB 어댑터는 서버(`server.adapters`)에 두고 이 단위의 질의만 쓴다.
