# ADR-0064 GPU 백엔드는 서버마다 NIC 여럿을 rail로 꽂는 세 번째 패브릭이고, rail 하나를 잃으면 느려질 뿐 끊기지 않는다

## 맥락
제품 책임자의 요구: 사업장 네트워크는 레거시, 클라우드, GPU 세 가지 구조를 다룬다. 앞의 둘은 ADR-0062가 다뤘다.
GPU 클러스터의 백엔드 망은 모양이 다르다. 서버 하나에 NIC가 GPU마다 하나씩 8개 있고, 모든 서버의 1번 NIC는 1번 leaf, 2번 NIC는 2번 leaf에 꽂힌다(rail-optimized). leaf는 스파인으로 올라간다. 그래서 고장도 다르게 보인다. 케이블 하나가 끊기거나 leaf 하나가 죽어도 서버는 살아 있고 7개 rail로 통신한다. 그런데 집합 통신(all-reduce)은 가장 느린 NIC에 맞추어 도니까 학습 전체가 느려진다. 알람이 "서버가 끊겼다"면 거짓이고, 아무 알람도 없으면 놓친다.

## 결정
1. **패브릭 종류에 `gpu`를 더한다.** 설계는 `cloud`와 같다(leaf의 모든 위쪽 케이블이 /31 라우팅 포트, leaf마다 anycast 게이트웨이, 케이블마다 eBGP). 다른 점은 VXLAN·EVPN이 없다는 것이다. GPU 백엔드는 이더넷 위의 RoCE이고 L3 라우팅만 쓴다. `show vxlan vni`는 "설정 없음", EVPN 요약은 이웃이 없고, `running-config`에 VXLAN 줄이 없다.
2. **종류는 스위치 속성 `fabric: gpu`가 정하고, 속성이 없으면 케이블에서 알아낸다.** 같은 도메인의 leaf 4개 이상에 꽂힌 서버가 하나라도 있으면 GPU 패브릭이다. 이중화(NIC 2개)는 이 값에 못 미친다. 네트워크를 이렇게 짜는 이유는 rail뿐이어서 오판할 일이 드물다. 속성이 있으면 속성이 이긴다.
3. **NIC마다 호스트 계획이 하나다.** 서버가 GPU 패브릭 leaf 2개 이상에 꽂혀 있으면, 꽂힌 순서대로 rail 1, 2, 3…이고 각 NIC가 자기 leaf의 /24에서 주소를 받는다. 이 NIC 계획은 `rail` 번호를 갖고, 열쇠(`key`)는 서버 아이디, 서버에 다른 계획이 이미 있으면 `<아이디>#r<번호>`다. 일반 케이블(관리망, 스토리지망)이 같이 있으면 그것이 서버의 첫 계획이고 모든 rail이 `#r`이다. ARP, MAC 표, `ping`, 도달성 계산은 NIC(키)마다 돈다. NIC마다 MAC이 다르다.
4. **rail을 잃어도 `host_unreachable`을 올리지 않는다.** 그 알람은 서버가 끊겼다는 뜻이다. rail NIC는 설정 오류로 끊겨도 `gpu_rail_degraded`가 말한다.
5. **알람 `gpu_rail_degraded.<끊긴 rail 번호들>`.** 서버가 켜져 있고 rail이 하나라도 위쪽 스위치에서 `ping`으로 닿지 않으면, 어떤 이유든(케이블, leaf 전원, BGP 이웃 shutdown, VLAN·SVI 설정) 서버당 하나가 오른다. 메시지는 몇 번 rail이 8개 중 몇 개인지 말한다. 전부 끊기면 critical, 아니면 warning이다. 알람은 처음 올랐을 때의 메시지를 간직하므로 끊긴 rail을 코드에 넣었다(`gpu_rail_degraded.2-7`). rail이 더 끊기면 새 코드의 알람으로 바뀐다. 스파인 하나가 사라지면 다른 스파인으로 닿으므로 알람이 없다(스파인을 모두 보는 `ping`).
6. **카탈로그에 400G 64포트 leaf(`al-rail-64x400g`)와 스파인(`al-rail-spine-64x400g`)을 더한다.** 값은 180백만 원(약 13.4만 달러)이다. 판매가를 찾지 못한 추정이다.
7. **InfiniBand는 하지 않는다.** 스위치 OS 두 종(EOS, NX-OS)이 이미 있다. InfiniBand는 NVIDIA 스위치 OS(MLNX-OS, UFM)를 따로 흉내 내야 한다.
8. **요구사항 REQ-067**을 더하고, REQ-065의 "GPU 네트워크는 다음 결정에서" 문장을 "REQ-067이 다룬다"로 바꾼다.

## 버린 대안
- **NIC를 월드의 엔티티로**: 수천 장 클러스터에서 엔티티가 서버의 8배다. 케이블의 한쪽 끝이 NIC라는 건 케이블이 이미 말해 준다.
- **rail을 이름이나 속성으로 지정**: 가져온 월드에서 쓸 수 없다. 케이블의 순서가 이미 번호다.
- **`host_unreachable`을 rail에도 사용**: 한 rail을 잃은 서버를 끊긴 서버와 같게 말한다. 에이전트가 처음 해야 할 일("끊긴 건가, 느려진 건가")을 가려 버린다.
- **알람 메시지를 갱신하게 엔진을 고침**: 모든 알람이 영향을 받는다(온도처럼 계속 변하는 값이 매번 새 알람이 된다). 이 알람만 코드로 풀었다.

## 한계 (솔직하게)
- GPU 클러스터를 만드는 **생성기는 없다.** 생성기가 만드는 GPU 서버는 일반 랙의 ToR 하나에만 꽂힌다. GPU 백엔드는 가져온 월드나 손으로 그린 청사진(NIC 케이블과 `fabric` 속성)에서 나온다.
- 대역폭은 없다. NIC 속도(400G, 800G)와 leaf 포트 속도가 맞는지, rail 하나를 잃으면 몇 % 느려지는지는 계산하지 않는다. "느려진다"는 말뿐이다.
- 서버의 NIC 수가 GPU 수와 같은지, 모든 서버가 모든 rail에 꽂혀 있는지(rail 균형)는 검사하지 않는다.
- PFC, ECN, DCQCN, 혼잡, 패킷 손실은 없다. 이더넷 RoCE의 진짜 고장(PFC 폭풍, ECN 미설정)은 흉내 내지 못한다.
- InfiniBand, 서브넷 매니저, UFM, NCCL은 없다.
- rail 계획이 만드는 서버당 NIC가 월드에 8개 호스트 계획으로 들어간다. 수천 대 월드에서 `ping` 판정은 서브넷마다 한 번만 계산해 나누지만, 실측은 아직 하지 않았다.
