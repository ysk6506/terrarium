# ADR-0026 하네스를 붙이는 세 가지 길

## 맥락
REQ-031은 하네스마다 다른 방식을 감싸는 계층을 요구한다. 사용자의 하네스는 여기서 닿을 수 없고, 앞으로 무엇이 붙을지도 모른다.
붙이는 일이 무거우면 아무도 붙이지 않는다. 또 에이전트 없이도 서버가 쓸모 있어야 한다(첫 실험, 기준선, 용량 측정).

## 결정
모든 하네스는 core의 `HarnessPort`(에이전트 목록, 실행 하나 돌리기) 뒤에 있다. 구현은 세 가지다.

1. **내장(scripted)** — 테라리움 툴만 쓰는 규칙 기반 기준 에이전트: `triage`(알람을 의존 방향으로 따라 올라가 원인을 찾음),
   `guess`(무작위, 시드 고정), `idle`(아무것도 안 함). 항상 있다(`builtin`). 벤치마크의 바닥과 잣대가 된다.
2. **OpenAI 호환(openai)** — 테라리움이 직접 도는 최소 에이전트 루프. LiteLLM·vLLM 같은 Chat Completions 엔드포인트의
   모델이 툴을 함수로 부른다. "다른 건 다 같고 모델만 다를 때"를 비교할 수 있다.
3. **하네스 프로토콜(http)** — 외부 하네스를 붙이는 기본 길. 테라리움이 `POST /runs`로 실행을 부탁하면서 **그 실행 전용 MCP
   엔드포인트**를 준다. 하네스는 자기 방식대로 에이전트를 돌리고 MCP로 툴을 부른다. 테라리움은 `GET /runs/:id`로 끝났는지 보고,
   취소는 `DELETE /runs/:id`. 끝날 때 토큰·비용·trace id를 알려 주면 분석에 쓴다. 문서: [하네스 프로토콜](../harness-protocol.md).

- 비밀 값(API 키, 토큰)은 설정 파일이 아니라 환경 변수 이름으로만 가리킨다.
- W3C `traceparent`를 넘겨, 하네스의 스팬이 실행의 trace에 붙게 한다(ClickStack 분석, REQ-037).

## 이유
- 툴을 MCP로 주면 하네스는 테라리움 코드를 몰라도 된다. MCP는 에이전트 프레임워크 대부분이 이미 지원한다.
- 실행 요청·상태·취소 세 가지만 있으면 하네스 앞에 얇은 어댑터(shim)만 두면 된다. 폴링은 방화벽·프록시 뒤에서도 잘 된다.
- 내장 기준 에이전트가 있으면 시나리오가 너무 쉬운지/어려운지도 바로 보인다(규칙이 다 맞히면 너무 쉬운 것).

## 버린 대안
- **하네스마다 전용 어댑터를 코드로**: 붙일 때마다 테라리움을 고쳐야 한다.
- **웹훅(콜백)으로 완료 알림**: 하네스가 테라리움 주소에 닿아야 하고, 놓친 콜백을 다시 받을 방법이 필요하다. 폴링이 단순하다.
- **툴을 HTTP REST로 노출**: 하네스마다 툴 호출 코드를 새로 짜야 한다. MCP는 이미 있다.
