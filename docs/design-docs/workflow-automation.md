# E2E 워크플로 자동화 (제안)

**이 문서는 제안이에요.** 제품 목표를 넓히는 결정이 있어야 요구사항과 결정 기록이 돼요(1절). 만들기는 운영 세계와 권한이 선 뒤에 시작해요(15절).

## 0. 한 문장

운영 세계의 객체에 "누가 무엇을 해도 되는지"를 워크플로로 정하고, **실험용 복사본에서 통과한 워크플로만** 실제 에이전트가 MCP 게이트웨이를 거쳐 실행하게 해요. 테라리움은 규칙과 승인과 기록을 맡고, 현실 장비에는 여전히 손대지 않아요.

## 1. 제품 목표와의 관계 (먼저 말해요)

지금 목표는 "평가하는 실험장"이에요. 실제 일을 에이전트에게 맡기는 것은 목표 밖이라서, 이 기능은 목표를 넓히는 결정이 필요해요.

넓힐 만한 이유는 하나예요. 워크플로를 그리고 에이전트를 붙이는 도구는 어디에나 있어요. 테라리움만 할 수 있는 것은 **내보내기 전에 같은 워크플로를 닮은 세계에서 돌려 보고 점수로 통과시키는 것**, 그리고 **내보낸 뒤에도 같은 잣대로 계속 재는 것**이에요. 그래서 이 기능은 "빌더"가 아니라 "검증을 통과해야 열리는 문"으로 설계해요.

제안하는 목표 문장의 덧붙임: "…평가하고, **평가를 통과한 일만 운영에 나가게 하는** 사내 실험장."

원칙 여섯에 대 보면 이래요.

| 원칙 | 이 기능에서 |
|---|---|
| 모델은 하나 | 워크플로의 단계와 액션은 실험과 운영에서 같은 정의예요. 액션에 묶는 툴만 달라요 |
| 자산은 세계를 가리지 않는다 | 워크플로는 실험 세계에서 돌고 채점돼요. 시나리오·툴·채점과 같은 자산이에요 |
| 버전을 고정하면 결과가 같다 | 워크플로 버전이 모델·액션·묶기·에이전트·승인 규칙의 버전을 함께 묶어요 |
| 모르는 것은 말하고 고칠 길을 준다 | 실험에 흉내가 없는 액션, 게이트웨이가 지켜 주지 못하는 규칙은 화면에 표시하고 그만큼 권한을 줄여요 |
| 사람은 규칙을 정하고 건별로 손대지 않는다 | 승인은 규칙(액션의 위험 등급)이에요. 건마다 승인은 규칙이 요구할 때만 하고, 실적이 쌓이면 줄여요 |
| 현실에는 읽기만 한다 | 테라리움은 실제 툴을 부르지 않아요. 부르는 것은 에이전트, 막는 것은 게이트웨이예요 |

## 2. 큰 그림: 정하는 곳, 막는 곳, 하는 곳

| 누가 | 맡는 것 |
|---|---|
| 테라리움 | **정해요**(워크플로·범위·승인 규칙), **답해요**("이 호출을 해도 되나"), **적어요**(건의 기록), **재요**(끝까지 간 비율, 줄어든 사람 손) |
| MCP 게이트웨이 | **막아요.** 에이전트의 신원과 툴 호출의 인증·인가를 책임져요. 테라리움이 낸 허가증이 없는 호출은 통과시키지 않아요 |
| 에이전트 | **해요.** 자기 툴과 스킬을 가진 채 연동돼서, 게이트웨이를 거쳐 실제 툴을 불러요 |

테라리움이 규칙을 정해도 지키는 힘은 게이트웨이에 있어요. 그래서 게이트웨이와의 연동 수준이 이 기능이 할 수 있는 일을 정해요.

| 연동 수준 | 게이트웨이가 해 주는 것 | 테라리움이 할 수 있는 것 |
|---|---|---|
| 가. 보기만 | 서버와 툴 목록, 호출 기록 | 워크플로 정의, 실험 검증, 그림자 적용, 기록과 지표. **막지는 못해요** |
| 나. 허가증 | 호출 전에 테라리움이 낸 허가증을 확인(또는 테라리움에 물어봄) | 범위와 승인을 호출마다 강제. 승인 적용과 자율 적용 |

되돌릴 수 없는 액션은 수준 나에서만 에이전트에게 맡겨요. 수준 가에서는 사람이 해요.

## 3. 낱말

새 말은 넷만 더해요. 나머지는 이미 있는 말이에요.

| 말 | 뜻 |
|---|---|
| **워크플로** | 어떤 일이 시작돼서 끝날 때까지의 단계와, 단계마다 누가 무엇을 해도 되는지 |
| **건** | 워크플로가 한 번 돈 것. 실험의 "실행"과 섞이지 않게 따로 불러요(워크플로 › 건 › 단계) |
| **묶기** | 액션을 실제 툴에 잇는 규칙(객체 타입과 액션과 조건 → 서버·툴·인자) |
| **허가증** | 이 건의 이 단계에서 이 대상에게 이 툴을 불러도 된다는, 짧게만 유효한 표 |

"운영 모드"는 이미 실험의 한 종류 이름이에요([운영 모드](operation-mode.md)). 워크플로가 실제 일에 쓰이는 상태는 **운영 적용**이라고 불러요.

## 4. 워크플로의 모양

빈 캔버스에서 시작하지 않아요. 시나리오마다 적어 둔 **지금 하는 방식 표**([프로세스 비교](process-compare.md): 순번, 누가, 무엇을, 걸리는 시간)를 복사해 "앞으로 하는 방식"으로 고쳐요. 단계를 합치거나 없애고, 남은 단계마다 담당을 사람 역할 또는 에이전트로 정해요. 몸을 써야 하는 단계는 사람으로 남아요.

단계 하나가 갖는 것:

| 칸 | 내용 |
|---|---|
| 담당 | 사람 역할, 또는 연동된 에이전트 하나(버전 고정) |
| 해도 되는 액션 | 객체 타입과 동사의 목록. 여기 없는 것은 못 해요 |
| 범위 | 이 단계가 읽고 손댈 수 있는 객체(8절) |
| 승인 | 필요 여부와 승인자(9절). 에이전트 단계는 반드시 적어요 |
| 끝났다는 조건 | 객체의 상태가 어떻게 돼 있어야 하나(사후 확인) |
| 시간 한도와 실패하면 | 넘으면 누구에게 넘기나 |

흐름은 처음에는 **차례대로, 조건이 맞으면 건너뛰기, 실패하면 넘기기**만 둬요. 갈라졌다 모이는 흐름은 쓰임이 확인되면 더해요.

## 5. 액션과 묶기

### 액션은 모델의 것이에요
모델에는 이미 액션이 있어요(툴과 승인·넘기기, [현실 데이터와 모델](reality-data-and-ontology.md)). 이것을 객체 타입마다의 **동사 목록**으로 드러내요.

| 액션이 갖는 것 | 쓰임 |
|---|---|
| 대상 객체 타입과 입력 값 | 묶기의 인자 |
| 위험 등급: 읽기 / 되돌릴 수 있음 / 되돌릴 수 없음 | 승인 규칙의 기본값 |
| 기대 효과: 객체의 어떤 상태가 어떻게 바뀌나 | 사후 확인 |
| 되돌리는 액션 | 실패했을 때 제안 |
| 실험 세계의 툴 | 실험에서 이 액션을 하는 방법 |

동사는 닫힌 목록으로 시작해요: 조회, 재시작, 끄기·켜기, 옮기기, 비우기, 격리, 설정 바꾸기, 늘리기·줄이기, 전력 상한 정하기, 교체 요청, 티켓 만들기·고치기, 알리기. 사용자가 액션을 더할 수 있지만 실험에 흉내가 없으므로 "검증할 수 없음"으로 표시되고, 늘 승인을 받아야 하며 자율 적용으로 올라가지 못해요.

### 묶기는 규칙이에요. 객체를 하나씩 잇지 않아요
게이트웨이에서 읽어 온 툴 목록을 보고 **객체 타입 × 액션 × 조건 → 서버·툴·인자**를 정해요. 조건은 객체의 속성이에요(예: 플랫폼이 무엇인가에 따라 다른 툴). 인자 칸에는 대상 객체의 어느 속성이 들어가는지 적어요. 이 인자 대응이 있어야 게이트웨이가 "이 호출의 대상이 누구인지" 알고 범위를 지킬 수 있어요.

- 화면은 못 묶인 것을 까닭별로 모아 보여요: 맞는 툴이 없음, 인자를 채울 속성이 없음, 조건이 겹침.
- 툴의 이름·설명·입력 모양과 액션을 견줘 후보를 제안해요. 제안은 목록을 읽어 온 뒤에만 나와요.
- 실제 객체 몇 개로 "이렇게 부르게 돼요"를 미리 보여 줘요. 테라리움이 부르지는 않아요.
- 묶기는 툴의 입력 모양 지문을 함께 고정해요. 동기화에서 지문이 달라지면 그 묶기를 쓰는 워크플로는 "점검 필요"가 되고, 자율 적용이던 단계는 승인 적용으로 내려가요.

## 6. 게이트웨이와 잇기

- **읽어 오기.** 게이트웨이는 소스의 한 종류예요([소스 관리](source-management.md)). 서버와 툴의 이름·설명·입력 모양을 읽기 전용으로 주기마다 받아 저장하고 이력을 남겨요. 자격 증명은 받지도 갖지도 않아요.
- **내놓기.** 테라리움은 에이전트가 쓸 MCP 서버 하나를 내놔요: 객체 찾기, 이웃 보기, 영향 범위, 바뀐 것 보기, 이 건의 범위와 이 단계에서 해도 되는 액션 보기, 승인 요청, 단계 끝 보고. 이 서버도 게이트웨이에 등록해서 에이전트의 인증이 한곳에서 이뤄지게 해요.
- **등록 확인.** 테라리움이 다음 동기화에서 자기 서버를 목록에서 찾고, 에이전트가 건 없이 "나는 누구인가"를 한 번 불러 성공하면 확인된 것으로 봐요.

## 7. 시작 조건

닫힌 목록 넷이에요.

| 시작 조건 | 예 | 알아 둘 것 |
|---|---|---|
| 사건 | 운영 세계에 들어온 알람이 조건(객체 타입·종류·심각도)에 맞음 | 동기화 주기만큼 늦어요. 소스가 밀어 줄 수 있으면 받아서 줄여요 |
| 상태 변화 | 동기화가 찾은 차이(용량이 기준을 넘음, 설정이 기준과 달라짐, 만료가 가까움) | 운영 세계의 이력에서 나와요 |
| 일정 | 점검, 패치 시간 | 변경 금지 기간 달력을 지켜요 |
| 사람의 요청 | 양식, API, 티켓 시스템의 웹훅 | 요청한 사람이 기록에 남아요 |

- 알람이 쏟아질 때: 영향 범위가 겹치는 알람은 **한 건**으로 묶어요. 건은 알람이 아니라 뿌리 후보 하나에 대해 열려요.
- 같은 객체에 같은 워크플로는 동시에 한 건만 돌아요. 다른 워크플로가 손대는 중인 객체는 잠겨 있어요.
- 되풀이 방지 시간과 하루 건수 한도를 워크플로마다 둬요. 한도를 넘으면 멈추고 알려요.
- 초 단위로 대응해야 하는 일에는 맞지 않아요. 화면에 그렇게 적어요.

## 8. 범위

건의 범위는 **시작한 객체에서 규칙으로 넓힌 것**이에요. 규칙은 링크 타입과 방향과 걸음 수, 영향 범위, 저장해 둔 객체 묶음, 속성 조건 가운데서 골라요. 단계는 건의 범위를 좁힐 수만 있어요.

- 읽는 범위와 손대는 범위를 따로 둬요. 진단은 넓게 읽고 조치는 좁게 해요.
- 읽기는 테라리움의 MCP 서버가 직접 걸러요. 실제 툴 호출은 게이트웨이가 허가증의 대상 목록과 인자를 맞춰 봐요(수준 나).
- 묶기가 없는 툴은 대상을 알 수 없어서 범위를 지킬 수 없어요. 건 안에서 그런 툴의 호출은 읽기 등급이면 통과시키고 적고, 그 밖에는 거절해요.
- 범위 밖 시도는 기록하고 알려요. 되풀이되면 건을 멈춰요.
- 객체를 마지막으로 본 때가 오래됐으면(동기화가 밀렸으면) 그 객체에 대한 조치를 허가하지 않아요.

## 9. 승인

- **기본값은 위험 등급에서 와요.** 읽기는 승인 없음, 되돌릴 수 있는 것은 승인 한 사람, 되돌릴 수 없는 것은 승인 두 사람. 만드는 사람이 단계마다 고쳐 적지만, 되돌릴 수 없는 액션을 "승인 없음"으로 바꾸는 것은 관리자만 할 수 있어요.
- **승인자는 사람, 무리, 또는 "그 객체를 맡은 조직의 당번"**이에요. 마지막 것은 모델의 담당 링크에서 풀어요. 그래서 다른 조직의 객체에 손대는 단계는 그 조직이 승인해요. 요청한 쪽이 스스로 승인할 수는 없어요.
- **승인 화면이 답하는 것**: 무엇을 하려 하나(액션·대상·툴·인자), 왜(에이전트가 본 것), 이 객체가 멈추면 무엇이 멈추나(영향 범위), **실험용 복사본에서 같은 조치를 미리 돌려 본 결과**, 되돌리는 방법. 누를 것은 승인, 거절(이유), 사람이 직접 하기.
- 승인은 그 호출 한 번, 그 인자에만 유효해요. 인자가 달라지면 다시 받아요. 시간 한도를 넘으면 기본은 취소예요.
- **승급과 내려감.** 같은 액션 규칙이 승인을 받고 정해 둔 번수만큼 잇달아 성공하면(사후 확인 통과, 되돌림 없음) "스스로 하게 할까요?"를 제안해요. 정하는 것은 사람이에요. 실패나 되돌림이 생기면 저절로 승인 적용으로 내려가요.

## 10. 적용 단계

| 단계 | 에이전트가 하는 것 | 올라가는 조건 |
|---|---|---|
| 초안 | 없음 | — |
| 검증 | 실험용 복사본에서 워크플로를 돌려요. 시작 조건에 맞는 고장을 넣고, 액션은 실험의 툴로 하고, 채점해요 | 정해 둔 상황 수와 번수에서 합격 기준을 넘음. 통과 기록이 버전에 붙어요 |
| 그림자 | 실제 건에서 읽기만 하고 "나라면 이렇게 하겠다"를 내요. 사람이 실제로 한 것과 견줘요 | 일치한 비율과 건수, 검토자의 승인 |
| 승인 적용 | 실제 툴을 부르되 9절의 승인을 받아요 | 승급 제안과 사람의 결정(단계마다) |
| 자율 적용 | 승인 없이 해요(규칙이 허락한 액션만) | — |

- 검증 없이는 그림자로 못 가요. 실험에 흉내가 없는 액션이 든 단계는 승인 적용까지만 가요.
- 배포는 만든 사람이 아닌 사람이 승인해요.
- 이전 버전으로 한 번에 되돌려요. 돌고 있던 건은 시작한 버전으로 끝나요.
- 멈춤 스위치는 워크플로, 에이전트, 전체에 하나씩 있어요.

## 11. 건의 한살이

1. 시작 조건이 맞으면 테라리움이 건을 열고, 첫 단계의 담당 에이전트를 실험 때와 같은 연결 방식으로 불러요. 건 번호, 단계, 목표, 범위, MCP 서버 주소를 줘요.
2. 에이전트가 토폴로지를 읽고, 조치가 필요하면 승인을 요청해요.
3. 승인되면 테라리움이 허가증을 내요. 에이전트는 게이트웨이를 거쳐 실제 툴을 불러요.
4. 테라리움이 **사후 확인**을 해요. 운영 세계의 다음 동기화에서 기대 효과가 보이는지 봐요.
5. 보이면 다음 단계로 가요. 사람 단계면 맡은 조직에 알리고 끝 표시를 기다려요.
6. 시간 초과, 거절, 사후 확인 실패는 사람에게 넘기고, 되돌리는 액션이 있으면 제안해요.

단계마다 에이전트가 달라도 건의 기록이 문맥이 돼요.

## 12. 누가 무엇을

전역 역할은 지금처럼 둘이에요([권한](permissions.md)). 워크플로마다 **맡은 일**을 사람이나 무리에게 줘요.

| 맡은 일 | 할 수 있는 것 |
|---|---|
| 주인 | 맡은 일 나눠 주기, 멈추기, 지우기 |
| 편집 | 초안 고치기, 검증 돌리기 |
| 배포 승인 | 적용 단계 올리기와 되돌리기. 자기가 고친 버전은 승인 못 해요 |
| 단계 승인 | 건 안의 승인 요청에 답하기 |
| 보기 | 건과 지표 보기 |

게이트웨이 연결과 액션 카탈로그는 관리자가 다뤄요. 묶기는 그 툴을 가진 조직의 사람이 만들고 관리자가 배포해요.

## 13. 지켜보기와 알리기

- **건 화면**은 실험의 실행 상세와 같은 틀이에요: 한 일 순서, 누가 승인했나, 무엇이 바뀌었나.
- **워크플로 화면의 첫 물음 셋**: 잘 돌고 있나(끝까지 간 비율), 어디서 막히나(넘긴 단계, 승인을 기다린 시간), 사람 손이 얼마나 줄었나(지금 하는 방식 표와 견준 단계·사람·시간).
- 함께 세는 것: 되돌린 수, 사후 확인 실패, 범위 밖 시도, 점검 필요가 된 묶기.
- 지표와 감사 기록은 밖으로 내보내요. 기록에는 비밀과 행의 내용을 넣지 않아요.
- **알림**은 사건 종류(승인 요청, 넘김, 실패, 멈춤, 끝, 범위 밖 시도, 묶기 점검 필요, 승급 제안)와 맡은 일과 채널의 조합이에요. 채널은 일반 웹훅과 메일로 시작하고 메신저는 웹훅 틀로 붙여요. 조용한 시간과 묶어 보내기가 있어요. 승인은 알림 안에서 하지 않고 링크로 들어와서 해요(누가 눌렀는지 확인해야 해서요).

## 14. 미리 봐 둔 위험

| 위험 | 대응 |
|---|---|
| 알람이나 티켓의 글이 에이전트를 속임 | 글은 데이터로만 다뤄요. 속아도 허가증과 범위와 승인 밖으로는 못 나가요 |
| 테라리움이 멈춤 | 게이트웨이는 허가증이 없으면 거절해요(닫힌 쪽으로 실패). 일은 사람 절차로 돌아가요. 그래서 운영 세계의 고가용이 먼저예요 |
| 실제 툴이 실험의 툴과 다르게 움직임 | 그림자 단계와 사후 확인이 잡아요. 어긋난 액션은 승인 적용으로 내려가요 |
| 툴이 바뀜 | 입력 모양 지문, 점검 필요, 내려감(5절) |
| 두 워크플로가 같은 객체에 손댐 | 잠금(7절) |
| 누가 책임지나 | 누가 배포를 승인했고 누가 건을 승인했는지, 어느 에이전트 버전이 했는지가 기록에 남아요 |
| 에이전트 비용 | 건마다 부른 수와 비용을 세고 워크플로마다 한도를 둬요 |
| 기존 변경 관리 절차 | 건이 티켓을 만들고 고치는 액션을 써서 기존 절차에 흔적을 남겨요 |

## 15. 순서

먼저 있어야 하는 것: 권한과 감사 기록, 운영 세계 한 줄(엑셀과 Splunk), 실험용 복사본, 액션을 모델의 동사 목록으로 드러내기.

그 뒤 얇게 한 줄: 워크플로 하나를 연동 수준 가로 **그림자까지**. 예를 들면 "서버 부품 고장: 진단(에이전트) → 교체 요청(에이전트, 승인) → 교체(사람) → 확인(에이전트)". 여기까지는 실제 툴 호출을 막을 필요가 없어서 게이트웨이의 허가증 기능 없이 값이 나와요.

그다음: 허가증(수준 나), 승인 적용, 승급.

지금 하는 일에 미리 반영할 것은 셋이에요. 감사 기록의 모양에 건과 승인을 넣을 자리를 두고, 권한에 자원마다의 맡은 일을 둘 수 있게 하고, 모델 화면에서 액션을 객체 타입 옆에 보여요.

## 16. 정해야 하는 것

1. 제품 목표를 넓힐지(1절의 문장).
2. 게이트웨이가 무엇을 해 줄 수 있는지: 툴 목록과 호출 기록을 읽을 수 있는지, 호출 전에 허가증을 확인할 수 있는지. 둘째가 안 되면 수준 가에 머물러요.
