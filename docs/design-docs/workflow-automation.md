# E2E 워크플로 자동화 (REQ-120 예정, [ADR-0189](adr/0189-verified-workflows-go-to-operation.md))

제품 목표의 넷째 부분("통과한 것만 운영에 나간다")의 설계예요. 만들기는 권한과 운영 세계가 선 뒤에 시작해요(16절).

## 0. 한 문장

운영 세계의 객체에 "누가 무엇을 해도 되는지"를 워크플로로 정하고, **실험용 복사본에서 통과한 워크플로만** 실제 에이전트가 MCP 게이트웨이를 거쳐 실행하게 해요. 테라리움은 규칙과 승인과 기록을 맡고, 현실 장비에는 여전히 손대지 않아요.

## 1. 왜 테라리움이 하나

워크플로를 그리고 에이전트를 붙이는 도구는 어디에나 있어요. 테라리움만 할 수 있는 것은 둘이에요. **내보내기 전에 같은 워크플로를 닮은 세계에서 돌려 보고 점수로 통과시키는 것**, 그리고 **내보낸 뒤에도 같은 잣대로 계속 재는 것**. 그래서 이 기능은 "빌더"가 아니라 "검증을 통과해야 열리는 문"이에요.

| 원칙 | 이 기능에서 |
|---|---|
| 모델은 하나 | 워크플로의 단계와 액션은 실험과 운영에서 같은 정의예요. 액션에 매핑하는 툴만 달라요 |
| 자산은 세계를 가리지 않는다 | 워크플로는 실험 세계에서 돌고 채점돼요. 시나리오·툴·채점과 같은 자산이에요 |
| 버전을 고정하면 결과가 같다 | 워크플로 버전이 모델·액션·툴 매핑·에이전트·승인 규칙의 버전을 함께 묶어요 |
| 모르는 것은 말하고 고칠 길을 준다 | 실험에 흉내가 없는 액션, 검증하지 못한 갈래는 화면에 표시하고 그만큼 사람에게 돌려요 |
| 사람은 규칙을 정하고 건별로 손대지 않는다 | 승인은 규칙(액션의 위험 등급)이에요. 건마다 승인은 규칙이 요구할 때만 하고, 실적이 쌓이면 줄여요 |
| 현실에는 읽기만 한다 | 테라리움은 실제 툴을 부르지 않아요. 부르는 것은 에이전트, 막는 것은 게이트웨이예요 |

## 2. 큰 그림: 정하는 곳, 막는 곳, 하는 곳

| 누가 | 맡는 것 |
|---|---|
| 테라리움 | **정해요**(워크플로·범위·승인 규칙), **알려 줘요**(이 단계에서 무엇을 어떤 툴과 인자로 부르나), **적어요**(건의 기록), **재요**(끝까지 간 비율, 줄어든 사람 손) |
| MCP 게이트웨이 | **막아요.** 에이전트의 신원과 툴 호출의 인증·인가를 책임져요 |
| 에이전트 | **해요.** 자기 툴과 스킬을 가진 채 연동돼서, 게이트웨이를 거쳐 실제 툴을 불러요 |

### 게이트웨이에 기대는 것 (가정)
이 설계는 게이트웨이가 인증과 인가를 책임진다는 가정 위에 있어요. 테라리움이 게이트웨이에서 받아야 하는 것은 셋이에요.

| 기대는 것 | 쓰임 | 없으면 |
|---|---|---|
| 서버와 툴의 목록(이름·설명·입력 모양)을 읽을 수 있다 | 툴 매핑(6절) | 툴 매핑을 손으로 적어야 해요 |
| 테라리움의 MCP 서버를 부르는 에이전트의 신원을 넘겨준다 | 건의 담당이 맞는지 확인(13절) | 건 토큰만으로 확인해요 |
| 실제 툴 호출을 인가할 때 테라리움이 낸 **허가증**을 확인하고, 호출 기록을 읽게 해 준다 | 범위와 승인을 호출마다 강제, 준비한 호출과 실제 호출의 대조 | 테라리움은 어긋난 호출을 **뒤에 알아챌** 뿐 막지 못해요. 이때 되돌릴 수 없는 액션은 사람이 해요 |

## 3. 낱말

새 말은 넷만 더해요. 나머지는 이미 있는 말이에요.

| 말 | 뜻 |
|---|---|
| **워크플로** | 어떤 일이 시작돼서 끝날 때까지의 단계와, 단계마다 누가 무엇을 해도 되는지 |
| **건** | 워크플로가 한 번 돈 것. 실험의 "실행"과 섞이지 않게 따로 불러요(워크플로 › 건 › 단계) |
| **툴 매핑** | 액션을 실제 툴에 잇는 규칙(객체 타입과 액션과 조건 → 서버·툴·인자). 실험 세계의 툴에는 이미 매핑돼 있어요 |
| **허가증** | 이 건의 이 단계에서 이 대상에게 이 툴을 이 인자로 불러도 된다는, 짧게만 유효한 표 |

"운영 모드"는 이미 실험의 한 종류 이름이에요([운영 모드](operation-mode.md)). 워크플로가 실제 일에 쓰이는 상태는 **운영 적용**이라고 불러요.

## 4. 워크플로의 모양

빈 캔버스에서 시작하지 않아요. 시나리오마다 적어 둔 **지금 하는 방식 표**([프로세스 비교](process-compare.md): 순번, 누가, 무엇을, 걸리는 시간)를 복사해 "앞으로 하는 방식"으로 고쳐요. 단계를 합치거나 없애고, 남은 단계마다 담당을 사람 역할 또는 에이전트로 정해요. 몸을 써야 하는 단계는 사람으로 남아요.

### 단계 하나가 갖는 것

| 칸 | 내용 |
|---|---|
| 담당 | 사람 역할, 또는 연동된 에이전트 하나(버전 고정) |
| 해도 되는 액션 | 객체 타입과 동사의 목록. 여기 없는 것은 못 해요. 액션과 대상을 미리 정해 둘 수도 있고(정해진 조치), 목록 안에서 에이전트가 고르게 둘 수도 있어요(판단) |
| 범위 | 이 단계가 읽고 손댈 수 있는 객체(9절) |
| 승인 | 필요 여부와 승인자(10절). 에이전트 단계는 반드시 적어요 |
| 출력 칸 | 이 단계가 남기는 값. 고르기 목록(예: 원인 종류), 수, 객체 목록 가운데서 정해요. 조건 분기가 읽어요 |
| 끝났다는 조건 | 객체의 상태가 어떻게 돼 있어야 하나(사후 확인) |
| 시간 한도, 다시 해 보기 | 몇 번까지 다시 하고, 넘으면 어느 갈래로 가나 |

## 5. 흐름: 조건 분기, 반복, 병렬, 대기

흐름은 **블록을 안에 넣는 구조**예요. 선을 아무 데나 잇는 그림이 아니에요. 그래서 어떤 워크플로도 반드시 끝나고, 들여쓴 목록으로 읽히고, 경로를 모두 셀 수 있어요.

| 블록 | 뜻 | 한도 |
|---|---|---|
| 단계 | 사람이나 에이전트가 하는 일 하나 | 시간 한도 |
| **조건 분기** | 조건마다 갈래 하나. 위에서부터 처음 맞는 갈래로 가요 | 마지막에 "그 밖에는" 갈래가 꼭 있어요. 안 적으면 "사람에게 넘기기"예요 |
| **반복** | 객체 목록의 하나하나에 같은 블록들을 해요(예: 영향 받는 서버마다 비우기 → 고치기 → 확인) | 한 번에 몇 개, 몇 개 실패하면 멈출지, 대상 수의 상한 |
| **병렬** | 갈래들을 동시에 해요(예: 두 조직이 각자 확인) | 모이는 조건(모두 끝나면, 하나라도 끝나면). 갈래끼리 같은 객체에 손대지 못해요 |
| **대기** | 조건이 될 때까지, 또는 정한 시간만큼 | 시간 한도가 꼭 있고, 넘으면 가는 갈래를 적어요 |
| 다른 워크플로 부르기 | 자주 쓰는 묶음을 다시 써요 | 부르는 버전을 고정하고, 범위는 좁혀서만 넘겨요 |
| 끝, 넘기기 | 건을 끝내거나 사람에게 넘겨요 | — |

끝없이 도는 되풀이는 없어요. 되풀이는 "반복"(대상 목록이 한도), "대기"(시간이 한도), "다시 해 보기"(번수가 한도)뿐이에요.

### 조건은 닫힌 목록이고, 테라리움이 따져요

| 조건이 보는 것 | 예 |
|---|---|
| 객체의 값 | 타입, 속성, 상태를 같다·다르다·크다·작다·들어 있다로 견줘요 |
| 앞 단계의 결과 | 성공, 실패, 거절, 시간 초과 |
| 앞 단계의 출력 칸 | 원인 종류가 하드웨어다, 대상이 3개가 넘는다 |
| 건의 사실 | 시작 조건의 종류, 심각도, 때(근무 시간, 변경 금지 기간) |
| 영향 범위 | 영향 받는 서비스가 몇 개인가, 특정 서비스가 들어 있나 |

- 조건은 "모두 맞을 때"와 "하나라도 맞을 때"로 묶어요. 식이나 코드를 적는 칸은 없어요.
- **에이전트의 판단은 출력 칸을 거쳐서만 조건 분기에 들어가요.** 에이전트가 쓴 글을 조건이 읽지 않아요. 고르기 목록의 값마다 갈래가 있어야 저장돼요("모름"도 값이에요).
- 조건은 에이전트가 아니라 테라리움이 따지고, 그때 본 값을 건에 적어요. "왜 이 경로로 갔나"가 기록에 남아요.

### 저장할 때 보는 것

- 모든 경로가 끝이나 넘기기에 닿는가. 갈 수 없는 갈래가 있는가.
- 에이전트 단계마다 승인이 적혀 있는가.
- 갈래마다 그 조건에 맞는 객체에 **매핑된 툴이 있는가**(예: 어떤 플랫폼의 갈래에만 툴이 없음).
- "병렬"의 갈래끼리 손대는 범위가 겹치지 않는가.
- **경로 목록**: 처음부터 끝까지의 경로마다 단계 수, 사람 손, 걸릴 시간을 보여 주고 지금 하는 방식과 견줘요.

### 고치는 화면
기본은 들여쓴 목록이에요. 블록 하나를 누르면 옆 칸에서 고쳐요. 그림(흐름도)은 같은 내용을 보여 주기만 해요. "이 건이라면 어느 경로로 가나"에 지난 사건이나 객체를 넣으면 조건을 따져서 경로를 칠해 줘요.

## 6. 액션과 툴 매핑

### 액션은 모델의 것이에요
모델에는 이미 액션이 있어요(툴과 승인·넘기기, [현실 데이터와 모델](reality-data-and-ontology.md)). 이것을 객체 타입마다의 **동사 목록**으로 드러내요.

| 액션이 갖는 것 | 쓰임 |
|---|---|
| 대상 객체 타입과 입력 칸 | 툴 매핑의 인자 |
| 위험 등급: 읽기 / 되돌릴 수 있음 / 되돌릴 수 없음 | 승인 규칙의 기본값 |
| 기대 효과: 객체의 어떤 상태가 어떻게 바뀌나 | 사후 확인 |
| 되돌리는 액션 | 실패했을 때 제안 |
| 실험 세계의 툴 | 실험에서 이 액션을 하는 방법 |

동사는 닫힌 목록으로 시작해요: 조회, 재시작, 끄기·켜기, 옮기기, 비우기, 격리, 설정 바꾸기, 늘리기·줄이기, 전력 상한 정하기, 교체 요청, 티켓 만들기·고치기, 알리기. 사용자가 액션을 더할 수 있지만 실험에 흉내가 없으므로 "검증할 수 없음"으로 표시되고, 늘 승인을 받아야 하며 자율 적용으로 올라가지 못해요.

### 툴 매핑은 규칙이에요. 객체를 하나씩 잇지 않아요
게이트웨이에서 읽어 온 툴 목록을 보고 **객체 타입 × 액션 × 조건 → 서버·툴·인자**를 정해요. 조건은 객체의 속성이에요(예: 플랫폼에 따라 다른 툴). 인자마다 무엇이 들어가는지 적어요: 대상 객체의 속성, 액션의 입력 칸, 정해 둔 값.

- 화면은 매핑하지 못한 것을 까닭별로 모아 보여요: 맞는 툴이 없음, 인자를 채울 속성이 없음, 조건이 겹침, 담당 에이전트가 그 툴을 부를 권한이 없음.
- 툴의 이름·설명·입력 모양과 액션을 견줘 후보를 제안해요. 제안은 목록을 읽어 온 뒤에만 나와요.
- 실제 객체 몇 개로 "이렇게 부르게 돼요"를 미리 보여 줘요. 테라리움이 부르지는 않아요.
- 툴 매핑은 툴의 입력 모양 지문을 함께 고정해요. 동기화에서 지문이 달라지면 그 매핑을 쓰는 워크플로는 "점검 필요"가 되고, 자율 적용이던 단계는 승인 적용으로 내려가요.
- 게이트웨이는 소스의 한 종류예요([소스 관리](source-management.md)). 읽기 전용으로 주기마다 받아 저장하고 이력을 남겨요. 자격 증명은 받지도 갖지도 않아요.

## 7. 에이전트에게 주는 MCP 툴

테라리움은 에이전트가 쓸 MCP 서버 하나를 내놓고, 이것도 게이트웨이에 등록해요. 에이전트는 이 서버에서 **무엇을 어떤 툴과 인자로 불러야 하는지**를 받아요.

| 툴 | 답하는 것 |
|---|---|
| `whoami` | 나는 누구이고, 어느 건의 어느 단계를 맡았나 |
| `get_task` | 이 단계의 목표, 범위, 시간 한도, 끝났다는 조건, 채워야 할 출력 칸. 정해진 조치가 있으면 그 목록 |
| `find_objects`, `get_object`, `get_neighbors` | 범위 안의 객체와 이웃 |
| `get_blast_radius`, `get_changes` | 이 객체가 멈추면 무엇이 멈추나, 최근에 무엇이 바뀌었나 |
| `list_actions` | 이 객체에 이 단계에서 해도 되는 액션: 위험 등급, 승인이 필요한가, 매핑된 툴이 있는가, 받는 입력 칸 |
| `prepare_action` | 객체와 액션과 입력을 주면 **부를 서버, 툴, 채워진 인자**, 승인 상태, 기대 효과, 되돌리는 호출, 유효 시간, 호출 표를 돌려줘요. 승인이 필요하면 요청을 내고 "기다리는 중"이라고 답해요 |
| `get_action` | 준비한 호출의 상태: 승인 기다림, 준비됨, 거절됨, 만료됨, 끝남 |
| `report_action` | 부른 결과를 알려요. 테라리움이 사후 확인을 시작해요 |
| `set_output` | 단계의 출력 칸을 채워요 |
| `complete_step`, `hand_over` | 단계를 끝내거나, 까닭을 적어 사람에게 넘겨요 |

- **에이전트는 인자를 스스로 짓지 않아요.** 에이전트가 정하는 것은 어느 객체에 어느 액션을 할지와 액션의 입력 칸뿐이고, 인자는 툴 매핑이 채워요. 그래야 승인자가 본 호출과 실제 호출이 같고, 툴이 바뀌어도 에이전트를 고치지 않아요.
- 준비한 호출은 한 번만, 정한 시간 안에만 유효해요. 준비한 것과 다른 인자로 부르면 허가증이 맞지 않아요.
- 범위 밖의 객체, 이 단계에 없는 액션, 매핑된 툴이 없는 액션은 까닭과 함께 거절해요.
- 실험용 복사본에서도 같은 툴이 같은 모양으로 답해요. `prepare_action`이 돌려주는 것이 실험의 툴일 뿐이에요. 그래서 검증에서 본 행동이 운영에서의 행동이에요.
- 등록 확인: 테라리움이 다음 동기화에서 자기 서버를 목록에서 찾고, 에이전트가 `whoami`를 한 번 불러 성공하면 확인된 것으로 봐요.

## 8. 시작 조건

닫힌 목록 넷이에요.

| 시작 조건 | 예 | 알아 둘 것 |
|---|---|---|
| 사건 | 운영 세계에 들어온 알람이 조건(객체 타입·종류·심각도)에 맞음 | 동기화 주기만큼 늦어요. 소스가 밀어 줄 수 있으면 받아서 줄여요 |
| 상태 변화 | 동기화가 찾은 차이(용량이 기준을 넘음, 설정이 기준과 달라짐, 만료가 가까움) | 운영 세계의 이력에서 나와요 |
| 일정 | 점검, 패치 시간 | 변경 금지 기간 달력을 지켜요 |
| 사람의 요청 | 양식, API, 티켓 시스템의 웹훅 | 요청한 사람이 기록에 남아요 |

- 알람이 쏟아질 때: 영향 범위가 겹치는 알람은 **한 건**으로 묶어요. 건은 알람이 아니라 뿌리 후보 하나에 대해 열려요.
- 같은 객체에 같은 워크플로는 동시에 한 건만 돌아요. 다른 워크플로가 손대는 중인 객체는 잠겨 있어요.
- 되풀이 방지 시간과 하루 건수 한도를 워크플로마다 둬요. 한도를 넘으면 멈추고 알려요.
- 초 단위로 대응해야 하는 일에는 맞지 않아요. 화면에 그렇게 적어요.

## 9. 범위

건의 범위는 **시작한 객체에서 규칙으로 넓힌 것**이에요. 규칙은 링크 타입과 방향과 걸음 수, 영향 범위, 저장해 둔 객체 묶음, 속성 조건 가운데서 골라요. 단계는 건의 범위를 좁힐 수만 있어요.

- 읽는 범위와 손대는 범위를 따로 둬요. 진단은 넓게 읽고 조치는 좁게 해요.
- 읽기는 테라리움의 MCP 서버가 직접 걸러요. 실제 툴 호출은 `prepare_action`이 범위 안에서만 호출을 준비해 주고, 게이트웨이가 허가증으로 확인해요.
- 범위 밖 시도는 기록하고 알려요. 되풀이되면 건을 멈춰요.
- 객체를 마지막으로 본 때가 오래됐으면(동기화가 밀렸으면) 그 객체에 대한 조치를 준비해 주지 않아요.

## 10. 승인

- **기본값은 위험 등급에서 와요.** 읽기는 승인 없음, 되돌릴 수 있는 것은 승인 한 사람, 되돌릴 수 없는 것은 승인 두 사람. 만드는 사람이 단계마다 고쳐 적지만, 되돌릴 수 없는 액션을 "승인 없음"으로 바꾸는 것은 관리자만 할 수 있어요.
- **승인자는 사람, 무리, 또는 "그 객체를 맡은 조직의 당번"**이에요. 마지막 것은 모델의 담당 링크에서 풀어요. 그래서 다른 조직의 객체에 손대는 단계는 그 조직이 승인해요. 요청한 쪽이 스스로 승인할 수는 없어요.
- **승인 화면이 답하는 것**: 무엇을 하려 하나(액션·대상·툴·인자), 왜(에이전트가 본 것), 이 객체가 멈추면 무엇이 멈추나(영향 범위), **실험용 복사본에서 같은 조치를 미리 돌려 본 결과**, 되돌리는 방법. 누를 것은 승인, 거절(이유), 사람이 직접 하기.
- 승인은 그 호출 한 번, 그 인자에만 유효해요. 시간 한도를 넘으면 기본은 취소예요.
- **승급과 내려감.** 같은 액션 규칙이 승인을 받고 정해 둔 번수만큼 잇달아 성공하면(사후 확인 통과, 되돌림 없음) "스스로 하게 할까요?"를 제안해요. 정하는 것은 사람이에요. 실패나 되돌림이 생기면 저절로 승인 적용으로 내려가요.

## 11. 적용 단계

| 단계 | 에이전트가 하는 것 | 올라가는 조건 |
|---|---|---|
| 초안 | 없음 | — |
| 검증 | 실험용 복사본에서 워크플로를 돌려요. 시작 조건에 맞는 고장을 넣고, 액션은 실험의 툴로 하고, 채점해요 | 정해 둔 상황 수와 번수에서 합격 기준을 넘음. 통과 기록이 버전에 붙어요 |
| 그림자 | 실제 건에서 읽기만 하고 "나라면 이렇게 하겠다"를 내요. 사람이 실제로 한 것과 견줘요 | 일치한 비율과 건수, 검토자의 승인 |
| 승인 적용 | 실제 툴을 부르되 10절의 승인을 받아요 | 승급 제안과 사람의 결정(단계마다) |
| 자율 적용 | 승인 없이 해요(규칙이 허락한 액션만) | — |

- **검증은 갈래마다 해요.** 테라리움이 갈래마다 그 경로를 지나는 시험 상황을 제안하고, 지나서 합격한 갈래만 "검증됨"이 돼요. 운영에서 검증 안 된 갈래에 들어서면 그 건은 사람에게 넘어가요.
- 검증 없이는 그림자로 못 가요. 실험에 흉내가 없는 액션이 든 단계는 승인 적용까지만 가요.
- 배포는 만든 사람이 아닌 사람이 승인해요.
- 이전 버전으로 한 번에 되돌려요. 돌고 있던 건은 시작한 버전으로 끝나요.
- 멈춤 스위치는 워크플로, 에이전트, 전체에 하나씩 있어요.

## 12. 건의 한살이

1. 시작 조건이 맞으면 테라리움이 건을 열고, 첫 단계의 담당 에이전트를 실험 때와 같은 연결 방식으로 불러요. 건 번호와 건 토큰과 MCP 서버 주소를 줘요.
2. 에이전트가 `get_task`로 할 일을 받고, 토폴로지를 읽어요.
3. 조치가 필요하면 `prepare_action`으로 호출을 준비해요. 승인이 필요하면 여기서 기다려요.
4. 준비된 호출을 게이트웨이를 거쳐 그대로 부르고, `report_action`으로 결과를 알려요.
5. 테라리움이 **사후 확인**을 해요. 운영 세계의 다음 동기화에서 기대 효과가 보이는지 봐요.
6. 에이전트가 출력 칸을 채우고 단계를 끝내요. 테라리움이 조건을 따져 다음 블록으로 가요. 사람 단계면 맡은 조직에 알리고 끝 표시를 기다려요.
7. 시간 초과, 거절, 사후 확인 실패는 적어 둔 갈래로 가고, 없으면 사람에게 넘겨요. 되돌리는 액션이 있으면 제안해요.

단계마다 에이전트가 달라도 건의 기록이 문맥이 돼요.

## 13. 권한: 툴은 게이트웨이, 워크플로는 테라리움

권한은 두 층이에요. **에이전트가 어떤 툴을 부를 수 있는가**는 게이트웨이의 일이고, **누가 워크플로를 다루고 무엇이 건을 실행하는가**는 테라리움의 일이에요.

### 다루는 권한
전역 역할은 지금처럼 둘이에요([권한](permissions.md)). 워크플로마다 **맡은 일**을 사람이나 무리에게 줘요.

| 맡은 일 | 할 수 있는 것 |
|---|---|
| 주인 | 맡은 일 나눠 주기, 멈추기, 지우기 |
| 편집 | 초안 고치기, 검증 돌리기 |
| 배포 승인 | 적용 단계 올리기와 되돌리기. 자기가 고친 버전은 승인 못 해요 |
| 시작 | 사람의 요청으로 건을 열기 |
| 단계 승인 | 건 안의 승인 요청에 답하기 |
| 보기 | 건과 지표 보기 |

게이트웨이 연결과 액션 카탈로그는 관리자가 다뤄요. 툴 매핑은 그 툴을 가진 조직의 사람이 만들고 관리자가 배포해요.

### 실행하는 권한
- **에이전트를 단계에 지정하는 것이 실행 권한을 주는 것**이에요. 지정하는 사람이 그 에이전트를 쓸 수 있어야 하고(연결의 공개 범위), 지정은 워크플로 버전에 고정돼요. 버전이 바뀌면 다시 배포 승인을 받아요.
- 에이전트가 테라리움의 MCP 서버를 부를 때마다 **게이트웨이가 넘겨준 신원**과 **건 토큰**을 함께 봐요. 이 에이전트가 이 건의 지금 단계 담당일 때만 답해요. 건이 끝나거나 멈추면 토큰은 죽어요.
- 사람이 시작한 건이라도 에이전트는 워크플로가 정한 범위와 액션 안에서만 움직여요. 시작한 사람이 누구인지는 건에 남아요.
- 건의 기록에는 운영 세계의 내용이 들어 있어요. "보기"를 맡은 사람만 보고, 운영 세계를 볼 수 없는 사람에게는 객체의 내용을 가려요.
- 맡은 일을 바꾸는 것, 배포, 승인, 시작, 멈춤은 모두 감사 기록에 남아요.

## 14. 지켜보기와 알리기

- **건 화면**은 실험의 실행 상세와 같은 틀이에요: 한 일 순서, 어느 갈래로 왜 갔나, 누가 승인했나, 무엇이 바뀌었나.
- **워크플로 화면의 첫 물음 셋**: 잘 돌고 있나(끝까지 간 비율), 어디서 막히나(넘긴 단계, 승인을 기다린 시간), 사람 손이 얼마나 줄었나(지금 하는 방식 표와 견준 단계·사람·시간).
- 함께 세는 것: 갈래마다의 건수, 되돌린 수, 사후 확인 실패, 범위 밖 시도, 준비한 것과 다른 호출, 점검 필요가 된 매핑.
- 지표와 감사 기록은 밖으로 내보내요. 기록에는 비밀과 행의 내용을 넣지 않아요.
- **알림**은 사건 종류(승인 요청, 넘김, 실패, 멈춤, 끝, 범위 밖 시도, 매핑 점검 필요, 승급 제안)와 맡은 일과 채널의 조합이에요. 채널은 일반 웹훅과 메일로 시작하고 메신저는 웹훅 틀로 붙여요. 조용한 시간과 묶어 보내기가 있어요. 승인은 알림 안에서 하지 않고 링크로 들어와서 해요(누가 눌렀는지 확인해야 해서요).

### 성과는 건마다 저절로 재요

워크플로를 만들 때 단계마다 적는 "지금은 누가, 얼마나 걸려서 하나"가 기준이 돼요. 건이 돌 때마다 코드가 기록에서 같은 것을 세서 기준 옆에 놓아요. 사람이 숫자를 적어 넣지 않아요([프로세스 비교](process-compare.md)의 원칙 그대로예요).

| 건마다 세는 것 | 어디서 |
|---|---|
| 처음부터 끝까지 걸린 시간, 단계마다 걸린 시간 | 건의 기록 |
| 사람 손이 간 수: 승인, 넘김, 사람 단계 | 건의 기록 |
| 기다린 시간: 승인을 기다림, 사람 단계를 기다림 | 건의 기록 |
| 에이전트가 쓴 것: 부른 수, 비용 | 건의 기록 |
| 결과: 사후 확인 통과, 되돌림, 사람에게 넘어감 | 건의 기록과 운영 세계의 다음 동기화 |

- **적은 값과 잰 값은 늘 따로 보여요.** 기준은 사람이 믿고 적은 값이라 부풀려질 수 있어요. 그림자 단계에서 사람이 실제로 처리한 건의 시간(티켓이 열리고 닫힌 때)을 소스에서 읽을 수 있으면, 기준을 잰 값으로 바꿔요.
- **기준은 경로마다 있어요.** 갈래에 따라 걸리는 시간이 다르므로 건은 자기가 지난 경로의 기준과 견줘요.
- **재는 것은 자율 적용 전부터예요.** 그림자에서는 "에이전트라면 얼마나 걸렸을까"가, 승인 적용에서는 승인을 기다린 시간이 따로 나와요. 이 숫자가 어느 단계를 자율로 올릴지의 근거가 돼요.
- **모아서 보는 것**: 워크플로마다 기간별 건수, 줄어든 사람 시간(기준과 잰 값의 차이를 모은 것), 사람 손 없이 끝난 비율, 되돌린 비율, 에이전트 비용. 줄어든 시간만 보이지 않게 되돌림과 넘어감을 같은 줄에 둬요.

## 15. 미리 봐 둔 위험

| 위험 | 대응 |
|---|---|
| 알람이나 티켓의 글이 에이전트를 속임 | 글은 데이터로만 다뤄요. 속아도 범위와 액션 목록과 승인 밖으로는 못 나가고, 조건 분기는 글을 읽지 않아요 |
| 테라리움이 멈춤 | 에이전트는 호출을 준비받지 못해 멈추고, 일은 사람 절차로 돌아가요. 그래서 운영 세계의 고가용이 먼저예요 |
| 실제 툴이 실험의 툴과 다르게 움직임 | 그림자 단계와 사후 확인이 잡아요. 어긋난 액션은 승인 적용으로 내려가요 |
| 툴이 바뀜 | 입력 모양 지문, 점검 필요, 내려감(6절) |
| 두 워크플로가 같은 객체에 손댐 | 잠금(8절) |
| 갈래가 많아져 아무도 다 보지 못함 | 경로 목록과 갈래마다의 검증(5절, 11절). 검증 안 된 갈래는 사람에게 가요 |
| 누가 책임지나 | 누가 배포를 승인했고 누가 건을 승인했는지, 어느 에이전트 버전이 했는지가 기록에 남아요 |
| 에이전트 비용 | 건마다 부른 수와 비용을 세고 워크플로마다 한도를 둬요 |
| 기존 변경 관리 절차 | 건이 티켓을 만들고 고치는 액션을 써서 기존 절차에 흔적을 남겨요 |

## 16. 순서

먼저 있어야 하는 것: 권한과 감사 기록, 운영 세계 한 줄, 실험용 복사본, 액션을 모델의 동사 목록으로 드러내기.

그 뒤 얇게 한 줄: 워크플로 하나를 **그림자까지**. 예를 들면 "서버 부품 고장: 진단(에이전트) → 원인에 따라 분기 → 교체 요청(에이전트, 승인) → 교체(사람) → 확인(에이전트)". 그림자에서는 에이전트가 읽기만 하므로 허가증 없이 값이 나와요.

그다음: 허가증, 승인 적용, 승급. "병렬"과 "다른 워크플로 부르기"는 쓰임이 확인된 뒤에 넣어요.

지금 하는 일에 미리 반영할 것은 셋이에요. 감사 기록의 모양에 건과 승인을 넣을 자리를 두고, 권한에 자원마다의 맡은 일을 둘 수 있게 하고, 모델 화면에서 액션을 객체 타입 옆에 보여요.
