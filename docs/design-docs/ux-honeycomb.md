# UX를 숫자로 재는 법 (REQ-041, [ADR-0031](adr/0031-ux-honeycomb-measurement.md))

Peter Morville의 UX Honeycomb 7개 면을 각각 0~100점으로 자동 측정한다. 실제 브라우저(Playwright, Chromium)에서 서버를
새로 띄우고, 사람이 하는 일을 홈에서부터 그대로 한다. 점수는 `docs/generated/ux-score.json`에 쌓이고 면마다 하한이 있다.

## 쓰는 법

| 명령 | 하는 일 |
|---|---|
| `pnpm ux` | 웹을 빌드하고, 서버와 브라우저를 띄워 재고, 기록을 쓰고, 낮은 항목을 찍어 준다. 5~8분 걸린다. |
| `pnpm ux ratchet` | 마지막 측정에서 2점을 뺀 값으로 면별 하한(`harness/config/ux-floor.json`)을 올린다. 내리지 않는다. |
| `pnpm ux check` | `pnpm check`가 돌리는 검사. 브라우저를 열지 않고 기록만 본다. |

UI를 바꿨다면 `pnpm ux`를 한 번 돌려야 `pnpm check`가 통과한다(기록이 낡으면 `UX004`). 출력에서 100%가 아닌 항목이
"무엇을 고쳐야 하는지"이고, `note:` 줄이 구체적인 화면과 요소를 말해 준다.

## 측정 항목

점수는 면에 속한 항목 점수의 평균이다. 증거가 없는 항목은 0점이다.

| 면 | 항목 | 어떻게 재나 |
|---|---|---|
| 유용함 (useful) | 여정 완수 | 아래 여정 11개를 끝까지 해냈는가 |
| | 오류 없는 화면 | 여정 중 지난 화면에서 콘솔 오류, 잡히지 않은 오류, 실패한 요청이 없었는가 |
| 사용성 (usable) | 손 수 | 여정마다 클릭, 입력, 선택, 키, 끌기 횟수가 예산(`JOURNEY_BUDGETS`) 안인가. 예산의 두 배면 0점 |
| | 잘못된 입력 | 말이 안 되는 크기, 없는 서버룸, 너무 많은 실행 횟수, 빈 이름을 넣으면 바로 이유가 뜨고 막히는가 |
| | 해요체 (`voice`) | 모든 화면의 보이는 글 줄 가운데 한다체·합니다체 문장이 없는 줄의 비율 (REQ-058, [ADR-0050](adr/0050-toss-ux-principles.md)) |
| | 한 가지 행동 (`one-thing`) | 주된 버튼(`btn-primary`)이 보이는 화면이 한 개 이하인 비율 |
| | 버튼 이름 (`buttons`) | 보이는 버튼 이름 가운데 "취소"이거나 한다체 문장인 것이 없는 비율 |
| | 꺼진 버튼의 이유 (`disabled-why`) | 꺼진 버튼이 `title`이나 `aria-describedby`로 이유를 말하는 비율 |
| | 포인터 반응 (`hover`) | 화면마다 앞쪽 버튼 3개에 포인터를 올리면 색, 그림자, 테두리 같은 모양이 바뀌는 비율 |
| 매력 (desirable) | 디자인 토큰 | 스타일시트의 색 값 중 테마 토큰(`:root`) 밖에서 쓴 비율 |
| | 진행 표시 | 세계 생성, 미리 보기, 도는 실험 중에 진행이 보이는가 |
| | 첫 화면 크기와 시간 | 홈이 내려받는 양(700 kB)과 제목이 보일 때까지의 시간(2.5초) 예산 |
| | 3D 장면 | 세계 화면의 캔버스가 비어 있지 않은가 |
| 찾기 쉬움 (findable) | 닿는 길 | 홈에서 안의 링크를 두 번 눌러 화면 10종(목록, 세계, 시나리오, 실험, 실행, 벤치마크, 새 실험)에 닿는가 |
| | 위치 표시 | 화면마다 자기 제목, 본문 제목, 내비게이션에 현재 구역 표시가 있는가 |
| 접근성 (accessible) | axe | 모든 화면을 밝은 테마와 어두운 테마로 axe-core에 걸어 치명 0.2, 심각 0.1, 보통 0.02점씩 깎는다 |
| | 키보드 | 탭과 엔터만으로 메뉴 이동, 실험 시작, 공유 메뉴 열고 닫기, 대화상자 열고 닫기(초점 복귀), 탭 전환을 하는가 |
| | 보이는 초점 | 탭으로 지나간 칸마다 초점 표시(외곽선이나 그림자)가 있는가 |
| | 누르는 크기 (`targets`) | 보이는 컨트롤(문장 속 링크 제외)의 높이가 32 px 이상이고 너비가 24 px 이상인 비율 |
| | 움직임 줄이기 | 줄이기를 켜면 움직이는 요소가 없는가 |
| 신뢰 (credible) | 오류 화면 | 없는 세계, 시나리오, 실험, 실행, 없는 주소, 서버에 닿지 않을 때가 원인을 말하고 다음 길을 주는가 |
| | 빈 화면 | 비어 있는 목록이 이유와 할 일을 말하는가 |
| | 수치 설명 | 결과 화면의 모든 수치가 글로 무엇인지 밝히는가(마우스 위에서만 뜨는 설명은 인정하지 않는다), 재현되는 결과인지 말하는가 |
| | 단위나 이름이 붙은 숫자 (`units`) | 홀로 놓인 숫자 옆에 무엇을 센 것인지 글이 있거나 표 머리말이 있는 비율 |
| 가치 (valuable) | 결정을 돕는 정도 | 합격률이 첫 화면에 있는가, 조건을 바꿔 다시 돌리는 길이 첫 화면에 있는가, 몇 회 결과인지·오차를 말하는가, 포크가 원본과 견주는 결과를 두 화면 안에 보여 주는가, 실행이 정답과 견주는가, 벤치마크가 순위의 근거를 말하는가 |

## 여정

모두 홈에서 시작해 화면의 버튼만 누른다. 앞 여정이 만든 것을 뒤 여정이 쓴다.

| 여정 | 예산(손 수) | 하는 일 |
|---|---|---|
| build | 8 | 사업장 그대로(작게)로 세계를 만들고, 첫 서버룸에서 랙을 놓고, 되돌린다 |
| design | 8 | 템플릿으로 시나리오를 만들고, 팔레트에서 블록을 끌어다 놓고, 저장한다 |
| author | 8 | 빈 캔버스에서 시작해 "블록 넣기" 한 번으로 에이전트 투입 블록이 줄에 이어지는 것을 보고, 편집기에서 시험지 점검을 돌려 기준선 점수가 나오는 것까지 본다 (REQ-071) |
| run | 6 | 새 실험을 시작하고 결과가 나올 때까지 본다 |
| cancel | 8 | 실행 횟수를 20으로 하고 시작해, 도는 중에 취소한다 |
| share | 5 | 끝난 실험에서 링크를 복사하고, 이름 모르는 사람의 브라우저에서 연다 |
| fork | 6 | 끝난 실험에서 에이전트를 바꿔 다시 돌리고 원본과 견주는 결과를 본다 |
| compare | 4 | 벤치마크에서 줄을 골라 조건을 바꿔 해 보는 화면까지 간다 |
| site | 6 | 작게 시작으로 작은 사업장을 만들고, 팔고 있는 땅을 사서 "팔고 있는 땅이 n곳"이 줄어드는 것을 보고, 되돌린다 |
| build-small | 8 | 작게 시작 → 다음 할 일 칩으로 서버룸 채우기(랙 24대) → 시운전까지 (REQ-077, ADR-0083). 맨 뒤에 둔다 |
| topology | 5 | 화성을 실제 크기로 올려 두고 세계 목록에서 열어 토폴로지를 누른다. **타일이 150개 이하**이고 **첫 그림이 3초 안에** 나오는지 재고, 층(전원)을 바꾸고, 접힌 묶음 하나를 펼친다 (REQ-078). 끝나면 그 세계를 숨긴다. 맨 뒤 여정이다 |

## 코드 위치와 고치는 법

- `harness/src/ux/score.ts`: 항목과 예산, 점수 계산, 측정 파일 읽기. 측정이 바뀌면 이 문서의 표도 함께 바꾼다.
- `harness/src/ux/check.ts`, `run.ts`: 기록과 하한 검사(`UX001`~`UX005`), 명령.
- `tests/e2e/ux/`: 브라우저에서 세는 쪽. `journeys.ts`(여정), `probes-*.ts`(나머지 측정: 말투는 `probes-voice.ts`, 작은 부분은 `probes-detail.ts`), `measure.ts`(조립).
- 새 화면이나 새 여정을 더하면 측정에도 더한다. 측정하지 않는 화면은 점수에서 보이지 않을 뿐 좋은 것이 아니다.

## 기계가 재지 못하는 것 (사람이 확인한다)

ADR-0050의 디테일 표 가운데 이것들은 기계가 재지 못한다. 화면을 바꿀 때마다 훑는다: 쉬운 말인가(전문 용어에 한 줄 풀이가 있는가), 한 문장이 두 줄 안인가, 날짜·시간이 "10월 29일", "3분 전"처럼 말하는가, 지우는 일이 확인하거나 되돌릴 수 있는가.
