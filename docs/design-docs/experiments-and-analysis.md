# 실험과 결과 분석 (REQ-015, REQ-030~033, REQ-037~040)

## 한 문장으로

**실험은 "시험지 한 장을 같은 조건으로 여러 번 풀게 한 것"이고, 분석은 그 답안지들을 모아 채점·비교·공유하는 일이다.**

## 실험 (`core.experiments`)

- **레시피** = 세계 × 시나리오 × 하네스 × 에이전트 × 툴 + 시드 목록 + 시간 정책 + 제품 버전(vCenter·vROps).
  시드 하나가 실행(run) 하나다. 기본 시드는 1, 2, 3이고 최대 20개다. 같은 시드는 같은 세계 흐름을 만든다(결정론).
- **스냅샷**: 실험을 만들 때 세계와 시나리오의 digest를 적어 둔다. 나중에 누가 세계를 고쳐도 이 실험은 자기가 돌린 것을 가리킨다.
- **실행 상태**: 대기 → 실행 중 → 완료 / 실패 / 취소. 허용되지 않는 전이(완료된 실행을 다시 시작 등)는 `ConflictError`다.
- **포크(REQ-040)**: 실험을 그대로 가져와 조건 일부만 바꾼다. 아무것도 안 바꾸면 거절한다("실행을 추가하라"). 포크는 부모를
  기억하고(`parentId`), 바뀐 점은 `recipeDiff`가 "에이전트 triage → deep" 같은 말로 만든다. 계보는 위(`lineage`)로도
  아래(`forksOf`)로도 따라간다.
- **누가 돌렸나, 어느 버전인가(REQ-052, REQ-053, [ADR-0043](adr/0043-connection-secrets-retention-versions.md))**: 실험은 만든 때의 하네스·에이전트 정보(`subject`)와 사람이 붙인 메타데이터를 그대로 지닌다.
  또 에이전트가 스스로 밝힌 정보가 가장 새 버전과 다르면 새 버전(`agent-version.ts`)을 쓰고 실험에 그 번호(`agentVersion`)를 붙인다. 앞 버전과의 차이는 저장하지 않고 견주어 만든다(이름·모델·사실·연결 메타데이터·사람이 붙인 속성).
  번호는 오르기만 하고 다시 쓰이지 않는다. 포크는 부모의 에이전트가 아니라 지금 에이전트를 본다.
- **스케줄러(REQ-032)**: [ADR-0024](adr/0024-fair-scheduling.md). 지금 가장 적게 돌리고 있는 사람의 실행부터, 서버·사람·하네스 한도 안에서.
- **저장소 포트**: `ExperimentStore`. 메모리 구현(`MemoryStore`)은 테스트와 기본값, 서버는 SQLite 구현을 쓴다.

## 분석 (`core.analysis`)

결과는 세 출처를 합친다(REQ-037).

| 출처 | 무엇 | 없으면 |
|---|---|---|
| 오라클 채점 | 점수, 항목별 판정, 정답(`facts`) | 없을 수 없다 (테라리움이 채점) |
| 테라리움 툴 호출 기록 | 무엇을 언제 불렀나, 실패, 세계를 바꾼 행동 | 없을 수 없다 |
| 하네스 텔레메트리 (ClickStack) | 모델 호출, 토큰, 비용, 실제 걸린 시간 | 해당 칸이 비고 나머지는 그대로 |

- **실행 하나**(`analyzeRun`): 진단이 맞았나(원인 장비·고장 유형 따로), 진단까지 시뮬레이션 시간, 정답 장비를 처음 들여다본 시점,
  같은 호출 반복, 실패한 호출, 금지 행동. 발견(findings)은 근거를 가리키는 한국어 문장이다("정답 장비(crah-1)를 한 번도 직접 살펴보지 않았다").
- **실험 하나**(`analyzeExperiment`): 완료된 실행만으로 합격률·진단 정확도·평균 점수(±95% 구간)·항목별 달성률을 낸다.
  실패·취소는 진행률에서 따로 센다. 포크면 원본과 비교한다.
- **"분명한 차이"**: 두 평균의 95% 구간이 겹치지 않을 때만. 실행 1번끼리는 절대 아니다. [ADR-0023](adr/0023-benchmark-sets-and-comparison.md).

## 벤치마크 대시보드 (REQ-039)

같은 **벤치마크 세트**(같은 시험지: 세계·시나리오 digest, 오라클 버전, 시간 정책, 제품 버전)끼리만 줄 세운다. 한 줄은 하네스 × 에이전트 ×
툴 집합이고, 여러 사람의 실험이 합쳐진다. 완료된 실행이 3번 이상이어야 순위를 받는다. 정렬은 평균 점수 → 합격률 → 진단 시간 → 호출 수.

## 공유 (REQ-038)

- `renderText`: 채팅에 붙여 넣는 몇 줄.
- `renderMarkdown`: 위키·이슈용. 표 안의 `|`는 이스케이프한다.
- `renderHtml`: 파일 하나로 끝나는 보고서. 스크립트·외부 파일이 없어 어디서나(오프라인, 메일 첨부) 같은 모습으로 열리고, 밝은/어두운 테마와
  인쇄를 지원한다. 에이전트가 쓴 요약 같은 바깥 글은 모두 이스케이프한다. 대표 실행의 지표를 작은 선 그래프로 넣을 수 있다.
- 링크 공유는 서버가 만든다(읽기 전용 토큰).

## 디지털 트윈 쪽으로 (REQ-015)

- **진단 기록**(`diagnosisRecords`): 완료된 실행마다 한 줄 — 실제 고장, 에이전트의 답, 맞았는지, 걸린 시간, 툴 오류. 스키마 이름은
  `terrarium.diagnosis/1`이고 JSON Lines(`toJsonl`/`fromJsonl`)로 내보낸다. 다른 도구에서 메타 분석할 때 쓴다.
- **모델링 브리프**(`modelingBrief`): 시뮬레이터를 고치는 에이전트에게 넘기는 Markdown.
  1. 고장 유형별 정답률(낮은 순)과 자주 헷갈린 답 — 여러 에이전트가 함께 틀리면 시뮬레이터가 단서를 덜 만드는 것일 수 있다.
     5번 넘게 모두 맞히면 너무 쉬운지 의심한다.
  2. 툴 오류를 메시지 모양으로 묶은 것(id와 숫자는 지운다) — 에이전트가 기대했지만 시뮬레이터가 못 하는 동작의 후보.
  3. 가져온 세계에서 매핑하지 못한 라벨·관계와 가정 — 실제 구성 중 세계에 빠진 것.
