# 생김새 견본 시험 (REQ-115 예정, ADR-0161)

[현실 데이터와 모델](reality-data-and-ontology.md)이 "커넥터보다 먼저 견본으로 시험한다"고 정한 그 시험이에요. 코드는 없고 종이 위에서 했어요.

## 한 줄로

여덟 가지 생김새를 설계에 넣어 봤어요. 뼈대(네 단, 줄과 열의 표, 잇는 틀 다섯, 근거 등급 셋)는 버텼어요. 막힌 곳은 열아홉 군데였고, 모두 "모양을 하나로 좁히는 일"에 적지 않은 빈칸이었어요. ADR-0161으로 메웠어요. 받지 못하는 모양 셋은 화면이 이름을 대고 나가는 길을 알려 줘요.

## 어떻게 했나

- 견본은 열 이름과 겹침 구조만 본뜬 **지어낸** 데이터예요. 실제 데이터는 이 저장소에 없어요.
- 견본마다 같은 물음을 차례로 던졌어요: 받은 그대로가 표가 되나 → 손질로 목적지 모양이 되나 → 다른 소스의 같은 것을 알아보나 → 규칙이 선을 잇나 → 이중화(묶음)가 적히나.
- 막히면 설계가 틀린 곳으로 적었어요. 견본을 설계에 맞게 고치지 않았어요.
- 제품 API의 자세한 모양은 설계 담당이 아는 대로 적었어요. 프리셋을 만들 때 제품 문서와 하나씩 대조해요.

| 견본 | 본뜬 생김새 | 역할 |
|---|---|---|
| 1 | 엑셀 랙 위치 대장 (양식이 아닌 것) | 구성 |
| 2 | 엑셀 전원 계통 | 구성 |
| 3 | 엑셀 냉방 계통 | 구성 |
| 4 | Splunk의 SPL 결과 | 구성·사건·실측 |
| 5 | vROps의 자원과 관계 | 구성 |
| 6 | VMware vCenter의 목록 API | 구성 |
| 7 | OpenStack (컴퓨트·네트워크·블록 스토리지) | 구성 |
| 8 | 스위치의 포트·포트 묶음·이웃·BGP 세션 (OpenConfig 모양, 이웃 표) | 구성 |

## 견본마다 걸어 본 것

### 1. 엑셀 랙 위치 대장

```
     A         B     C      D            E        F        G
1  | 위치                 | 장비                          | 전원     |   ← 합친 칸
2  | 전산실    열    랙   | 장비명       종류     U위치   | 용량     |
3  | 전산실 A  A열   A03  | esx-a03-01   서버     12-13   | 0.8kW    |
4  |                      | sw-a03-t1    스위치   42      | 0.3kW    |   ← 빈 칸은 "위와 같음"
5  |                      | PP-A03-1     패치패널 44      |          |
.. | 합계                                                 | 1.1kW    |
```

- 머리 줄이 두 줄이고 칸이 합쳐져 있어요. 세로로 합친 "전산실 A"는 여러 줄을 덮어요. 합계 줄이 섞여 있어요. → **막힘 1**
- 합친 칸이 아닌 빈 칸을 "위와 같음"으로 쓰는 사람의 버릇이 있어요. → **막힘 6**(위 값 잇기)
- "12-13", "U12~13", "0.8kW"는 나누기와 단위 바꾸기로 돼요. 못 읽는 줄은 문제 목록으로 가요. 버텼어요.
- 방·열·랙은 자기 표가 없어요. 장비 줄의 열로만 나와요. 대응의 미리 보기는 겹친 키를 문제로 본다고 적혀 있어서, 랙 하나가 줄 40개에 나오면 문제 40건이 돼요. → **막힘 8**
- 한 시트에 서버·스위치·패치 패널이 "종류" 열로 섞여 있어요. 값은 조직의 말이에요("L4", "방화벽"). → **막힘 9**
- 패치 패널, KVM, 다른 부서 장비는 모델의 종류에 없어요. 버리면 랙의 빈 자리와 전력 합이 틀려져요. → **막힘 10**
- 랙 이름 "A03"은 방마다 있어요. 키는 (방, 랙)으로 묶어야 하고, 장비가 랙을 가리킬 때도 묶은 키로 가리켜요. → **막힘 13**
- 엑셀은 "esx-a03-01", 가상화 관리자는 "esx-a03-01.dc.example.internal", 감시 도구는 "ESX-A03-01"이에요. 글자 그대로 견주면 세 개체가 돼요. → **막힘 12**
- **못 받는 모양**: 랙을 그림처럼 그린 실장도(열이 랙, 줄이 U, 칸이 장비 이름, 여러 U는 합친 칸). 줄로 펼칠 수는 있지만, 한 장비의 여러 줄을 "U 12부터 2칸"으로 모으는 손질이 없어요. → **막힘 7**

### 2. 엑셀 전원 계통

```
설비명      종류      상위 설비    계통   용량
TR-1        변압기    수전-1       A      2000kVA
UPS-A       UPS       TR-1         A      500kVA x 3 (N+1)
PDU-2F-A1   분전반    UPS-A        A      250A

랙     A계통 분전반/차단기    B계통 분전반/차단기
A03    PDU-2F-A1 / 12         PDU-2F-B1 / 12
```

- "상위 설비"는 같은 표의 다른 줄을 가리키는데, 가리키는 것의 종류가 줄마다 달라요(변압기, UPS, 분전반). → **막힘 14**
- 랙 표는 A·B가 옆으로 나란해요. 규칙 둘(A 열, B 열)에 역할을 하나씩 못박으면 돼요. 버텼어요.
- 서버의 전원 장치가 랙의 어느 콘센트에 꽂혔는지는 엑셀에 거의 없어요. 관례 틀("랙의 서버는 그 랙의 A·B에")이 가정 등급으로 메워요. 전원 장치가 하나뿐인지 모르는 장비는 "모름"이에요. 버텼어요.
- "500kVA x 3 (N+1)"은 사람이 읽는 글이에요. 묶음에서 몇 개가 살아야 하는지는 선의 수에서 나오지 않아요. → **막힘 16**

### 3. 엑셀 냉방 계통

```
설비명        종류     방         담당 구역     냉수 계통
CRAH-2F-A-1   항온기   전산실 A   A열~D열       1차
CH-1          냉동기   기계실     -             1차 (N+1)
```

- 냉방은 장비에서 장비가 아니라 설비에서 공간(방·열)으로 이어져요. 랙은 자기가 놓인 공간을 거쳐 받아요. 담김 틀과 관계 표의 "공급받는다"로 돼요. 버텼어요.
- **못 받는 모양**: "A열~D열"처럼 범위를 한 칸에 적은 것. 나누기는 A와 D를 꺼낼 뿐 B와 C를 만들지 못해요. → **막힘 7**
- N+1의 N은 전원과 같아요. → **막힘 16**

### 4. Splunk의 SPL 결과

```
index=net sourcetype=lldp | stats latest(remote_port) as remote_port by host, local_port, remote_host

host    local_port     remote_host        remote_port
sw01    Ethernet1/1    SW02.corp.local    Eth1/49
sw01    Ethernet1/2    10.20.0.7
```

- 검색 하나가 표 하나라는 틀이 그대로 맞아요. 여러 값이 든 칸은 줄로 펼치면 돼요. 버텼어요.
- 값이 없는 칸은 줄에서 빠지고, 어느 줄에도 값이 없으면 그 열이 통째로 안 와요. "열이 사라지면 멈춘다"가 거짓 경보를 내요. → **막힘 5**
- 사건에서 뽑은 구성은 "그 시간 범위에 말한 것"이에요. 하루 조용했던 장비가 사라져 보여요. 세 번 안 보여야 지우는 안전장치와 10% 사라짐 멈춤이 막아요. 검색의 시간 범위를 동기화 주기의 세 배보다 길게 잡으라고 화면이 권해요. 버텼어요.
- 이웃이 이름이 아니라 IP로만 와요("10.20.0.7"). IP 하나로 장비를 알아봐야 하는데, 장비는 IP를 여럿 가져요. → **막힘 13**
- "Ethernet1/1"과 "Eth1/49"는 같은 표기법의 두 얼굴이에요. → **막힘 12**
- 한도에 닿아 잘린 결과는 적용하지 않고 멈춰요(소스 관리 10절). 버텼어요.

### 5. vROps의 자원과 관계

```
자원:   identifier, resourceKey.name, resourceKey.adapterKindKey, resourceKey.resourceKindKey,
        resourceKey.resourceIdentifiers[] = { identifierType.name, value }
관계:   자원 하나마다 따로 묻거나 여럿을 한 번에 물음 → (부모 identifier, 자식 identifier)
```

- `resourceIdentifiers`는 이름·값 줄의 목록이에요. 자식 표로 펼치면 세로로 긴 표가 되고, 대응이 쓰려면 이름마다 열이 되어야 해요. 다섯 손질에는 그 반대(가로를 세로로)만 있어요. → **막힘 6**(열로 모으기)
- 관계에 종류가 없어요. 부모·자식뿐이고, 뜻은 양 끝의 자원 종류에서 나와요(호스트 → VM이면 "위에서 돈다", 클러스터 → 호스트면 "묶인다"). → **막힘 14**
- 어느 규칙도 집지 않은 관계 줄이 얼마나 남았는지 보이지 않으면, 못 읽은 것이 조용히 사라져요. → **막힘 11**
- 관계는 자원마다 따로 물어야 와요. → **막힘 2**
- vROps의 identifier는 vROps 안에서만 쓰는 번호예요. 다른 소스와 맞추는 키는 펼친 식별자 둘(가상화 관리자의 ID + 그 안의 개체 ID)을 묶은 것이에요. → **막힘 13**

### 6. VMware vCenter의 목록 API

```
VM 목록:    vm, name, power_state, cpu_count, memory_size_MiB        ← 어느 호스트인지 없음
호스트의 VM: VM 목록을 "이 호스트의 것만"이라는 조건으로 다시 물음
VM 상세:    nics = { "4000": { mac_address, backing: { type, network } }, ... }   ← 이름이 키인 묶음
            disks = { "2000": { backing: { vmdk_file: "[ds1] vm/vm.vmdk" }, capacity } }
```

- VM이 어느 호스트에 있는지는 응답의 열이 아니라 **요청의 조건**에 있어요. 호스트마다 묻고, 물을 때 쓴 호스트를 결과의 열로 붙여야 관계가 생겨요. → **막힘 2**
- `nics`와 `disks`는 배열이 아니라 번호가 키인 묶음이에요. "겹친 것은 자식 표로"가 배열만 말하고 있었어요. → **막힘 3**
- "[ds1] vm/vm.vmdk"에서 데이터스토어 이름은 패턴으로 나누면 나와요. 버텼어요.
- 물리 NIC가 어느 가상 스위치의 윗길인지, 그 NIC의 이웃 스위치 포트가 무엇인지는 이 목록 API에 없고 XML로 묻는 옛 API에만 있어요. → **막힘 4**
- vSAN은 호스트의 디스크로 만든 스토리지예요. 호스트 몇 대를 잃어도 되는지는 정책의 값이에요. → **막힘 16**

### 7. OpenStack

```
서버:    id, name, OS-EXT-SRV-ATTR:hypervisor_hostname, OS-EXT-AZ:availability_zone,
         addresses = { "net-a": [ { addr, OS-EXT-IPS-MAC:mac_addr } ] },
         os-extended-volumes:volumes_attached[] = { id }
포트:    id, network_id, device_id, device_owner, fixed_ips[] = { subnet_id, ip_address }, binding:host_id
무리:    애그리거트 = { name, availability_zone, hosts[] }
```

- `addresses`는 네트워크 이름이 키인 묶음이에요. → **막힘 3**
- 포트의 `device_id`는 `device_owner`에 따라 서버를 가리키기도 하고 라우터를 가리키기도 해요. → **막힘 14**
- 호스트 하나가 애그리거트 여럿에 들어요. 가용 영역은 하나예요. 애그리거트는 배치할 때 쓰는 꼬리표이지 "고장 나면 여기서 다시 뜬다"는 뜻이 없어요. 표준 모델 대조 문서의 대응 표가 애그리거트와 가용 영역을 모두 `cluster`에 맞춰 둔 것은 틀렸어요. → **막힘 17**
- 호스트 이름과 배치 정보는 관리자 역할에게만 보여요. 읽기만 하는 역할이 없는 판의 클라우드에서는 "읽기 전용 계정이어야 잇는다"를 지킬 수 없어요. → **막힘 19**
- 같은 구성을 VMware 모양과 OpenStack 모양으로 넣으면 같은 종류·같은 관계가 되는지는 17을 고치면 돼요.

### 8. 스위치의 포트·묶음·이웃·세션

```
포트:    장비, name, 속도, 묶음 번호(aggregate-id), 설명
묶음:    장비, name(Port-Channel10), lacp 방식, min-links, 짝 묶음 번호(두 스위치에 걸친 것)
이웃:    장비, 내 포트, 상대 장비 표시(이름 또는 MAC), 상대 포트 표시(이름 또는 MAC 또는 번호)
세션:    장비, 이웃 주소(IP), 이웃 AS, 무리(peer-group)
```

- 포트·묶음·세션이 장비에 딸린 줄로 들어오는 것은 ADR-0156 2번 그대로예요. 버텼어요.
- 포트에도 갈래가 있어요: 물리 포트, 하나를 넷으로 쪼갠 포트, 묶음, 하위 인터페이스, 루프백. 묶음과 하위 인터페이스는 아래의 포트에 얹혀요. 딸린 줄에 갈래와 "아래 포트"를 적을 칸이 없었어요. → **막힘 18**
- 이웃 표는 상대를 이름으로도, MAC으로도, 번호로도 말해요. 이름은 표기가 달라요("Ethernet1/1", "Eth1/1", "Et1/1"). → **막힘 12, 13**
- 같은 선을 양쪽이 한 번씩 말해요. 한쪽만 말하기도 하고(서버는 말이 없음), 둘이 어긋나기도 해요. 상대가 모델에 없는 장비이기도 해요. → **막힘 15**
- BGP 세션의 상대는 IP예요. 그 IP가 어느 장비의 어느 포트인지 찾아야 세션이 선 위에 얹혀요. → **막힘 13**
- LACP는 `min-links`가 "몇 개가 살아야 하나"를 직접 말해요. 두 스위치에 걸친 묶음은 짝 묶음 번호가 같은 것끼리 한 무리예요. 묶음 틀의 키를 (짝 영역, 번호)로 묶으면 돼요. 버텼어요.
- ECMP가 켜져 있는지와 누가 구성원인지를 어디서 읽을지 정해 두지 않았어요. → **막힘 16** (답: 장비 설정이에요. 같은 이웃 무리의 BGP 세션들이 구성원이고, "여러 경로를 몇 개까지 같이 쓰는가"가 2 이상이면 ECMP예요. ADR-0164)

## 막힌 곳과 고친 것

| # | 단 | 막힌 것 | 고친 것 (ADR-0161) |
|---|---|---|---|
| 1 | 수집 | 엑셀의 두 줄 머리, 합친 칸, 합계 줄 | 파일 커넥터의 읽기 설정: 머리 줄 범위, 합친 칸은 덮는 칸 모두의 값, 데이터가 끝나는 곳 |
| 2 | 수집 | 관계가 요청의 조건에 있거나 자원마다 따로 물어야 옴 | HTTP 커넥터의 **딸린 요청**: 앞 표의 줄마다 요청하고, 요청에 쓴 값을 결과의 열로 붙여요. 요청 수에 한도 |
| 3 | 수집 | 이름이 키인 묶음, 줄마다 JSON 한 덩이 | 받은 그대로로 펼치는 규칙에 더해요(키는 열 하나가 돼요) |
| 4 | 수집 | XML로만 묻는 API | 받지 않아요. 같은 내용을 vROps 프리셋이나 밀어 넣기로 받아요 |
| 5 | 수집 | SPL 결과에서 빈 열이 통째로 빠짐 | 검색을 저장할 때 기대하는 열을 적어 둬요. 빠진 열은 "모두 빈 값"이고, 멈출지는 필수 속성과 사라짐 안전장치가 정해요 |
| 6 | 손질 | 다섯 가지로 모자라고 "붙이기"가 두 뜻 | 여덟 가지로 이름을 못박아요(아래 표) |
| 7 | 손질 | 실장도 격자, 범위를 적은 칸 | 모으기와 범위 펼치기는 넣지 않아요. 화면이 모양을 알아보고 목록 양식을 안내해요 |
| 8 | 대응 | 여러 줄이 한 개체 | 대응에 "줄마다 하나"와 "값마다 하나"를 둬요. 값마다 하나에서는 겹친 키가 정상이고, 줄 사이에 속성이 어긋나면 문제예요 |
| 9 | 대응 | 한 표에 여러 종류, 조직의 말 | 고르기와 값 사전. 사전에 없는 값은 목록으로 |
| 10 | 대응 | 모델에 없는 장비 | 현실 표준 종류 "기타 실장 장비": 자리와 전력만 있고, 여기에 기대는 것은 없어요 |
| 11 | 대응 | 아무도 집지 않은 줄 | "어느 대응·규칙에도 안 쓰인 줄 N개"를 종류 짝별로 내요 |
| 12 | 알아보기 | 표기가 다른 같은 이름 | 정해진 다듬기로 견줘요: 대소문자, 앞뒤 공백, 도메인 꼬리, 포트 이름. 원래 값은 그대로 둬요 |
| 13 | 알아보기 | IP·MAC처럼 여럿인 키, 어떤 범위 안에서만 유일한 키 | 여러 값 속성은 "하나라도 같으면", 범위가 있는 키는 묶은 키로 |
| 14 | 규칙 | 가리키는 상대의 종류가 줄마다 다름 | 규칙에 양 끝의 종류 조건을 둬요. 둘 이상에 맞으면 잇지 않고 목록으로 |
| 15 | 규칙 | 양쪽이 말하는 선, 한쪽만 말하는 선, 모델 밖 이웃 | 한 번만 잇고 "양쪽·한쪽"을 적어요. 어긋나면 잇지 않아요. 모델 밖 이웃은 숫자로 내요 |
| 16 | 묶음 | "몇 개가 살아야 하나"의 출처 | 소스가 말하면 사실, 종류의 기본값이면 가정, 기본값이 없으면 모름. ECMP는 장비 설정에서 읽어 사실이고, 이웃 무리가 설정에 없어 역할로 묶었을 때만 가정(ADR-0164) |
| 17 | 모델 | OpenStack 애그리거트를 `cluster`에 맞춤 | 대응 표를 고쳐요: 가용 영역은 호스트 무리, 애그리거트는 호스트의 꼬리표, 인스턴스 HA 구역이 자동 재배치를 켠 무리 |
| 18 | 모델 | 포트의 갈래와 층 | 딸린 줄에 갈래와 "아래 포트" 칸 |
| 19 | 읽기 전용 | 읽기만 하는 역할이 없는 소스 | 규칙은 그대로예요(잇지 않아요). 길은 밀어 넣기예요 |

### 손질은 여덟 가지예요

| 손질 | 하는 일 | 견본 |
|---|---|---|
| 줄로 펼치기 | 한 칸의 여러 값, 옆으로 늘어선 열을 줄로 | 4, 5 |
| 열로 모으기 | 이름·값 줄을 이름마다 열로 | 5 |
| 나누기 | 구분자, 자리, 패턴으로 한 칸을 여러 열로 | 1, 6 |
| 옆으로 붙이기 | 키가 같은 두 표의 열을 합침 | 5, 7 |
| 아래로 쌓기 | 열이 같은 표들을 한 표로 | 8 |
| 고르기 | 조건에 맞는 줄만 | 1, 7 |
| 위 값 잇기 | 빈 칸을 위의 값으로 | 1 |
| 값 바꾸기 | 단위, 값 사전, 다듬기 | 1, 2 |

코드는 여전히 못 넣어요. 여덟 가지로 안 되면 바깥에서 손질해 밀어 넣어요.

## 설계가 버틴 곳

- **네 단과 "받은 그대로"**: 여덟 견본 모두 줄과 열의 표로 내려앉았어요(막힘 3을 더한 뒤).
- **잇는 틀 다섯**: 새 틀이 필요하지 않았어요. 모자란 것은 틀의 조건과 뒷정리였어요(14, 15).
- **근거 등급 셋**: 엑셀에 없는 콘센트 연결, 기본값으로 채운 묶음, 역할에서 끌어낸 ECMP가 모두 "가정"에 들어가요.
- **같은 것 알아보기가 첫걸음**: 여덟 견본 모두 다른 소스의 같은 장비나 같은 자리와 맞춰야 했어요.
- **안전장치**: 사건에서 뽑은 구성의 빈틈(4)을 이미 있는 것들이 막아요.

## 못 받는 모양과 나가는 길

| 모양 | 화면이 하는 말 | 나가는 길 |
|---|---|---|
| 실장도 격자 | "이 시트는 랙 그림처럼 보여요" | 목록 양식으로 옮겨 올리기 |
| 범위를 적은 칸 | "이 칸은 범위예요. 하나씩 적어야 읽어요" | 냉방·전원 양식(구역마다 한 줄) |
| XML로만 묻는 API | 프리셋에 없음 | vROps 프리셋, 밀어 넣기 |

실장도 격자를 직접 읽는 기능은 만들지 않아요. 위치 엑셀은 한 줄에 장비 하나인 목록으로 와요(ADR-0164).

## 만들 때의 시험

| 시험 | 내용 |
|---|---|
| 견본 | 이 문서의 여덟 견본을 지어낸 파일로 두고, 각각 수집 → 손질 → 대응 → 규칙을 돌려 기대한 개체·선·문제 목록이 나온다 |
| 합 | 받은 줄 수 = 개체가 된 줄 + 선이 된 줄 + 문제 목록 + 안 쓰인 줄 (견본마다) |
| 다듬기 | 표기만 다른 이름이 한 개체가 되고, 다듬어도 다른 이름은 합쳐지지 않는다 |
| 양쪽 | 양쪽이 말한 선은 하나이고, 어긋난 선은 이어지지 않는다 |
| 묶음의 출처 | 살아야 하는 수가 소스에 있으면 사실, 기본값이면 가정, 없으면 모름으로 적힌다 |
| 같은 세계 | 같은 구성의 VMware 모양과 OpenStack 모양이 같은 종류·같은 관계의 세계가 된다 |
