# 테라리움 요구사항

테라리움은 사내 Agent/Harness를 평가하기 위한 **스테이트풀 IT 인프라 시뮬레이터이자 실험 플랫폼**이다.
이 문서는 요구사항의 단일 출처다. 모든 요구사항은 `REQ-NNN` ID를 가지며, 테스트는 제목에 `[REQ-NNN]`을 넣어
요구사항을 가리킨다. 테스트가 없는 요구사항은 CI에서 실패한다(`TRACE001`). 요구사항을 바꾸려면 ADR이 필요하다.

## 시뮬레이터

| ID | 요구사항 |
|---|---|
| REQ-001 | 월드는 상태를 가진다. 시간이 흐르고 이벤트가 일어나면 상태가 변하고, 같은 입력(시드 포함)이면 같은 결과가 나온다. |
| REQ-002 | 서버는 Redfish 스키마와 목업 문서를 기반으로 에뮬레이트한다. |
| REQ-003 | 파사드는 Redfish/vCenter/vROps 요청·응답 모양을 월드 중립 명령과 주고받는 번역+렌더 계층이다. 파사드는 웹 프레임워크를 모른다. |
| REQ-004 | 프로파일은 제품(버전)별 동작 변형을 담고, 장비 모델별 차이는 모델 카탈로그가 담는다. 둘은 섞이지 않는다. |
| REQ-005 | 데이터센터 시설(냉각, 전력, 공조, 분전반)이 월드에 존재하고 IT 장비 상태에 영향을 주고받는다. |
| REQ-006 | 웹 UI로 월드를 3D로 볼 수 있다. |
| REQ-007 | 실험 때 에이전트가 호출하는 툴(API)이 있다. 벤치마크·채점은 시뮬레이터 내부를 건드리지 않고 이 툴과 기록만 사용한다. |
| REQ-008 | 파사드는 월드를 포트 뒤에서 읽고 쓴다. 같은 포트로 현실 장비 API(읽기 전용)를 연결할 수 있다. |
| REQ-009 | 월드 생성기(worldgen)가 프리셋·파라미터로부터 월드를 만든다. |
| REQ-010 | (폐기, ADR-0084) 현실 세계 가져오기(realimport)는 없앤다. 베타 사용자가 "내 장비 목록으로 실험하고 싶다"고 실제로 요청할 때 ADR-0084의 조건(JSON Schema 교환 형식, 안정 ID와 출처, 차이 반영, 파일 어댑터 먼저)으로 다시 설계한다. |
| REQ-011 | realimport는 현실을 읽기만 한다. 현실 장비를 제어하지 않으며 어디까지나 시뮬레이션용이다. |
| REQ-012 | 공간 계산은 독립 모듈이며 worldgen과 realimport가 함께 소비한다. 둘은 서로를 모른다. |
| REQ-013 | 도면이 없어도 랙/서버/스토리지/스위치의 위치 프로퍼티(타입별로 값 형식이 다름)에서 좌표계를 만든다. |
| REQ-014 | 장애를 주입할 수 있고, 월드 스냅샷과 리셋이 가능하다(반복 실행용). |
| REQ-015 | 디지털 트윈을 향한 확장: 에이전트의 진단 결과를 쌓고, 메타 분석용으로 내보내고, 모델링 정보를 정리해 시뮬레이터 개발용 에이전트에 넘길 수 있다. |

## 실험 플랫폼

| ID | 요구사항 |
|---|---|
| REQ-030 | 사람이 하네스 × 에이전트 × 툴 조합으로 실험을 만들고, 실행하고, 취소하고, 결과를 확인할 수 있다. |
| REQ-031 | 하네스는 인터페이스 계층(어댑터)을 통해 어떤 하네스든 연결한다. 에이전트는 그 하네스에 만들어진 것 중에서 고르고, 툴은 테라리움이 제공하는 것 중에서 고른다. |
| REQ-032 | 여러 사람이 실험을 매우 많이 만들어도 동시에 돌 수 있다. 스케줄러가 사용자 간 공정하게 자원을 나눈다. 기준 자원은 8 vCPU / 64 GB DRAM이며, 한도는 측정으로 정한다. |
| REQ-033 | 실험의 세계는 새로 만들거나 기존 세계를 가져온다. 시나리오는 새로 구성하거나 기존 것을 고른다. |
| REQ-034 | 시나리오는 노코드 워크플로처럼 드래그 앤 드롭으로 설계한다. 시뮬레이터가 지원하지 않는 블록은 쓸 수 없고, 이유가 보인다. |
| REQ-035 | 세계는 타이쿤 게임처럼 건설한다: 부지(기흥/화성/온양/천안/수원/평택 사업장) → 건물 → 층 → 서버룸 → 컨테인먼트 → 랙 → 장비, 그리고 설비·케이블·분전반·전원. |
| REQ-036 | 3D는 가벼워야 한다(성능 예산을 기계가 확인한다). 디자인은 타이쿤 느낌이다. |
| REQ-037 | 실험 결과는 오라클 채점, 하네스의 트레이스·메트릭·로그(ClickStack), 테라리움 툴 호출 기록을 종합해 분석한다. |
| REQ-038 | 결과는 링크, HTML, 텍스트 복사로 쉽게 공유한다. |
| REQ-039 | 여러 사람의 실험을 비교하는 벤치마크 대시보드가 있다. 같은 조건(벤치마크 세트)끼리만 순위를 매긴다. |
| REQ-040 | 실험을 그대로 가져와 하네스/에이전트/툴 조건만 바꿔 바로 다시 돌릴 수 있다. 원본과의 차이와 계보가 보인다. |
| REQ-041 | UX는 Honeycomb 모델(useful, usable, desirable, findable, accessible, credible, valuable)로 정량화하고, 계속 측정해 점수가 떨어지지 않게 한다. |
| REQ-058 | UX는 이 제품의 가장 중요한 품질이다. 화면은 토스의 UX 원칙을 따른다: 한 화면에 한 가지를 하게 하고(One Thing), 다음 할 일이 한눈에 보이고(Clear Action), 쉬운 말을 쓰고(Casual Concept), 이유를 말하고(Explain Why), 답하기 쉽게 묻고(Easy to Answer), 얻는 것을 먼저 보여 주고(Value First), 기다리게 하지 않고(No More Loading), 기능은 꼭 필요한 만큼만 둔다(Minimum Features). 글은 하나의 친근한 말투(해요체)로 쓴다. 눈에 보이는 모든 디테일(글 한 줄, 버튼 이름, 꺼진 버튼의 이유, 누르는 크기, 마우스·초점 반응, 빈 화면·오류·불러오는 중, 되돌릴 수 없는 일의 확인과 되돌리기, 숫자의 단위)까지 기준을 두고, 기계로 잴 수 있는 것은 UX 점수(REQ-041)에 넣어 떨어지지 않게 한다. 시각 디자인을 토스 쪽으로 바꾸는 일은 안을 보여 주고 사용자가 고른 것만 적용한다(REQ-025). |
| REQ-059 | 가격은 현실 세계의 값을 최대한 따른다. 땅은 사업장이 있는 동네의 시세(㎡당·평당)로, 건물은 용도·넓이·층수에 따른 건설비로, 장비는 실제로 팔리는 값(1달러 = 1,343원)으로 정한다. 값마다 근거와 날짜를 문서에 남기고, 기사·공고·판매처에서 직접 확인한 값과 계산해 추정한 값을 구분해 밝힌다. 값이 현실에서 멀어지지 않도록 단가의 범위를 기계가 확인한다. |
| REQ-060 | 데이터센터 설비는 표준이 있으면 그 표준의 말로 답한다. 서버·스위치·PDU·분전반·CDU는 DMTF Redfish(스키마를 기계가 대조한다), 스위치·UPS는 SNMP(UPS-MIB RFC 1628, IF-MIB, SNMPv2-MIB), 항온항습기·냉동기·CDU·발전기·분전반·UPS는 BACnet(ANSI/ASHRAE 135)이다. 값은 모두 월드의 상태에서 나오고, 쓰기는 월드를 실제로 바꾸며(예: 항온항습기 설정온도, 차단기 재투입), 전원이 없는 설비는 응답하지 않는다. 그 설비가 쓰지 않는 말로 물으면 어떤 말을 쓰는지 알려 준다. 표준이 정한 번호(BACnet 객체·속성·단위·오류, SNMP 오류 상태)는 표준과 같다. 표준이 없는 설비(모드버스처럼 기기마다 레지스터가 다른 것)는 흉내 내지 않는다. |
| REQ-061 | vCenter와 Aria Operations(vROps)의 응답은 제조사가 공개한 API 참고서가 말하는 모양을 따른다. 필수 항목은 빠지지 않고, 참고서에 없는 항목은 만들지 않고, 열거값은 참고서의 값만 쓴다. 참고서에서 옮겨 적은 스키마로 기계가 대조하고, 제품 버전(프로파일)마다 확인한다. 참고서가 말하지 않는 것은 흉내 내지 않고 비워 둔다(예: 월드에 없는 VM의 디스크·네트워크 카드). |
| REQ-062 | 스위치는 자기가 쓰는 운영 체제의 말로 답한다. 아리스타 EOS, 시스코 NX-OS, 시스코 IOS XE마다 명령줄(SSH)의 프롬프트·모드·줄임말·오류 문구·표 모양이 다르고, EOS는 eAPI, NX-OS는 NX-API(JSON)로도 부른다. 포트 `shutdown`·`no shutdown`은 월드의 링크를 실제로 끊고 되살려서 반대편 장비, SNMP, 알람, 서버의 네트워크가 함께 바뀐다. 호스트명과 포트 설명은 명령줄과 SNMP가 같은 값을 본다. 장비 하드웨어는 가상 제조사이고 OS 이름·버전·명령 모양만 현실을 따른다. 월드에 없는 기능(VLAN, MAC 표, 라우팅, 패킷 카운터)은 흉내 내지 않는다. |
| REQ-063 | PDU 콘센트를 하나씩 끄고 켤 수 있고, 랙은 두 규격을 다룬다. 콘센트를 끄면(Redfish `Outlet.PowerControl`) 그 케이블에 달린 장비는 그 급전을 잃는다. 급전이 하나뿐이면 꺼지고 알람이 오르고, 둘이면 남은 급전으로 계속 돈다. 랙은 EIA-310 19인치와 OCP Open Rack v3(ORv3: 21인치 장비, 48mm OpenU, 48V 버스바를 먹이는 파워 셸프)가 있다. 한 규격의 장비는 다른 규격의 랙에 달리지 않고, 이유를 말해 준다. 파워 셸프는 Redfish에서 `PowerShelf`로 보이고 콘센트가 없다. 현실의 ORv3 세부(전원 모듈 N+1, BBU, 버스바 전류)와 콘센트별 계량은 흉내 내지 않는다. 장비값은 대부분 추정이다. |
| REQ-064 | 스위치는 2계층과 3계층을 안다. VLAN, MAC 주소 표, ARP, VLAN 인터페이스(SVI)의 IP, 연결된 경로와 정적 경로, 게이트웨이가 있다. 명령줄(`show vlan`, `show mac address-table`, `show ip route`, `show ip arp`, `ping`, `traceroute`, 그리고 `vlan`, `switchport ...`, `interface vlan`, `ip address`, `ip route` 설정)과 eAPI·NX-API로 보고 바꾼다. 처음 모양은 케이블에서 정해진다(랙마다 VLAN과 /24, 위쪽 스위치가 게이트웨이, 스위치 사이 케이블은 /31). 설정을 바꾸면 길이 실제로 바뀐다. 포트를 다른 VLAN에 넣거나, 트렁크에서 VLAN을 빼거나, VLAN 인터페이스를 끄거나, 경로를 지우면 서버가 닿지 않게 되고(`ping`이 실패한다) 알람 `host_unreachable`이 그 서버를 이름으로 말한다. 케이블이 끊겼거나 전원이 나가서 닿지 않는 서버는 이 알람이 아니라 기존 링크·전원 알람이 말한다. 스패닝 트리와 BGP는 REQ-065가 다룬다. LACP, 패킷 카운터, OSPF, MAC 에이징과 이동, 서버 쪽 설정은 흉내 내지 않는다. |
| REQ-065 | 사업장의 네트워크는 한 가지가 아니다. 이번엔 **레거시**(VLAN과 트렁크, 스패닝 트리, 위쪽 스위치의 VLAN 인터페이스가 게이트웨이)와 **클라우드**(leaf-spine: 말단 스위치의 모든 위쪽 케이블이 라우팅 포트, 케이블마다 eBGP 세션, 모든 말단에 같은 anycast 게이트웨이, VXLAN·EVPN)를 구분한다. 어느 쪽인지는 스위치 속성 `fabric`(`legacy`가 기본, `cloud`)이 정하고, 생성기는 장비 묶음(family)에 따라 팟마다 하나를 고른다. 클라우드에서는 `router bgp`, `neighbor … shutdown`(NX-OS는 `neighbor` 아래 `shutdown`), `show ip bgp summary`, EVPN 요약, VNI 표, `show running-config`의 BGP·VXLAN 줄을 세 OS의 말로 보고 바꾼다. 세션은 케이블이 살아 있고 양쪽 스위치에 전원이 있고 아무도 끄지 않았을 때만 선다. 끄면 그 세션으로 배운 경로가 사라지고, 남은 길로 돌거나 서버가 끊기며(`host_unreachable`), 끈 스위치에 알람 `bgp_session_down`이 선다. 배운 경로는 `no ip route`로 지울 수 없다. 레거시에서는 `show spanning-tree`가 루트와 막힌 포트를 보여 주고, 케이블을 뽑거나 루트 스위치 전원을 내리면 트리가 다시 선다. 이웃과 AS 번호는 케이블에서 정해지므로 `neighbor … remote-as`는 이미 그 값일 때만 받는다. 경로 속성(MED, 커뮤니티), EVPN 경로의 실제 교환, 시간에 따른 수렴, VLAN별로 다른 STP 루트, BGP를 지우는 `no router bgp`는 흉내 내지 않는다. GPU 네트워크는 REQ-067이 다룬다. |
| REQ-066 | GPU는 칩 이름으로 다룬다. 현장에서 쓰는 H100, H200, B200, B300을 NVIDIA가 공개한 사양(메모리 종류와 용량, 메모리 대역폭, 장당 전력, NVLink, 짝으로 오는 NIC)으로 가진 사양표가 있고, 서버 모델은 `gpuModel`로 어느 칩을 얹었는지 말한다. 8장짜리 HGX 서버가 칩 세대마다 있고(H100·H200 8U, B200 10U, B300 8U 공랭과 4U 수랭) 값은 판매처에 올라온 8-GPU 서버 가격을 따른다. 베라 루빈은 내년(2027) 도입 예정이라 사양표에 "도입 예정"으로만 있고 어느 서버에도 얹히지 않으며, 빌더가 그 사실을 알려 준다. 서버의 BMC(Redfish)는 `Systems/…/Processors`에 CPU와 GPU를 늘어놓고, 칩이 정해진 GPU는 제조사·모델·메모리·장당 전력·일련번호를 말한다. 수랭 서버는 수랭 랙에만 달린다는 기존 규칙이 그대로 적용된다. 사양표의 값은 공개 자료에서 확인한 것과 보도에 기댄 것(루빈)을 나누어 밝힌다. GPU 칩 단위의 온도·전력·사용률(nvidia-smi, DCGM), NVLink 구성, GPU 네트워크(InfiniBand·RoCE)는 이 요구사항이 다루지 않는다. |

| REQ-057 | 사업장의 건물은 지도와 배치도가 보여 주는 이름과 자리를 따른다. 화성은 12·13라인·S4·15·16·17·S3·V1과 변전소·UT3·사무동·HPC센터(V1 앞 잔디밭)·DSR(북동쪽 끝), 평택은 P1~P6(P5·P6는 아직 비어 있는 자리)과 복합동·사무동·그린동·정수장·물류센터·고덕변전소, 기흥은 S1·6라인·NRD-K다. 월드가 만들지 않는 건물(사무동, 유틸리티동, 정수장, 변전소, 물류센터, 공사장)도 그 자리에 그려지고 다른 꾸미기가 덮지 않는다. |
